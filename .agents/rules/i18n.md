# User-Facing Text Rules

Mandatory conventions for text the Go backend produces for a person to read: web console API messages, errors returned to AI clients, stored log content, emails and notifications, and server log lines. `AGENTS.md` defines when a task touches user-facing text (see **User-facing text (mandatory read gate)**); any task that matches MUST read this whole file before planning, coding, or reviewing. Tasks that match none of those triggers may skip it. Rules use the same MUST / Do NOT wording as `AGENTS.md` and carry the same weight.

**English literals only:** String literals in Go code MUST be English. Text in other languages belongs in the locale files (`web/src/i18n/locales/*.json`, `i18n/locales/*.yaml`) and in comments. Data that must stay as written (default group descriptions, vendor names, stored filter values) lives only in the files listed in `TestGoStringLiteralsAreEnglish` (`i18n/i18n_test.go`); add a file there only for such data, never for a message.

**Who translates:** The reader decides where a text is translated. Do NOT translate the same text in both places.

- **Web console APIs** (handlers under `/api/*`, the middleware in front of them, and the `model/` and `service/` errors they return): the web console translates, in all seven interface languages. The backend sends the English source text and never translates it.
- **AI-client APIs** (relay routes such as `/v1/*`, token authentication, distribution, rate limiting, pre-consume): no web console is in between, so the backend translates with `i18n.T(c, i18n.MsgXxx, params)` in the language saved by the token's user, then the language of the request's `Accept-Language` header.
- **Stored text shown later** (usage, top-up and system log content, task fail reasons): store structure, never a translated sentence. The viewer's language is not known when the row is written, and an administrator reads other users' rows.
- **Emails and notifications**: the backend translates with `i18n.Translate(lang, key, params)` in the recipient's saved language (`UserSetting.Language`), then the request language (`i18n.StatedLang`). Pass an empty language when neither exists.
- **Server logs** (`common.SysLog` / `SysError` / `FatalLog`, `logger.Log*`, `log.*`, `fmt.Print*`): English only. They are not translated.

**Web console messages:** Build them with `common.NewMessage(key, params)`, `common.ApiErrorT(c, key, params)` or `common.ApiSuccessT(c, key, data, params)`.

- The key is the English source text and the key of the entry in `web/src/i18n/locales/en.json`. Write it as a string literal or constant at the call, so `TestWebConsoleMessageKeysAreTranslated` can check it. Reuse an existing key with the same meaning before adding one.
- Dynamic values go in params and appear in the key as `{{snake_case}}` placeholders. Do NOT concatenate or `fmt.Sprintf` them into the key. Params hold display-ready values: format quota with `logger.FormatQuota` and fixed-precision numbers with `fmt.Sprintf`.
- A `*common.Message` is an `error`. `model/` and `service/` code returns it, and `common.ApiError(c, err)` sends `message` (English text), `message_key` and `message_params`. Send such errors through `common.ApiError`; a hand-written `gin.H{"message": err.Error()}` drops the key. Never declare a `*common.Message` variable and return it as `error` (typed nil).
- An error that can reach both a web console response and an AI-client response stays a plain English error.
- Responses with their own shape keep it and add `message.Fields()`.
- Add every new key to all seven files in `web/src/i18n/locales/` with the same placeholders. A plain string key (a task fail reason, a built-in group description) has no `common.NewMessage` call: register it in `web/src/i18n/static-keys.ts` and show it with `translateServerText`, because the same field also carries upstream or administrator text that must be shown as written.
- In the web console, `getServerErrorMessage` / `handleServerError` / `createServerError` translate `message_key`. Code that reads a response message itself MUST use `getServerMessage(response)`, not `response.message`.
- Authentication messages MUST stay as generic as before; the existing `code` values are the contract the web console maps.

**AI-client and notification messages:** Add the key constant to `i18n/keys.go` and the text to all three files in `i18n/locales/` (`en`, `zh-CN`, `zh-TW`), with go-i18n placeholders (`{{.Name}}`). `TestLocalesRenderEveryKey` requires the constants and the three files to list the same keys. Remove a key when its last use goes away.

**Reader who states no language:** A new-api gateway that uses another one as its upstream matches the upstream's error text, for example to disable a channel whose account ran out of quota. The messages listed in `chineseByDefault` (`i18n/keys.go`) were Chinese for every reader before the backend translated them, so they stay Chinese, with their original wording, when the account has no saved language and the request has no `Accept-Language`. Do NOT reword their `zh-CN` text, and do NOT add new keys to that list; new keys are English for such a reader.

**Stored text:**

- Log content is `[]*common.Message` (`model.RecordLog`, `model.RecordTopupLog`, `RecordConsumeLogParams.Content`, `RecordTaskBillingLogParams.Content`). It is stored as `other.content_parts`; the `content` column keeps the English text for exports and older rows. The web console renders it with `renderLogContent`.
- Audit and login logs keep their `other.op` action and params, with the template in `AUDIT_TEMPLATES` (`web/src/features/usage-logs/lib/format.ts`) and the English fallback in `auditContentTemplates` (`controller/audit.go`).
- A task or Midjourney `fail_reason`, and a refund `reason`, written by the gateway is an English key without params. Upstream text is stored as received.
