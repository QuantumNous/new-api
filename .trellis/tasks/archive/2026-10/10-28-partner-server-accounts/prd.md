# 合作方服务端密钥接入：子账号首次使用自动开户

## Goal

让合作方（首个为可得财务，测试站 `test.cw.mercuryseek.cn`）把野菜API当作内置的模型服务商接入：合作方后端持服务端密钥，为它的每个用户在野菜自动开一个子账号、领取长期有效的模型 API Key、查询余额与消耗，并为用户创建充值订单。终端用户全程不需要登录或授权野菜账号，在合作方界面内付款，钱直接充进自己的子账号钱包。

参照模式：AdsPower 内嵌 FlashIP，用户无需登录服务商账号。

## Background

- 现有 Partner OAuth（授权码 + PKCE，`.trellis/spec/backend/partner-oauth.md`）已上线。绑定、刷新令牌和 Key 30 天硬截止，刷新不延长。可得的日报机器人、工单自动回复等后台任务要长期运行，不适合这种方式。
- 可得测试站目前在自己页面上收集野菜账号密码，并嵌入人机验证（截图，2026-10-28）。这会让第三方接触用户密码明文并绕过 2FA/Passkey，不符合 OWASP。本任务上线后，可得必须删除该表单（见“外部依赖”）。

## Key Decisions（用户已确认）

| # | 决策 | 结论 |
|---|---|---|
| D1 | 接入形态 | 服务端密钥直连，用户无需在野菜登录或授权；与现有 Partner OAuth 并存，后者行为不变 |
| D2 | 账号模型 | 每个合作方用户对应一个真实的野菜用户（子账号），按 `(合作方, external_user_id)` 唯一映射，各自独立钱包 |
| D3 | 开户时机 | 首次使用自动开户（2026-10-28“做法一”）：写操作遇到未知 `external_user_id` 时自动开户；读操作不开户 |
| D4 | 子账号限制 | 随机用户名、无密码、无邮箱，不能通过任何方式登录网页；不发注册赠额、不参与邀请奖励和充值返现 |
| D5 | 认证 | 复用 `partner_oauth_clients`，新增服务端授权方式与专用 scope；支持新旧两把密钥并存轮换、出口 IP 白名单、限流、审计日志；写操作必须带 `Idempotency-Key` |
| D6 | 资金模式 | **野菜收款**（2026-10-28 确认，即原 B 方案）：合作方为子账号创建 Epay 充值订单，用户付款给野菜，额度直接进子账号钱包；不做额度池 |
| D7 | 分组 | 每个合作方一个专用用户分组，便于定价和渠道隔离；子账号同时可以使用 `default` 分组 |
| D8 | Key 数量 | 每个子账号一把模型 Key，可以轮换；额度不限，但花费受子账号钱包余额约束；长期有效 |
| D9 | 子账号上限 | 每个合作方最多 100,000 个子账号，管理员可以调整 |

| D15 | 到账确认 | 可得轮询我们的订单查询接口；本期不做我们到可得的 Webhook；用户扫码付款后没有浏览器跳回 |
| D16 | 开户速率 | 每个合作方每分钟最多开 60 个子账号，管理员可以调整 |
| D17 | Key 轮换 | 由合作方调用接口主动触发，我们不定期强制轮换；支持“立即作废旧 Key”（怀疑泄露时）和“旧 Key 24 小时后作废”（计划轮换，默认）两种模式 |

| D21 | 发票、退款、分成 | 本期不考虑 |
| D22 | 统计口径 | 子账号的消耗、用量和收入照常计入所有报表，不排除 |
| D23 | 后台展示 | 用户列表给子账号加“合作方子账号”标记，并支持按合作方筛选；2FA 开启率统计的分母去掉子账号（2026-10-28 确认） |

## Resolved（联调结论）

- Q16（2026-10-28，经用户同意）：用生产商户号对 `https://zpayz.cn/mapi.php` 下了一笔 10 元 alipay 测试单（`GATEATEST1793164650`，未支付）。返回 `code=1`，`qrcode`、`payurl`、`payurl2` 都是同一个支付宝链接 `https://qr.alipay.com/…`（二维码内容），`img` 是 ZPay 托管的二维码图片地址。用同一个订单号再调一次，返回同一个 ZPay 订单（`O_id` 不变）和一个新的支付宝链接，不报重复。现有实现（优先 `qrcode`、忽略 `img`、失败后用同一订单号重试）不用改。生产只开了 alipay，wxpay 未验证。

## Requirements

### R1 合作方服务端认证

- 合作方用 `client_id` 加服务端密钥换取短期访问令牌，令牌只能用于本任务新增的接口。
- 一个合作方最多同时有两把有效密钥：轮换时先发新密钥，合作方切换完成后再吊销旧的。密钥只展示一次，只存哈希。
- 可配置出口 IP 白名单（可选；为空时后台显示风险提示）；配置了白名单时，不在名单内的请求一律拒绝，包括换取令牌的请求。白名单只对经过主站入口的请求可靠。
- 成功和失败的令牌签发都写审计；鉴权失败按类别节流后写审计。
- 服务端接口不返回 CORS 头，不支持浏览器直接调用。
- 按合作方限流，与现有 Partner OAuth 的按绑定限流互不影响。
- 合作方被停用或删除后，令牌立即失效。
- 只在主站 Host 提供；敏感响应 `no-store`；带 `X-Request-Id`。

### R2 子账号与自动开户

- 合作方以 `external_user_id` 标识自己的用户：32–64 个字符，字符集为 `A-Z a-z 0-9 . _ -`，区分大小写（MySQL 默认排序规则不区分大小写，实现时要保证唯一约束也区分大小写）。同一合作方下唯一，不同合作方之间互不可见。
- **会开户的接口：** 领取或轮换 Key、创建充值订单。遇到未知 `external_user_id` 时，在同一事务内开户并完成原操作。
- **不开户的接口：** 查询账号、余额、订单、消耗明细。遇到未知 `external_user_id` 返回 404，没有任何写入。
- 同一 `external_user_id` 并发首次请求时，只产生一个子账号，其余请求返回同一个账号。
- 达到子账号上限（默认 100,000）或开户速率上限时返回明确错误码，不建账号。

### R3 子账号属性

- 初始额度为 0；不发 `QuotaForNewUser`；没有邀请人，不给任何人发邀请奖励；充值订单不产生返现。
- 钱包账本完整：开户时写入不可退款的零额开户事件，与现有注册流程一致。每笔充值入账沿用现有 Epay 入账路径的钱包事件。
- 不能登录：密码登录、第三方 OAuth/OIDC 登录、Passkey、找回密码、“注册即登录”等全部路径都不能进入该账号，也不能为它创建个人访问令牌。
- 用户分组为合作方配置的专用分组（D7）。该分组可以使用 `default` 分组，具体做法在 design 阶段确定，优先复用现有的分组配置能力：分组特殊可用分组、分组对分组倍率、Key 自动分组。
- 管理员能在后台识别出子账号及其所属合作方。

### R4 模型 API Key

- 首次领取时发 Key；重复领取返回同一把 Key。
- 轮换：发一把新 Key。旧 Key 按合作方选择立即作废，或 24 小时后作废（默认）；宽限期内新旧两把都可用，任何时候最多两把有效。
- Key 长期有效、不设额度上限，但请求仍受子账号钱包余额约束，余额不足时模型接口照常拒绝。
- 子账号被停用或合作方被停用时，Key 全部失效，不能通过再次领取或轮换绕过。
- 领 Key 可以反复取回明文；领 Key 和轮换按合作方单独限流（每分钟 120 次）。
- 管理员可以一键吊销某个合作方名下的全部 Key（后台执行）；之后合作方通过轮换取得新 Key。

### R5 查询

- **账号：** 状态、钱包余额（内部额度和展示货币金额，口径同现有 `/api/integrations/v1/balance`）、累计消耗、创建时间。
- **充值订单：** 只能查本合作方的订单，返回字段同现有 Partner OAuth 订单查询。
- **消耗明细（D12）：** 按子账号查询模型消耗记录，包括时间、模型、token 用量、扣除额度。分页，单次时间跨度不超过 31 天，最早只能查到 90 天前，单独限流（每个合作方每分钟 60 次），字段采用白名单，不返回请求内容、IP、渠道等内部信息。是否另外提供按天汇总在 design 阶段确定。

### R6 充值（野菜收款）

- 复用现有 Epay 下单、回调和入账逻辑，订单挂到子账号而不是 OAuth 绑定；不修改现有 `partner_oauth_payment_orders` 表的约束。
- 金额语义、最小值、最大值、分组充值倍率（按子账号专用分组）、预设折扣、钱包容量都与网页端一致。
- 必须带 `Idempotency-Key`，幂等范围为“合作方 + Key”；相同 Key、相同请求体返回同一订单；相同 Key、不同请求体返回 409。
- 限流分两层：按子账号，以及按合作方总量。
- 订单返现上下文标记为不参与返现（不记录请求 IP/UA/设备）。
- 支付合规未确认、Epay 未配置时返回 503，与现有行为一致。
- 下单成功时返回二维码内容（`qr_code`）。ZPay 没给二维码时，退回返回支付链接（`pay_url`），两者至少有一个。合作方可传终端用户 IP，ZPay 要求必填，不传时用合作方服务器 IP。
- 幂等重放返回同一笔订单和同一个二维码，不会在 ZPay 再下一次单。
- 到账以订单查询接口返回的 `success` 为准，合作方轮询。

### R7 停用与管理

- 合作方可以停用、恢复单个子账号：停用后 Key 失效，不能再创建充值订单；余额保留。
- 停用合作方：其所有子账号的 Key 失效，令牌失效。重新启用后，只恢复因“合作方停用”而失效的子账号（D11）。实现上要能区分失效原因，不能把所有禁用的 Key 统一恢复。
- 删除合作方（D13）：本期不设计业务流程。安全默认值是，有子账号的合作方禁止删除，只能停用，避免留下仍然有效的 Key。
- 管理员可以配置合作方的服务端模式：启用开关、IP 白名单、子账号上限、开户速率、专用分组，以及密钥的签发、轮换和吊销。敏感操作沿用现有的 `sensitive_write` 二次验证。
- 管理后台可以按合作方查看子账号列表。

### R8 审计

- 写入 `partner_oauth_authorization_logs`（或同表新增 action）：令牌签发失败、开户、Key 首次签发与轮换、充值下单、子账号停用与恢复、合作方停用与恢复、密钥轮换与吊销、IP 白名单拒绝。
- 不记录密钥、令牌、Key、`Idempotency-Key` 原文、`checkout_url` 和请求体。

## Constraints

- **认证安全：** 按 AGENTS.md 6.2 对照 OWASP ASVS 5.0 及 OAuth 2.0、Authentication、Session Management、Secrets Management 等 Cheat Sheet。交付时列出引用的条目号、已验证项和未验证的缺口；存在缺口时不得声称合规。
- **计费与返现：** 遵守 `.agents/rules/billing.md` 的额度换算与安全不变量，以及 `.trellis/spec/backend/referral-recharge-cashback.md` 的事务、额度防护（quota fence）和钱包账本要求。返现排除理由沿用 `partner_oauth`，如需新增理由要同步修改返现契约。子账号的成功充值会在“首充”活动里计为已有充值，因为子账号本身不参与返现，所以没有影响。
- **数据库验证：** 按用户要求只在一次性 Docker 容器中的 PostgreSQL 上验证（全新建表、从线上版本升级、重复迁移两次）。不跑 SQLite 和 MySQL，并在交付说明中如实写明，不声称三库兼容。代码本身仍要按三库兼容的规范写。
- **现有功能：** Partner OAuth 授权码流程、接口和数据行为保持不变。
- **文档：** `docs/` 下只新建 `docs/partner-server-api.md`（D24），不新增其他文件。规则变化同步更新 `.trellis/spec/backend/partner-oauth.md` 或新契约文件。
- **Git：** 在 `feat/partner-accounts` 分支开发；只提交本任务文件、使用明确路径；不直接推送 `main`（合入即部署生产）。
- **代码改动：** 未经用户明确确认，不开始改代码；本 PRD 之后还需要 `design.md` 和 `implement.md` 并经用户审阅。

## External Dependencies

- **可得侧：** 删除页面上收集野菜账号、密码和人机验证的表单，改为由可得后端调用本任务的接口；页面文案“使用野菜账号安全登录”同步修改。服务端密钥和模型 Key 只能放在可得后端，不能下发到浏览器。若启用白名单，提供出口 IP 列表。`external_user_id` 永久不变，变更会导致用户拿到新的空账号。
- **运维侧（建议，不在本任务范围）：** 把 WireGuard `8009` 的 TCP 直通入口改为会覆盖 `X-Forwarded-For` 的 HTTP 代理，或者为 `new-api` 显式设置 `TRUSTED_PROXIES`，让 IP 白名单在所有入口都可靠（`security-review.md` M2）。
- **运营侧：** 创建专用分组，并为它配置渠道、分组倍率、可用分组；否则子账号的模型列表为空。

## Acceptance Criteria

- [ ] 用服务端密钥能换到访问令牌；密钥错误、被吊销、合作方停用、IP 不在白名单时分别被拒绝；两把密钥并存期间都可用，吊销旧密钥后旧密钥立即不可用。
- [ ] 对未知 `external_user_id` 首次领 Key 或下单时自动开户；重复和并发请求只产生一个子账号和一把 Key；查询未知 ID 返回 404，且没有写入；只有大小写不同的两个 ID 是两个不同账号。
- [ ] 子账号初始额度为 0，没有注册赠额、邀请奖励和返现，钱包开户事件存在；所有登录路径都无法进入子账号。
- [ ] 子账号使用专用分组，能使用 `default` 分组的模型，计价符合分组配置。
- [ ] Key 不设过期、不设上限；余额为 0 时模型请求被拒绝；“立即作废”轮换后旧 Key 立刻失效，“宽限”轮换后旧 Key 24 小时内仍可用、之后失效。
- [ ] 下单返回二维码内容或支付链接；同一 `Idempotency-Key` 重放不会在 ZPay 重复下单；ZPay 调用失败时返回 503，用同一 Key 重试可以恢复。
- [ ] 停用子账号、停用合作方后 Key 全部失效，再次领取或轮换也拿不到可用的 Key；重新启用合作方后只恢复因合作方停用而失效的子账号。
- [ ] 达到子账号上限或开户速率上限时被拒绝，且不产生账号。
- [ ] 充值：下单拿到收银台信息，Epay 回调后额度进入子账号钱包；幂等重放不会重复下单；请求体不同返回 409；没有返现；只能查到本合作方的订单。
- [ ] 消耗明细只返回本合作方、该子账号的记录和白名单字段，分页和时间范围上限生效。
- [ ] 审计日志覆盖 R8 列出的事件，以及成功和失败的令牌签发、节流后的鉴权失败，且不含敏感值。
- [ ] OAuth 的 `pcs_` 密钥不能用于 `client_credentials`，服务端 `pss_` 密钥不能用于授权码和刷新流程；`pst_` 令牌访问 `/api/integrations/v1` 被拒绝，`oa_` 令牌访问 `/api/partner/v1` 被拒绝。
- [ ] 服务端接口不返回 CORS 头，预检返回 403。
- [ ] 领 Key 和轮换超过每分钟 120 次返回 429；消耗明细超过 90 天前或超过每分钟 60 次被拒绝。
- [ ] 吊销合作方全部 Key 后，所有旧 Key 被拒绝，余额不变，合作方通过轮换拿到可用的新 Key；合作方停用在后台执行，接口立即返回，服务端接口立即拒绝。
- [ ] 现有 Partner OAuth 的测试全部仍然通过。
- [ ] PostgreSQL（Docker）上全新建表、从线上版本升级、重复迁移两次均通过；交付说明写明只验证了 PostgreSQL。
- [ ] 后端测试、前端测试、类型检查和构建通过；OWASP 引用与缺口写入交付说明。

## Out of Scope

- 额度池、批发价，以及合作方代付或预充值。
