# 方案安全审查：合作方服务端密钥接入

- 审查对象：`prd.md`、`design.md`、`implement.md`（提交 `bd901743d`），**方案阶段，尚无代码**。
- 依据：OWASP ASVS 5.0（2026-10-28 从 `OWASP/ASVS` 仓库 `5.0/en` 读取原文核对条目号）、OAuth 2.0 / Secrets Management / Logging Cheat Sheet，以及 AGENTS.md §6.2。目标等级为 L2；L3 条目单独列为已接受的缺口。
- 本次核实的现网事实（只读，未输出任何秘密值）：
  - 生产 `new-api` 容器未设置 `TRUSTED_PROXIES`。程序默认信任回环地址、RFC 1918 和 IPv6 ULA 地址发来的转发头（`middleware/trusted_proxies.go`）。
  - 主站入口为 Cloudflare → 本机 nginx（`/etc/nginx/conf.d/newapi.conf`）。nginx 只信任 Cloudflare 网段发来的 `CF-Connecting-IP`，并且所有 location 都用 `proxy_set_header X-Forwarded-For $remote_addr` 覆盖转发头，再转到 `127.0.0.1:8008`。
  - WireGuard 入口 `10.77.0.2:8008`（`newapi_proxy.conf`）同样覆盖转发头。但 `10.77.0.2:8009` 是 Docker 直接映射的端口，并且有一个 nginx **TCP 直通**中转（`streams-enabled/xiaoji-dmit15t-ip99.conf`，监听 `10.77.0.99:8009`），**不会**改写 HTTP 头。
  - Gin 引擎级的 `CORS()`（`AllowAllOrigins=true`）在 `SetRelayRouter` 中注册，早于 `SetPartnerOAuthRouter`，因此对 `/oauth/token` 和之后注册的所有路由都生效。
  - 管理员接口 `PUT /api/user/` 可以给任意用户设置密码（`controller/user.go` 中 `UpdateUser` 的 `updatePassword` 分支），但不能设置邮箱或第三方身份；管理员的“绑定”类接口只有删除操作。

## 结论摘要

| 级别 | 编号 | 问题 | 建议 |
|---|---|---|---|
| 高 | H1 | 合作方密钥相当于最多 10 万个钱包的总钥匙：IP 白名单是可选的，而且 Key 可以被反复读出明文 | 白名单改为必填；Key 只在签发和轮换时返回一次明文；领 Key 接口单独限流；新增“吊销该合作方全部 Key”应急操作 |
| 中 | M1 | 设计写的是“成功换取令牌不写审计”，不满足 ASVS 16.3.1；鉴权失败也没有记录（16.3.2） | 记录每次成功和失败的令牌签发；鉴权失败按类别记录，并限制写入频率 |
| 中 | M2 | 通过 `8009` 直通口进来的请求可以伪造 `X-Forwarded-For`，从而绕过 IP 白名单（ASVS 4.1.3） | 方案里写明白名单只对主站入口有效；运维侧把 8009 改为会覆盖转发头的 HTTP 代理，或者显式设置 `TRUSTED_PROXIES` |
| 中 | M3 | 消耗明细可以查任意久远的时间，对用量很大的用户来说查询开销大（ASVS 2.4.1） | 只能查最近 90 天；这个接口单独限流（每个合作方每分钟 60 次） |
| 低 | L1 | 全局 CORS 允许任意来源，对 `/oauth/token` 和新接口也生效（ASVS 3.4.2） | 服务端接口去掉 CORS 响应头，让浏览器里的误用直接失败 |
| 低 | L2 | 轮换默认 24 小时宽限；合作方在密钥泄露时如果忘了选“立即作废”，旧 Key 还能用 24 小时 | 文档强调；H1 中的“全部吊销”提供兜底 |
| 低 | L3 | 合作方停用的批处理如果放在 HTTP 请求里同步执行，可能超时，留下部分完成的状态 | 改为后台执行、可以重入，并在后台显示进度 |
| 低 | L4 | `external_user_id` 出现在 URL 路径里，会进入 nginx 和 Cloudflare 的访问日志（ASVS 14.2.1） | 字符集已经排除 `@`，邮箱不可能出现；接入文档要求只能使用不透明 ID |
| 低 | L5 | 调用 ZPay `mapi.php` 是新增的出站请求 | 只允许 `https` 的支付地址；ZPay 失败时返回 503、不重试风暴（16.5.2）；响应内容不写日志 |

## 详细说明

### H1 合作方密钥的爆炸半径

**现状（方案）：** 服务端密钥加 1 小时令牌，就能对该合作方名下的任意子账号调用 `POST /accounts/{eid}/credential`。这个接口“天然幂等”，每次都返回同一把 Key 的**明文**。IP 白名单为空时不限制来源。

**风险：** 合作方密钥一旦泄露（例如出现在可得的日志或配置仓库里），攻击者可以从任何地方遍历 `external_user_id`，批量导出最多 10 万把长期有效、不限额度的 Key，花用户钱包里的真实充值金额。这些 Key 被导出后，合作方侧完全察觉不到。

**依据：** ASVS 13.3.2（访问秘密资产遵循最小权限）、14.2.6（只返回功能所需的最少敏感数据，L3）、2.4.1（防止批量调用导致数据外泄）、8.1.3（基于 IP 等环境属性的授权，L3）。

**建议：**
1. **IP 白名单必填：** 服务端接入开启时，白名单不能为空。可得是后端调用，出口 IP 是固定的。这是收益最大的一项。
2. **Key 只返回一次明文：**
   - 首次签发或轮换时返回完整的 `api_key`；
   - 之后再调用领 Key 接口，只返回 `key_id`、掩码（例如 `sk-abcd…wxyz`）和创建时间；
   - 合作方丢失 Key 时调用轮换。

   **代价：** 首次签发的响应如果在网络上丢失，合作方只能再轮换一次。不过轮换本身要求带 `Idempotency-Key`，用同一个 Key 重试会返回同一把新 Key，所以影响很小。
3. **领 Key 和轮换单独限流：** 例如每个合作方每分钟 120 次。正常业务只在用户首次使用时领一次，这个额度足够。超出时写审计日志。
4. **应急操作：** 管理员新增“吊销该合作方全部子账号 Key”（批量立即作废，后台执行），用于合作方密钥泄露的场景。之后合作方逐个调用轮换（`immediately`）拿新 Key。这个操作要求 `sensitive_write` 加二次验证。

### M1 认证事件的审计不完整

**现状：** design §7 写着“成功换取令牌、普通查询不写审计日志”。

**依据：** ASVS 16.3.1（L2）要求记录所有认证操作，成功和失败都要记录；16.3.2（L2）要求记录授权失败。

**建议：**
- 每次 `client_credentials` 签发都记录（成功的 `partner_server.token_issue`，失败的 `partner_server.token_issue_failed`），频率大约每小时一次，几乎没有开销；
- `PartnerServerBearer` 拒绝的请求（令牌无效、IP 不在白名单、合作方被停用）按“合作方 + 原因”每分钟最多写一条，防止日志被刷爆；
- `client_id` 不存在时不写入，这类情况只依靠每个 IP 的限流。

### M2 绕过 IP 白名单的路径

**现状：** 主站路径是可靠的。Cloudflare 网段之外发来的 `CF-Connecting-IP` 不被信任，nginx 再用真实地址覆盖 `X-Forwarded-For`。但 `10.77.0.2:8009`，以及 `10.77.0.99:8009` 上的 TCP 直通中转，会把请求原样送到容器。容器看到的来源是内网地址，属于默认信任的代理，于是会采信客户端自己填写的 `X-Forwarded-For`。

**影响：** 能连入 WireGuard 网络的机器可以伪造来源 IP，绕过某个合作方的白名单。前提是攻击者已经拿到了该合作方的令牌。WireGuard 的对端是你自己的机器，所以属于纵深防御层面的问题，不是外网可以直接利用的漏洞。

**依据：** ASVS 4.1.3（由中间层设置的 HTTP 头不能被用户覆盖）。

**建议（二选一，都属于运维改动，不在本任务代码范围内）：**
- 把 8009 中转改成 HTTP 反向代理，并像 8008 一样覆盖 `X-Forwarded-For`；
- 或者给 `new-api` 显式设置 `TRUSTED_PROXIES`，只信任本机 nginx 进入容器时的来源地址（需要先确认 Docker 端口映射下容器实际看到的源地址）。

在此之前，方案和交付说明中要写明：IP 白名单只对经过主站入口的请求有效。

### M3 消耗明细查询的开销

`logs` 表的分页走 `(user_id, id)` 索引，但时间条件 `created_at` 不在这个索引里。查询很久以前的时间段时，需要倒序扫过这段时间之后的所有日志。

**建议：**
- 只允许查询最近 90 天；
- 单次查询的时间跨度保持 31 天上限；
- 这个接口单独限流，每个合作方每分钟 60 次。

依据：ASVS 2.4.1、13.1.3（L3，资源管理）。

### L1 CORS

引擎级的 `CORS()` 会给 `/oauth/token` 和新接口加上 `Access-Control-Allow-Origin: *`。接口用的是 Bearer 和 Basic 认证，不用 Cookie，所以不能跨站利用。但服务端接口本来就不该被浏览器调用。

**建议：** 在 `/api/partner/v1` 路由组和 `client_credentials` 的响应里删除 CORS 头，预检请求返回 403。这样如果可得把密钥放进前端，联调时会直接失败，问题能更早暴露。依据：ASVS 3.4.2。

### L3 合作方停用批处理的执行方式

批量停用 10 万个账号需要几十秒到几分钟，不能放在管理员的 HTTP 请求里同步执行。

**建议：**
- 状态接口只负责写 `suspended_at`，此时服务端接口立即全部拒绝，然后在后台运行批处理；
- 批处理可以重入，进程重启后从头扫描 `suspended_by_partner` 的差异即可；
- 后台显示“已处理 / 总数”。

### L5 调用 ZPay

- 只有 `PayAddress` 是 `https` 时才调用 `mapi.php`，否则返回 503，并记录一条不含敏感信息的错误日志（ASVS V12，出站连接加密）；
- 超时 10 秒，不在同一个请求内自动重试（ASVS 16.5.2，外部依赖失败时安全降级）；
- `qrcode` 和 `payurl` 不写入任何日志；
- 不使用 ZPay 的订单查询接口（`api.php?act=order`），因为它要求把商户密钥放在 URL 里（ASVS 14.2.1）。

## 方案中已经满足的要求

| 依据 | 方案中的做法 |
|---|---|

| 10.4.11 只分配必要的 scope | 单独的 `partner:accounts` scope，不出现在同意页上 |
| 10.3.1 令牌只在对应服务使用（audience） | 服务端令牌和 OAuth 令牌分表存储。**需要补充测试：** `pst_` 令牌访问 `/api/integrations/v1` 被拒绝，`oa_` 令牌访问 `/api/partner/v1` 被拒绝 |
| 10.4.10 机密客户端的后端请求必须认证 | 使用 Basic 认证，只存哈希 |
| 6.3.1、6.3.8 防暴力破解和账号枚举 | 失败统一返回 `invalid_client`，比较耗时一致，按 client 计失败次数限流 |
| 8.2.2、8.4.1 防止越权访问和跨租户访问 | 所有查询都同时限定 `client_id`；跨合作方访问统一返回 404 |

## 已接受的 L3 缺口（交付时如实列出）

- **10.4.16** 强客户端认证（mTLS、`private_key_jwt`）：使用共享密钥加 IP 白名单代替。
- **10.3.5、10.4.14** 持有证明约束的令牌（DPoP、mTLS）：令牌是 Bearer 形式，依靠 1 小时有效期和 IP 白名单降低风险。
- **8.3.2** 授权变更立即生效：合作方快照最多有 60 秒延迟；合作方停用后，批量禁用完成前模型 Key 仍然可用。
- **13.3.4、13.1.4** 密钥按计划自动过期和轮换：不强制过期，在接入文档中建议每 90 天轮换一次。

## 用户决定（2026-10-28）

| 编号 | 决定 |
|---|---|
| H1 | **IP 白名单保持可选**；**领 Key 接口可以反复返回明文**，以便合作方随时取回；领 Key 和轮换**单独限流**（每个合作方每分钟 120 次）。按“其他按建议”的指示，同时加入管理员“吊销合作方全部 Key”的应急操作（design §5.7） |
| M1 | 按建议：记录成功和失败的令牌签发；鉴权失败节流后记录 |
| M2 | 按建议：方案和交付说明写明白名单只对主站入口可靠；运维改动作为建议列入 PRD 外部依赖，不在本任务范围 |
| M3 | 采纳：最早只能查到 90 天前，单次不超过 31 天，每个合作方每分钟 60 次 |
| L1–L5 | 按建议 |

**用户接受的剩余风险（交付说明必须如实列出）：** 由于白名单可选、Key 可以反复取回，合作方密钥一旦泄露，攻击者在没有白名单的情况下可以从任意来源导出该合作方名下所有子账号的 Key。缓解只靠领 Key 限流（10 万个账号约需 14 小时才能全部导出）、审计记录，以及事后由管理员吊销全部 Key。对应 ASVS 13.3.2、14.2.6 未满足或部分满足。
