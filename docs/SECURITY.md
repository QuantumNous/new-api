# 安全工程规范

漏洞披露流程以 `.github/SECURITY.md` 为准；本文件描述开发约束。

## 信任边界

- 所有客户端请求、上游响应、媒体元数据、回调和管理配置均视为不可信输入。
- 认证确认身份，授权单独确认资源和动作；管理员接口不能只依赖前端隐藏。
- API key、JWT、OAuth secret、数据库 DSN、支付密钥和渠道密钥不得写入仓库、日志、错误响应或测试快照。

## 必须保留的防护

- 请求体大小、字段范围、URL/SSRF、回跳地址、限流和权限校验。
- 密码、Passkey、OAuth/OIDC、会话与刷新 token 的既有安全语义。
- 支付 webhook 的签名/来源校验、幂等与金额核对。
- 管理员日志中的敏感信息分层；普通用户不得读取 `admin_info`。
- 所有数据库查询使用参数绑定或 GORM，避免拼接不可信输入。

## 高风险改动

认证、授权、支付、密钥处理、SSRF、跨租户数据、数据库迁移和生产配置必须人工确认，并读取 `loop-constraints.md`。不得由 Loop 自动实施或部署。

## 双用途主 API Key

- 将 API 调用 Key 同时作为后台登录凭据会扩大泄露影响，只允许在有明确产品模式和人工审查时启用。
- 双用途模式必须限制普通用户只有一条主 Key；管理员和服务账号的多 Key能力不能被隐式改写。
- 登录有效性与 API 调用额度必须分离：额度耗尽可阻止调用，但不能阻止用户登录后台处理余额或安全设置。
- 主 Key轮换必须原子废止旧 Key，并撤销全部旧后台会话；失败时保持旧 Key和会话有效，不能产生双 Key或无凭据账户。
- 轮换不能复制旧 Key 的 disabled/expired 状态；新 Key 应为启用且永不过期，额度字段按账户原有状态保留。
- 邮箱找回必须发送一次性确认链接，不能在仅收到邮箱地址时立刻轮换 Key，公开响应不得泄露邮箱是否存在。
- 默认只允许在首次创建或成功轮换的单次响应中展示完整 Key，不进入 URL、日志、管理员响应或前端持久存储。

### L1 安全判定

- “完整 Key 通过邮件发送”会扩大邮件正文、转发、供应商日志、客户端同步和备份的泄露面。当前 L1 生产实现按产品方明确要求，在邀请注册成功后同时通过 HTTPS 一次性响应和邮件发送完整 Key；这是已记录的风险接受例外，不是默认安全基线。后续若扩大范围，必须完成供应商数据保留审查、邮件失败告警和 Key 轮换演练后再复审。
- `APIKeyLoginEnabled`、`EmailDefaultTokenEnabled` 是候选实现开关，不是安全完成标志。它们不能绕过普通用户单主 Key、角色隔离、登录/额度解耦、轮换事务或找回限流。
- 任何“重置成功但新 Key 未交付”的路径都必须留下可恢复的邮箱找回入口和审计记录；不能静默保留旧 Key，也不能创建第二条可用 Key。
- 轮换事务提交后的缓存发布、旧会话撤销属于后置交付步骤；若任一步失败，接口不能只返回普通错误而丢失新 Key，必须返回一次性新 Key并附非敏感告警，或把账户置于可审计、可重试的待交付状态。
- 该约束覆盖所有后置异常，不仅是已知的缓存或 Session 错误；未知/包装后的异常也不得让新 Key 已提交而响应不含 Key。
- 邮箱找回接口的成功/失败、响应时间和错误文案应尽量一致；邮件发送任务需要幂等键和按邮箱/IP/账户的速率限制。
- SMTP 凭据（尤其是 Gmail 应用专用密码）只能通过部署环境或密钥管理器注入；设置接口和状态接口不得回显 `SMTP_TOKEN`。启用单主 Key 前必须确认 SMTP 静态配置完整，并在隔离环境验证实际投递。
- 若登录密码或应用专用密码被粘贴到聊天、截图、日志或工单，应按已泄露凭据处理：先修改 Gmail 登录密码、撤销旧应用专用密码和活动会话，再生成新应用专用密码；不得继续使用或把旧值复制到 `.env`、文档、测试夹具或命令行参数。凭据轮换完成前禁止真实 SMTP 测试和生产启用。
- 邮箱并发注册/找回的数据库锁必须在目标隔离级别和索引状态下做运行时验证：MySQL 的 gap/next-key lock、PostgreSQL advisory lock 与 SQLite busy timeout 都不能仅凭静态代码视为等价保证。

## 验证

- 运行相关 Go/Bun 测试和静态检查。
- 检查 diff 中是否出现 token、secret、私钥、真实用户数据或宽权限配置。
- 仓库当前没有可确认的统一自动安全扫描命令，`gate.yaml` 标记为 UNKNOWN。
