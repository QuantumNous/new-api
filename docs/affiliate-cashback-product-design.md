# 邀请返现产品设计

> 文档状态：最终产品方案，待技术实现
> 适用范围：默认前端、用户注册、充值、邀请返现结算与管理后台
> 设计原则：所有用户保留邀请码；奖励统一使用用户额度；币种固定为 CNY；使用“全局默认 + 指定用户覆盖”，不引入代理等级或套餐。

## 1. 背景

现有系统同时存在两类邀请奖励：

1. 注册邀请奖励：邀请者奖励和受邀者奖励位于通用额度设置中。
2. 充值返现：受邀者达到充值条件后，邀请者获得用户额度返现，并经过冻结、解冻和转入账户余额流程。

这两类能力的配置入口、余额口径和管理方式不一致。本设计将其收口到“邀请返现”，保留每个用户的邀请码，同时允许管理员对指定邀请者单独配置规则。

## 2. 产品目标

- 将邀请者奖励、受邀者奖励移入“邀请返现”设置。
- 邀请者奖励、受邀者奖励和充值返现统一以用户 `quota` 作为实际记账单位。
- 邀请者奖励和受邀者奖励的发放时点由管理员选择。
- 充值返现支持“按比例”或“固定额度”两种计算方式。
- 充值返现次数由管理员选择“仅首次达标”或“每笔充值”。
- 返现比例在设置页和用户端统一以 `%` 展示。
- 单个邀请的最高返现支持明确的“不限额”状态。
- 仅支持将返现额度转入用户账户余额，不提供银行卡提现能力。
- 在冻结金额旁展示最早一笔待解冻时间，并支持查看逐笔解冻时间。
- 将“对账单”替换为“被邀请者充值记录”，在隐私保护下向邀请者展示返现明细。
- 全局规则作为默认值，指定用户可覆盖其中的单个字段。

## 3. 非目标

- 不建立普通、银牌、金牌等代理等级。
- 不提供现金、银行卡或第三方收款账户提现。
- 不允许邀请者管理受邀者的 API 密钥、模型权限、用户组或账户余额。
- 不向邀请者展示受邀者的完整邮箱、用户名、支付账户或其他敏感信息。
- 充值退款不在第一版自动冲正返现，由管理员逐笔人工处理。

## 4. 核心概念

| 概念 | 定义 |
| --- | --- |
| 邀请者 | 邀请码的所有者，所有正常用户都可成为邀请者 |
| 受邀者 | 在邀请码 7 天归因有效期内完成注册并绑定邀请关系的用户 |
| 邀请者奖励 | 按管理员配置的时点给予邀请者的固定用户额度，进入邀请者返现账户并冻结 |
| 受邀者奖励 | 按管理员配置的时点给予受邀者的固定用户额度，直接增加受邀者 `User.Quota` |
| 充值返现 | 受邀者通过钱包在线充值且达到条件后，给予邀请者的按比例或固定用户额度奖励 |
| 冻结返现 | 已生成但尚未到可用时间的用户额度 |
| 可用返现 | 已解冻，可按 quota 1:1 转入邀请者 `User.Quota` 的额度 |
| 个性化配置 | 管理员为指定邀请者设置的字段级覆盖值 |

## 5. 规则优先级

### 5.1 全局默认与指定用户覆盖

系统仅有一套全局默认规则，不建立规则套餐。每个可个性化字段都支持两种状态：

- `跟随全局`：读取当前全局值。
- `指定值`：仅对选中的邀请者生效。

有效值的计算方式为：

```text
有效值 = 指定用户的覆盖值 ?? 全局默认值
```

支持个性化的字段：

- 邀请返现启用状态。
- 邀请者奖励。
- 受邀者奖励。
- 注册奖励发放时点。
- 充值返现方式。
- 充值返现次数。
- 返现比例或固定返现额度。
- 单个邀请最高返现及“不限额”状态。
- 达标充值金额。
- 冻结时长。
- 是否允许查看被邀请者充值记录。

金额与额度口径：

- 页面币种固定显示 CNY，不提供币种切换配置。
- 充值金额和累计达标门槛使用实际支付的 CNY 金额。
- 所有奖励账户、冻结余额、可用余额和转入金额使用用户 `quota` 记账。
- 管理员看到的固定奖励、最高返现等输入框按账户余额的 CNY 展示方式呈现，提交时转换为 quota。

### 5.2 个性化配置页

管理后台的“邀请返现”页分为三个标签：

1. `全局设置`：维护全体用户默认值。
2. `用户个性化设置`：按用户名、邮箱或用户 ID 搜索指定用户，编辑字段级覆盖值。
3. `人工调账`：查询充值返现记录，并在退款、拒付等人工处理场景中记录返现调减和无法自动扣回的额度。

个性化页必须同时展示：

- 全局默认值。
- 当前覆盖值。
- 合并后的最终生效值。
- 最后修改人、修改时间和修改原因。

恢复“跟随全局”时只删除该字段的覆盖，不影响其他个性化字段。

## 6. 邀请归因

### 6.1 所有用户保留邀请码

- 用户注册成功后拥有唯一邀请码。
- 管理员可禁用某个用户的返现资格，但不删除其邀请码和历史关系。
- 邀请返现关闭时，邀请链接仍可用于注册归因，但不新产生奖励，除非指定用户的个性化开关明确启用。

### 6.2 本地归因有效期

邀请码在浏览器中仅保留 7 天：

```json
{
  "code": "ABCD1234",
  "captured_at": 1785427200,
  "expires_at": 1786032000
}
```

产品规则：

- 用户访问带 `?aff=` 的链接时写入归因记录。
- 再次访问新的有效邀请链接时，重置为新邀请码和新的 7 天有效期，即“最后一次有效点击”归因。
- 手动填写的邀请码优先于本地保存值。
- 超过 7 天后自动删除，不参与注册。
- 注册成功后立即删除本地记录。
- 服务端在注册事务内再次校验邀请码，不信任浏览器传入的规则、金额或邀请者 ID。

## 7. 奖励规则

### 7.1 邀请者奖励和受邀者奖励

将原“额度设置”中的两个字段移入“邀请返现”：

- `邀请者奖励`：固定用户额度，0 表示不奖励。
- `受邀者奖励`：固定用户额度，0 表示不奖励。

管理员通过选项按钮统一设置邀请者奖励和受邀者奖励的发放时点：

- `注册成功后发放`：邀请关系绑定成功后立即创建两项奖励。
- `首次达标充值后发放`：受邀者的累计成功充值金额首次达到门槛时创建两项奖励。

该设置支持全局默认和指定用户覆盖。每个邀请关系的邀请者奖励和受邀者奖励分别只发放一次，通过“邀请关系 ID + 奖励类型”组成的唯一幂等键防止重复发放。规则版本只用于审计，不参与该幂等键，避免修改规则后重复发放注册奖励。

发放口径：

- 受邀者奖励直接增加受邀者 `User.Quota`。
- 邀请者奖励进入邀请者的冻结返现额度账户，与充值返现使用同一个管理员配置的冻结天数。
- 冻结天数为 `0` 时，邀请者奖励创建后立即进入可用返现。
- 修改发放时点不会重复发放已经发放过的奖励。

### 7.2 充值返现方式

管理员通过分段控件选择一种方式：

#### 按比例返现

- 输入框右侧固定显示 `%`。
- 输入范围为 `0%` 至 `100%`，步长 `0.01%`。
- 服务端以基点保存，`1% = 100 bps`，避免浮点误差。
- 计算公式：

```text
返现额度 = 实际支付 CNY 金额对应的用户额度 × 返现比例
```

实际支付金额转换为用户额度时，使用奖励生成时的钱包额度换算参数，并将参数写入本笔奖励快照。返现生成后只保留确定的 quota 数值，后续转入不再二次换算。

#### 固定额度返现

- 受邀者充值符合当前次数规则后，发放一笔管理员配置的固定用户额度。
- 固定额度必须大于或等于 0，0 表示不产生充值返现。

按比例返现和固定额度返现在同一时刻互斥，不叠加发放。

### 7.3 充值返现次数

管理员通过选项按钮选择一种次数规则：

- `仅首次达标`：受邀者的钱包在线充值累计金额首次达到门槛时结算一次，后续充值不再产生充值返现。
- `每笔充值`：受邀者的钱包在线充值累计金额首次达到门槛时结算第一笔返现；激活后，每一笔新的钱包在线充值都结算一次返现。

补充规则：

- 两种次数规则都支持按比例返现或固定额度返现。
- 达标门槛只用于首次激活邀请关系，不是每笔充值的最低金额限制。
- 首次达标时，按比例模式以“从邀请关系绑定到达标时的累计钱包在线充值金额”计算首笔返现；固定额度模式发放一次固定额度。
- 选择“每笔充值”后，激活后的下一笔充值无论金额大小都会触发返现。例如门槛为 `¥20`，达标后充值 `¥1` 也会产生本次返现。
- 激活后的按比例返现只以本笔实际支付金额作为计算基数；固定额度返现则每次发放配置的固定额度。
- 同一钱包在线充值订单只能产生一笔充值返现，通过唯一幂等键防止支付回调重复结算。

### 7.4 有效充值范围

只有用户在钱包页面发起、并由在线支付渠道成功回调确认的余额充值才计入累计金额和充值次数。

计入范围：

- 易支付、Stripe、Creem、Waffo、Waffo Pancake 等钱包在线充值订单。
- 订单状态必须由对应在线支付渠道回调变为成功。
- 实际支付金额必须大于 `0`，币种固定为 CNY。

不计入范围：

- 管理员手动完成订单或人工增加用户额度。
- 兑换码、签到、新用户赠送、邀请奖励等免费额度。
- 订阅购买和使用账户余额购买订阅。
- 邀请返现转入账户余额。
- 退款、失败、取消或金额为 `0` 的充值订单。

### 7.5 单个邀请最高返现

该字段控制一个邀请关系在全部有效充值上的累计返现额度上限，按比例和固定额度两种方式都生效：

- 使用独立开关 `不限额`，不使用 `0` 代表不限额。
- 关闭“不限额”后，必须输入大于 0 的最高返现额度。
- 开启“不限额”后，金额输入框禁用，服务端使用显式布尔字段判断，不对金额做封顶。
- 有限额时，每次返现额度不得超过“上限减去该关系累计已产生返现额度”的剩余额度；剩余额度为 `0` 时不再生成返现。
- 用户端文案分别显示 `最高 ¥25.00/人` 或 `不限额`。

邀请者奖励不占用充值返现上限。退款后的人工调减不自动恢复上限，避免通过退款和重复充值反复获取奖励。

### 7.6 冻结时长

- 管理员可自定义冻结时长。
- 第一版以整数天为配置单位，`0` 表示返现立即可用。
- 不提供小时级输入；服务端可换算为秒保存。
- 邀请者奖励和充值返现生成时，都按当时有效的冻结天数固化本笔记录的 `available_at`。
- 后续修改冻结天数不改变已生成返现的解冻时间。

## 8. 规则快照

### 8.1 为什么要保存快照

管理员修改全局规则或指定用户的个性化规则后，新规则需要影响该邀请者的全部邀请关系，而不只是修改后新绑定的关系。为了同时满足“全部关系生效”和财务可追溯，系统采用“当前有效规则版本 + 每笔结算快照”：

- 邀请关系只固化邀请码、邀请时间和双方身份等归因信息。
- 每笔奖励结算时，按邀请者当时的最终生效配置生成或复用对应的规则版本。
- 每次注册奖励或充值返现触发时，读取邀请者当时的最终生效规则，并把完整财务规则复制到本笔奖励记录。
- 新规则对全部已有和未来邀请关系的后续奖励事件生效。
- 已经生成的奖励额度、状态和解冻时间不追溯重算。
- 普通设置保存不会重新处理已经发生的注册或充值事件，也不会自动批量补发奖励。

### 8.2 快照字段

每条邀请关系保存归因快照：

- 邀请码快照。
- 邀请者和受邀者 ID。
- 邀请关系绑定时间。

每笔奖励或返现记录保存财务规则快照：

- 规则版本号。
- 邀请者奖励。
- 受邀者奖励。
- 注册奖励发放时点。
- 返现方式：按比例或固定额度。
- 充值返现次数：仅首次达标或每笔充值。
- 返现比例基点或固定返现 quota。
- 是否不限额以及有限时的返现额度上限。
- 达标充值金额，固定为 CNY。
- 冻结时长。
- 实际奖励 quota。
- 奖励生成时的 `QuotaPerUnit` 和钱包 CNY 展示汇率快照。
- 规则来源：全局默认或指定用户覆盖。

“是否可查看充值记录”不是财务规则，不写入关系快照，每次打开页面时动态读取当前全局值和用户覆盖值。这样管理员可以立即关闭某个用户的明细查看权限。

### 8.3 时间线示例

```text
8 月 1 日：全局返现 10%，用户 A 无个性化配置
8 月 2 日：用户 B 使用 A 的邀请码注册
             -> 保存 B 的邀请码和绑定时间等归因快照
8 月 5 日：管理员将 A 的个性化返现改为 20%
             -> 新规则对 A 的全部已有和未来邀请关系生效
8 月 6 日：用户 C 使用 A 的邀请码注册
8 月 10 日：B 累计在线充值达到条件，按当前生效的 20% 计算首次返现
8 月 10 日：C 累计在线充值达到条件，按 20% 计算首次返现
8 月 12 日：管理员将 A 的返现改为 15%
             -> 8 月 10 日已生成的两笔返现仍保留 20% 快照
             -> 若设置为每笔充值，B、C 后续在线充值按 15% 计算
```

当管理员修改规则时，全部邀请关系从规则生效时间起使用新规则处理后续事件。已经发生的注册和充值事件不重新执行；如果运营确实需要补发，必须通过独立的人工调账或批量补发功能执行，不作为保存设置的自动副作用。已发放的注册奖励永不重复发放。

当前功能尚未上线，因此第一版无需迁移历史现金返现或银行卡提现数据。上线后的已生成奖励额度和解冻时间永不因配置变更而自动重算；如需调整，由管理员通过人工调账产生一笔可审计的差额记录。

## 9. 用户端信息架构

### 9.1 邀请返现卡片

卡片保留在钱包页，展示：

- 邀请码和邀请链接。
- 已邀请人数。
- 冻结返现。
- 可用返现。
- 已转入余额。
- 当前返现规则，例如 `每笔充值返现 20%` 或 `首次达标固定返现额度 ¥5.00`。

冻结金额展示规则：

```text
已冻结 ¥18.50
最早解冻：2026-08-07 14:30
```

当存在多笔冻结返现时，卡片只显示最早一笔未解冻记录的时间。用户可在“被邀请者充值记录”中查看每笔解冻时间。没有冻结金额时不显示解冻时间。

### 9.2 邀请返现管理

原“管理”对话框改为两个标签：

1. `转入账户余额`。
2. `被邀请者充值记录`。

最终产品不提供银行卡提现和对账单入口，仅提供额度转入与被邀请者充值记录。

## 10. 转入账户余额

### 10.1 交互

用户将可用返现额度转入账户余额：

- 展示可转入金额。
- 输入本次转入金额，支持“全部转入”。
- 展示转入后增加的账户余额可消费价值。
- 用户确认后立即到账，无管理员审核步骤。
- 不收集提现方式、银行卡号、收款账号或打款凭证。

### 10.2 账务口径

- 仅可转入“可用返现”，冻结返现不可转入。
- 转入操作必须在一个数据库事务内同时减少可用返现、增加主账户余额并记录双方账本。
- 重复提交同一请求时只能成功一次。
- 返现账户与主账户都使用 quota，转入时按 quota 1:1 扣减和增加，不再进行金额或汇率换算。
- 每笔转入记录保存转入 quota、转入前后余额、请求幂等键和转入时间。
- 邀请返现总开关只控制新奖励生成；关闭后，已冻结额度继续按期解冻，已有可用额度仍可转入账户余额。

## 11. 被邀请者充值记录

### 11.1 开关和个性化权限

新增“允许邀请者查看被邀请者充值记录”开关：

- 全局开关是默认值。
- 指定用户可设置为“跟随全局”、“允许”或“禁止”。
- 开关只控制明细的查看权限，不影响邀请关系、返现计算或汇总金额。
- 关闭时，用户端不显示“被邀请者充值记录”标签，API 同时拒绝访问，不能只做前端隐藏。

### 11.2 列表字段

| 字段 | 用户端展示 | 说明 |
| --- | --- | --- |
| 受邀者邮箱 | 脱敏邮箱 | 例如 `a***z@example.com`；不返回完整邮箱 |
| 邀请时间 | 年-月-日 时:分:秒 | 邀请关系成功绑定时间 |
| 邀请码 | 完整邀请码 | 使用关系快照，不受后续换码影响 |
| 充值时间 | 年-月-日 时:分:秒 | 充值成功时间 |
| 充值金额 | 实际成功支付的 CNY 金额 | 向邀请者展示实际金额，用于核对按比例或固定额度返现 |
| 返现规则 | `20%` 或 `固定额度 ¥5.00` | 展示本笔实际使用的规则快照 |
| 返现额度 | quota 的 CNY 展示值 | 本笔实际产生的用户额度；未达标或未触发时显示 `¥0.00` |
| 解冻时间 | 时间或“立即可用” | 对应返现记录的 `available_at` |
| 状态 | 未达标/已冻结/可转入/已转入/已调整 | 便于区分门槛和额度状态 |

排序和筛选：

- 默认按充值时间倒序。
- 支持按受邀者脱敏邮箱、邀请码、返现状态和时间范围筛选。
- 展示邀请关系绑定后的全部钱包在线充值成功记录，包括累计门槛前返现为 `¥0.00` 的记录。
- 管理员补单和其他非在线钱包充值来源不进入该页面。
- 采用服务端分页，不一次返回所有充值记录。

### 11.3 邮箱隐私

邮箱脱敏在服务端完成：

- 本地部分长度为 1 时显示 `*`。
- 长度为 2 时显示首字符加 `*`。
- 长度大于 2 时保留首尾字符，中间统一显示 `***`。
- 保留域名，以便邀请者区分同一企业或邮箱服务商。
- 不在响应中附带完整邮箱、可逆推的用户资料或支付渠道账号。

## 12. 退款和人工调账

根据当前产品决定，钱包在线充值退款不自动冲正邀请返现额度。管理员逐笔人工处理：

1. 管理员在充值记录中定位原返现。
2. 选择“调减返现”并填写调整额度和原因。
3. 若返现仍冻结，从冻结金额扣减。
4. 若返现已解冻但未转入，从可用返现扣减。
5. 若返现已转入账户余额，第一版不自动扣减用户主余额；记录为“待人工处理”，由管理员确认后执行调账。
6. 每次调整必须生成独立账本记录和管理员审计日志，不直接覆盖原返现额度。

邀请者在充值记录中可看到“已调整”状态和调整后金额，但不展示内部退款审核备注。

## 13. 核心流程

### 13.1 邀请注册

```text
访问邀请链接
  -> 本地保存邀请码和 7 天到期时间
  -> 用户注册
  -> 服务端校验邀请码
  -> 合并全局规则和邀请者个性化规则
  -> 创建邀请关系和归因快照
  -> 读取注册奖励发放时点
  -> 若设置为注册成功后发放，保存财务规则快照并幂等发放邀请者/受邀者奖励
  -> 邀请者奖励按冻结天数进入冻结或可用返现
  -> 清除本地邀请码
```

### 13.2 充值返现

```text
受邀者的钱包在线充值由支付渠道回调确认成功
  -> 查找邀请关系
  -> 读取邀请者当前有效的全局与个性化规则版本
  -> 未激活时累计在线充值金额并检查首次达标门槛
  -> 若本次首次达标，幂等发放设置为“首次达标充值后”的邀请者/受邀者奖励
  -> 首次达标按累计金额或固定额度生成首笔返现
  -> 已激活且设置为“每笔充值”时，本次充值不再检查单笔最低金额
  -> 按本笔比例或固定额度计算后续返现
  -> 应用该关系累计返现额度的“有限额/不限额”规则
  -> 将计算结果转换并固化为用户 quota
  -> 保存本笔财务规则快照
  -> 创建冻结或立即可用的返现记录
  -> 在被邀请者充值记录中可查
```

### 13.3 解冻和转入

```text
返现到达 available_at
  -> 系统定时任务将其从冻结转为可用
  -> 用户申请转入余额
  -> 事务内按 quota 1:1 扣减可用返现并增加 User.Quota
  -> 写入返现账本和账户余额日志
```

## 14. 数据设计建议

### 14.1 用户个性化配置

新增用户级覆盖记录，以 `user_id` 唯一。字段使用可空值表示“跟随全局”，不使用特殊数字兼任状态。

| 字段 | 说明 |
| --- | --- |
| `user_id` | 被个性化配置的邀请者 |
| `enabled` | 可空布尔，空表示跟随全局 |
| `inviter_reward_quota` | 可空，邀请者固定奖励额度 |
| `invitee_reward_quota` | 可空，受邀者固定奖励额度 |
| `registration_reward_trigger` | 可空，`registration_success` 或 `first_qualified_topup` |
| `reward_mode` | 可空，`percentage` 或 `fixed` |
| `cashback_frequency` | 可空，`first_qualified` 或 `every_topup` |
| `reward_rate_bps` | 可空，比例基点 |
| `fixed_reward_quota` | 可空，固定返现额度 |
| `unlimited_reward` | 可空布尔 |
| `maximum_reward_quota` | 可空，有限额时的累计返现额度上限 |
| `minimum_topup_cents` | 可空，首次达标累计充值门槛，单位为 CNY 分 |
| `hold_seconds` | 可空，冻结时长 |
| `show_invitee_topups` | 可空布尔，明细查看权限 |
| `updated_by` | 最后修改管理员 |
| `updated_at` | 最后修改时间 |
| `change_reason` | 修改原因 |

### 14.2 邀请关系与规则版本

邀请关系保存第 8.2 节的归因快照。全局或个性化设置保存后立即成为当前有效规则；每笔奖励结算时，系统按邀请者当时的最终配置生成或复用不可变规则版本。全部邀请关系的后续奖励事件读取当时有效规则，不需要逐条覆盖历史关系数据。

### 14.3 奖励与返现记录

邀请者奖励、受邀者奖励和充值返现使用统一的可审计奖励记录，每笔记录保存：

- 邀请关系 ID。
- 奖励类型：邀请者奖励、受邀者奖励或充值返现。
- 奖励接收用户 ID。
- 来源事件类型和来源事件 ID；注册奖励关联注册/关系事件，充值返现关联充值记录。
- 受邀者充值记录 ID，可空，仅充值返现必填。
- 生效规则版本 ID。
- 充值来源，可空，仅充值返现填写且必须为 `online_wallet`。
- 本笔实际支付 CNY 分快照，可空，仅充值返现填写。
- 首次达标时的累计在线充值 CNY 分快照，可空，仅首笔返现填写。
- 充值返现次数规则快照，可空，仅充值返现填写。
- 返现方式、比例或固定额度快照。
- 实际奖励 quota。
- 奖励生成时的 `QuotaPerUnit` 和钱包 CNY 展示汇率快照。
- 产生时间和解冻时间。
- 冻结、可用、已转入、已入账、已调整等状态；受邀者奖励直接增加 `User.Quota` 后记为已入账。
- 幂等键：注册奖励按“邀请关系 ID + 奖励类型”唯一，充值返现按“邀请关系 ID + 充值记录 ID”唯一。

### 14.4 返现额度账户

邀请者返现账户与主账户统一使用 quota，至少保存：

- `pending_quota`：已生成但尚未解冻的额度。
- `available_quota`：已解冻、可转入主账户的额度。
- `transferred_quota`：累计已转入主账户的额度。
- `lifetime_earned_quota`：累计获得的邀请奖励和充值返现额度。

产品文案中的“冻结返现”对应 `pending_quota`。不再为银行卡提现保留新的冻结占用余额。

### 14.5 余额转入记录

新建额度转入记录：

- 转入 quota。
- 转入前后的返现可用 quota。
- 转入前后的 `User.Quota`。
- 请求幂等键。
- 转入时间。

### 14.6 上线与旧邀请额度

- 当前新版邀请返现尚未上线，不迁移现金返现、银行卡提现或对账单数据。
- 保留所有用户现有邀请码和邀请关系。
- 旧 `User.AffQuota` 与新返现账户使用相同 quota 单位，上线迁移时按 1:1 写入 `available_quota`，不得进行币种或汇率换算。
- 旧 `AffHistoryQuota` 保留为累计获得额度；`AffHistoryQuota - AffQuota` 作为历史已转入额度，不重复加入可用余额。
- 旧 `QuotaForInviter` 和 `QuotaForInvitee` 按 quota 原值迁入新的邀请者奖励和受邀者奖励配置。
- 迁移必须有幂等标记，重复执行不得重复增加可用额度。

## 16. 管理后台字段布局

### 16.1 全局设置

1. 启用邀请返现。
2. 邀请者奖励。
3. 受邀者奖励。
4. 注册奖励发放时点：注册成功后 / 首次达标充值后。
5. 充值返现次数：仅首次达标 / 每笔充值。
6. 充值返现方式：按比例 / 固定额度。
7. 返现比例 `%` 或固定返现额度。
8. 首次达标累计充值金额，固定使用 CNY。
9. 单个邀请累计最高返现 + 不限额开关。
10. 冻结天数。
11. 最低转入余额金额。
12. 允许查看被邀请者充值记录。

发放时点、返现次数和返现方式均使用互斥的选项按钮或分段控件，不使用自由文本或隐含数值表示状态。固定奖励、固定返现、返现上限和最低转入额度均以账户余额的 CNY 展示方式输入，服务端保存为 quota。

### 16.2 用户个性化设置

页面顶部是用户搜索框，选中用户后显示与全局设置同构的表单。每个字段旁提供“跟随全局”开关，下方以辅助文字显示最终生效值。

保存前确认对话框必须说明：

- 本次修改的字段。
- 修改后的最终生效值。
- 新规则会影响该邀请者全部已有和未来邀请关系的后续奖励事件。
- 保存设置不会重新处理已经发生的注册或充值事件，也不会自动批量补发。
- 已生成奖励额度和已固化的解冻时间不会重算。

### 16.3 人工调账

页面支持按邀请者、受邀者、邮箱、邀请码或充值订单号搜索充值返现记录，并按冻结、可转入、已转入、已调整状态筛选。记录展示邀请者、脱敏受邀者邮箱、订单号、充值时间、实际支付 CNY 金额、原返现 quota、已转入 quota 和当前状态。

管理员输入调减金额和必填原因后，系统优先扣减尚未转入的冻结或可用返现并写入返现账本。已转入账户余额的部分不自动扣减，接口返回待人工处理额度并在页面明确提示，避免退款操作隐式扣减用户主账户余额。

## 17. 状态与异常处理

- 无效邀请码：手动输入时明确提示无效，不得显示“已使用邀请码”的误导信息。
- 邀请者被禁用：不创建新奖励，已有返现和历史记录保留。
- 受邀者无邮箱：记录页显示稳定的脱敏标识，例如 `用户 ****1234`，不暴露完整用户 ID。
- 多笔冻结：汇总处显示最早一笔待解冻时间，明细中逐笔显示。
- 转入并发：对返现账户加行锁，余额不得变为负数。
- 返现计算溢出：CNY 金额使用分、奖励使用 quota，计算过程使用定点整数或 decimal，不使用无边界浮点转整数。
- 币种：第一版固定为 CNY，不提供修改入口。
- 无效充值来源：非在线钱包支付回调产生的额度变化不得进入累计充值或返现结算。
- 功能关闭：只停止新奖励生成，不停止已有额度解冻、查询和转入。
- 规则保存失败：全局字段必须在一个事务中整体回滚，不得出现部分字段生效；奖励事件重试不得重复发放。

## 18. 验收标准

### 18.1 设置

- 邀请者奖励和受邀者奖励只在“邀请返现”中维护，原入口不再出现可编辑控件。
- 比例输入和所有用户端比例文案均显示 `%`。
- “不限额”是独立开关，开启后不会被 `0` 金额误解为无返现。
- 管理员可通过选项按钮设置注册奖励发放时点和充值返现次数。
- 管理员能搜索指定用户，只覆盖选中的字段，其余字段继续跟随全局。
- 个性化规则不需要创建代理等级或套餐。

### 18.2 返现和冻结

- 按比例和固定额度两种模式均能得到可预期的精确额度。
- 按比例和固定额度互斥，不会叠加发放。
- “仅首次达标”和“每笔充值”按管理员设置生效，支付回调重试不会造成重复返现。
- 首次返现按累计在线充值金额计算；激活后每笔在线充值不再受单笔最低金额限制。
- 管理员补单、兑换码、订阅购买和返现转入余额不会触发返现。
- 有限额时不超过单个邀请上限，不限额时不做封顶。
- 邀请者奖励和充值返现均按整数天冻结；冻结时长使用有效规则快照，修改配置不改变已生成记录的解冻时间。
- 规则变更影响全部已有和未来邀请关系的后续奖励事件，但不重算已生成奖励。
- 冻结汇总旁显示最早的未解冻时间，充值记录显示每笔解冻时间。

### 18.3 余额转入

- 用户不再填写银行卡或收款账户。
- 可用返现 quota 可 1:1 即时转入主账户 `User.Quota`，冻结返现不可转入。
- 重复提交、并发提交和中途失败不会导致重复到账或余额丢失。
- 转入过程不进行币种或汇率换算，不受模型计费汇率影响。

### 18.4 充值记录和隐私

- 对账单入口被“被邀请者充值记录”替换。
- 明细包含受邀者脱敏邮箱、邀请时间、邀请码、充值时间、实际 CNY 充值金额、返现规则、返现额度和解冻时间。
- 明细开关关闭时，前端无入口，后端 API 也无权返回数据。
- 指定用户可单独允许或禁止查看明细。
- 普通邀请者无法通过响应内容获得完整邮箱。

## 19. 已确认产品决策

1. 邀请者奖励、受邀者奖励、冻结返现、可用返现和余额转入统一使用用户 quota 记账；不使用独立现金余额。
2. 邀请者奖励和受邀者奖励的发放时点由管理员设置，支持“注册成功后”和“首次达标充值后”。
3. 邀请者奖励进入冻结返现账户，与充值返现使用相同的管理员自定义冻结天数。
4. 充值返现次数由管理员设置，支持“仅首次达标”和“每笔充值”。
5. 首次达标按累计钱包在线充值金额计算首笔返现；激活后每笔在线充值均按次数触发，不设置单笔最低充值金额。
6. 只有钱包在线支付渠道回调确认成功的充值才计入累计金额和充值次数，管理员补单及其他额度来源均不计入。
7. 全局或指定用户规则修改影响全部邀请关系生效后的后续事件；保存设置不自动重放旧事件或批量补发。
8. “被邀请者充值记录”展示受邀者实际支付的 CNY 充值金额，邮箱仍在服务端脱敏。
9. 固定额度返现与按比例返现二选一，不叠加。
10. 币种固定为 CNY，不提供币种修改入口。
11. 冻结时长使用整数天精度，不提供小时级配置。
12. 最终产品不提供银行卡提现；可用返现 quota 只能 1:1 转入主账户 `User.Quota`。
13. 当前功能尚未上线，不设计现金返现或银行卡提现历史数据兼容；旧 `AffQuota` 仅按 quota 1:1 迁移。
