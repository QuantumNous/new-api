1. 目标与范围

Browser QA 的目标是在 staging 环境中自动复现新用户 onboarding 主路径，并在主路径成功后执行有边界的 UI / console / network 探索。它不改变生产发布链路，不访问 production Flatkey origin，不做付费、订阅、邀请、真实模型调用或管理员操作。

范围内范围外
staging website、staging console、只读 docs 入口、邮箱验证码、API Key 页面、报告和 cleanup。 生产站点、生产发布 gate、数据库级 hard purge、真实付费或会产生不可逆费用的行为。
GitHub Actions 构建固定 QA 镜像，更新 QA broker/main/cleanup Cloud Run 资源并等待执行完成。 把个人 OAuth 文件、OpenAI API key、refresh token、验证码或完整 Flatkey API key 写入仓库、日志、Terraform state 或报告。

主要落点：.github/workflows/gcp-browser-qa.yml、.github/workflows/gcp-deploy-staging.yml、scripts/browser_qa/、deploy/gcp/envs/browser-qa-staging/、deploy/gcp/docs/OPERATIONS.md。

2.1 Browser QA UI / Network Assertion DSL：staging 受控候选已验证

最新口径：以下能力已经在本地代码、contract tests 和真实 Cloud Run candidate runtime 中验证。受控 staging coverage candidate FQA-062169633278 使用 UI 断言加网络否定断言，三次 attempt 全部 passed，正式聚合为 ready_for_review。但自动 run 的 root candidates 为 0，所以 candidate-pr/Draft PR 的真实创建仍未触发。
新增能力语义边界
begin_network_capture步骤能力，必须是空对象；同一 proposed_case 中网络断言要求恰好一次 capture，且只观察 capture 之后的请求。
element_visibleUI 断言，只保留语义 locator。
element_hiddenUI 断言，只保留语义 locator。
element_enabledUI 断言，只保留语义 locator。
element_disabledUI 断言，只保留语义 locator；适合验证空名称、未同意条款等场景下提交按钮不可用。
element_value_equalsUI 断言，保留 locator 和期望 value。
element_count_equalsUI 断言，保留 locator 和 0..1000 的 count。
network_request_sent网络断言，只匹配同源请求的 method、origin 和 pathname，以及 0..5000ms timeout。
network_request_not_sent网络断言，只匹配同源请求的 method、origin 和 pathname，以及 0..5000ms timeout。

显式网络监听边界：网络断言只表达 GET、POST、PUT、PATCH、DELETE 的 same-origin request 是否在 capture 后出现；fingerprint 和 candidate bundle 只保留 method / origin / pathname / timeout。query、fragment、header、body、cookie、Authorization、auth credential 和任意 payload 都不保留，也不能为了满足网络断言去制造服务端写入。

steps:

assertions:

      locator: {by: test_id, test_id: submit}

  - click:

      path: /api/keys

Candidate 三次验证、sanitized artifact、candidate-pr Draft PR 和人工 review / merge 流程不变：候选仍必须通过 3/3 独立 attempt，PR 仍只走 Draft，不自动 approve、不自动 merge；本段新增的 UI/network DSL 只是让可固化 case 的断言表达更精确。

4. Record/Replay Skill 与 AI 发散边界

当前实现加载固定 Skill：.agents/skills/flatkey-new-user-onboarding。录制不是坐标脚本，而是稳定主路径：注册、邮箱验证、onboarding、初始额度、API Key、docs 入口和 cleanup-ready checkpoint。运行时 prompt 要求先执行严格 replay，只有 replay 到达 checkpoint 后才允许调用 qa_replay_checkpoint。core 模式在 checkpoint 后必须停止，不能调用 qa_start_exploration；normal 模式才允许进入探索。

Core mode: after the replay checkpoint, stop.
Final result: "exploration": {"status": "not_started", "actions_used": 0}

Normal mode:
1. replay onboarding
2. call qa_replay_checkpoint
3. call qa_start_exploration
4. explore up to 300 seconds or 30 browser actions
阶段边界实现位置
Replay语义回放 onboarding，允许小幅定位恢复；不创建第二个账号，不绕过 CAPTCHA。scripts/browser_qa/config/qa-prompt.md、supervisor.py
Fixed casesqa_replay_checkpoint 同步触发已启用结构化 fixed cases；它们属于 core_body，所以 normal 也必须执行。browser_evidence_helper.cjs、fixed_cases.py
Core到 checkpoint 和 fixed cases 后停止；禁止后续探索 action。control_mcp.py、mcp_budget_wrapper.py
Normal exploration最多 5 分钟或 30 个 browser tool action；只读观察 UI、console、network、恢复路径问题。budget.py、mcp_budget_wrapper.py
Candidate proposal每个 finding / coverage candidate 的 proposed_case 只能是 nullable closed object：不可输出 JS、shell、CSS/XPath selector、任意 URL、凭据或 cleanup-requiring proposal。result.schema.json、report.py、promotion.py

结果必须符合 scripts/browser_qa/config/result.schema.json：包含 replay、exploration、budgets、findings 和 coverage_candidates。模型只负责给出候选叙述和受限 proposed_case；Python schema、redactor、fingerprint、origin allowlist、candidate orchestrator 和 fixed-case runner 才是权威校验。非 info finding 会让产品 manifest 进入 findings_detected，但候选验证状态会单独汇总，不能被产品 passed 覆盖。

5. Finding / Coverage 候选固化与 3/3 状态机

findings[] 和 coverage_candidates[] 不是一类东西。Finding 表示 AI 观察到“可能坏了”的行为；Coverage Candidate 表示 AI 观察到“现在是好的，值得长期保护”的行为。二者都必须有证据和 high confidence，且能转成 closed fixed-case DSL，才进入候选固化。

类型进入条件3/3 语义最终状态
Finding 非 info、证据充分、同一 staging 行为可由 DSL 重放。 三次一致失败表示稳定复现 bug，进入 awaiting_product_fix；产品修复后再三次 pass，才进入 ready_for_review。 先等待产品修复，再待人审合并。
Coverage Candidate 当前表现正确、用户可见或发布关键、只读或 cleanup: not_required、能稳定断言。 三次 pass 直接表示回归候选稳定，进入 ready_for_review。 待人审合并。
三次必须独立：3/3 必须来自不同 Cloud Run execution、不同 attempt id、不同 evidence 目录。基础设施失败不计入业务成功或失败；cleanup failed 立即让候选 blocked 并停止后续 attempt。 
finding:
  candidate_draft
  -> awaiting_product_fix      # same failure signature, 3/3 failed
  -> ready_for_review          # after product fix, 3/3 passed

coverage:
  candidate_draft
  -> ready_for_review          # 3/3 passed

candidate execution status:
  skipped | passed | cleanup_failed | infrastructure_failed | promotion_failed | unknown

发散通过的 case 如何固化

候选通过资格检查后，系统按 fingerprint 去重：已存在 enabled fixed case 不建 PR；已有 open Draft PR 就更新；closed 未合并的重复 PR 不自动复活；merged PR 只记录“已合并”。系统永不调用 GitHub merge endpoint，也不自动 approve。

6. Staging Push 触发链

.github/workflows/gcp-deploy-staging.yml 在 staging 分支 push 后构建并部署 newapi-staging。deploy job 完成 Cloud Run 更新并通过 /api/status 健康检查后，workflow 内的 browser-qa-normal job 调用同仓 reusable workflow .github/workflows/gcp-browser-qa.yml，传入 mode: normal 和 fail_on_findings: false。这条自动链路是 alert-only：QA 失败会让 Actions run 变红用于排查，但不会自动 rollback staging。

QA 失败会让 Actions run 变红用于告警和排查，但 workflow 没有回滚已经完成的 staging 部署，也不触发 production 或 main 发布路径。

7. GitHub Actions / Workload Identity Federation

gcp-browser-qa.yml 支持 workflow_dispatch 与 workflow_call，输入模式为 normal、core、cleanup-only、promotion-only。主 browser-qa job 权限最小化为 contents: read 和 id-token: write，通过 QA 专用 WIF provider 和 deployer service account 访问 GCP。

permissions:
  contents: read
  id-token: write

env:
  QA_AR_REPO_URL: ${{ vars.GCP_BROWSER_QA_AR_REPO_URL }}
  QA_WIF_PROVIDER: ${{ vars.GCP_BROWSER_QA_WIF_PROVIDER }}
  QA_DEPLOYER_SA: ${{ vars.GCP_BROWSER_QA_DEPLOYER_SA }}
  QA_GCS_BUCKET: ${{ vars.GCP_BROWSER_QA_GCS_BUCKET }}

workflow 会先校验输入：cleanup-only 和 promotion-only 必须提供纯数字 original_run_id；normal/core 必须存在安全的 GCP_BROWSER_QA_GMAIL_BASE，且不能含 plus tag、逗号、CR 或 LF。

Job权限能做什么不能做什么
browser-qa contents: read + id-token: write 构建镜像、更新/执行 QA Cloud Run、读取私有 GCS manifest、上传 sanitized candidate artifact。 不能写仓库，不能创建 PR，不能 merge。
candidate-pr contents: write + pull-requests: write 只消费 browser-qa-candidate-pr-bundles 这个 sanitized artifact，按 fingerprint upsert Draft PR。 没有 GCP/WIF 凭证，不读取 Secret Manager，不下载私有 GCS evidence，不调用 merge endpoint。

8. Cloud Run Broker / Main / Cleanup / Candidate

同一个容器镜像由 scripts/browser_qa/entrypoint.sh 根据参数分派为四种模式：

main    -> python3 -m scripts.browser_qa.flatkey_browser_qa.supervisor
cleanup -> python3 -m scripts.browser_qa.flatkey_browser_qa.cleanup_job
broker  -> python3 -m scripts.browser_qa.flatkey_browser_qa.broker
candidate -> python3 -m scripts.browser_qa.flatkey_browser_qa.candidate_job
运行面职责Secret / IAM 边界
Broker service 读取 Gmail readonly OAuth，按当前 run id、email tag、时间窗查询验证码，只返回匹配的六位验证码或 pending。 只有 broker SA 读 Gmail OAuth secret；只有 QA runtime SA invoke broker。
Main job 生成一次性身份，启动受控 Chromium、egress proxy、Codex exec、MCP server，写 main manifest 与证据。 runtime SA 读 Codex API key 和 identity seed；写 GCS object；不读 Gmail OAuth。
Cleanup job 用同一 run id 重新派生身份，分页删除 API Key，删除账号，验证账号不能再登录，合并 root manifest。 cleanup SA 读 identity seed；对专用 QA bucket 有 object admin；不读 Codex API key 或 Gmail OAuth。
Candidate execution 每个候选独立运行 fixed-case DSL attempt，写 attempt manifest 和证据目录，供 promotion 聚合 3/3。 复用 runtime 边界；候选 payload 由 workflow 传入，schema/origin/DSL 校验失败即基础设施失败；真实 secret 不进 candidate payload。

容器镜像固定 Node/Codex/Playwright/Chromium 版本，以非 root 用户运行。workflow 在 push 镜像前执行容器 smoke test，包括非 root 检查、codex --version、playwright-mcp --version、Python unittest 和 CDP attach smoke。

9. Terraform 独立 State 与 Phase A + Phase B 合约

Browser QA 的 Terraform root 是 deploy/gcp/envs/browser-qa-staging/，GCS backend prefix 是 envs/browser-qa-staging。它与 production root 共享 state bucket 但不共享 state prefix；它只声明 Browser QA 专属资源和 browser_qa_* outputs。

阶段资源OutputsGuard phase
Phase A 26 个非 workload 基础资源：Artifact Registry、4 个 SA、logging IAM、3 个 Secret container、Secret accessor IAM、SA user/WIF IAM、report bucket 与 bucket IAM、WIF pool/provider。 4 个基础 outputs：AR repo URL、WIF provider、deployer SA、report bucket。 --phase infra

variables.tf 中 create_workloads 默认 true，terraform.tfvars 也保存 steady state 的 true。Phase A 只通过命令行临时覆盖 -var='create_workloads=false'，防止首次创建时 Cloud Run 引用尚未写入 version 的 latest Secret。

10. Secret Manager / Gmail OAuth / API Key / Identity Seed

Terraform 只创建 Secret Manager 容器和 IAM，不创建 google_secret_manager_secret_version，也不接收 Secret payload 作为变量。三个 Secret version 由人工 operator 在 Phase A 后写入：

  • flatkey-browser-qa-codex-api-key：只注入 main job 的 CODEX_API_KEY。
  • flatkey-browser-qa-identity-seed：main 和 cleanup 用来通过 HMAC 派生 run-scoped username、email tag、password、API key name。
  • flatkey-browser-qa-gmail-oauth：只注入 broker service 的 GMAIL_OAUTH_JSON，scope 必须是 Gmail readonly。

派生出的 Gmail plus tag 固定为 qa-<run-id>-<8-char-HMAC-suffix>。这个长度是注册链路的一部分：后端当前对完整邮箱执行 50 字符上限校验，所以 QA 身份不能恢复为更长的 flatkey-qa-... 前缀，也不能随意加长随机后缀。

{
  "refresh_token": "<operator-owned-oauth-refresh-token>",
  "token_uri": "https://oauth2.googleapis.com/token",
  "client_id": "<oauth-client-id>",
  "client_secret": "<oauth-client-secret>",
  "scopes": ["https://www.googleapis.com/auth/gmail.readonly"]
}

上面的 JSON 是形状示例，不是可用凭据。实际值不得进入仓库、聊天、GitHub logs、Terraform state、镜像层或报告。

12. 安全边界与 Egress

浏览器与 MCP

Chromium 由 supervisor 启动，CDP endpoint 只在 loopback。Playwright MCP 只能 attach 到该 endpoint，不负责 launch 浏览器。

Codex 沙箱

codex exec 使用 ephemeral、strict config、output schema、workspace-write，全局 approval_policy = "never"，配置中 network_access = false。

Egress allowlist

可写浏览仅允许 staging-website.flatkey.ai 和 staging-console.flatkey.ai；docs 通过 cookie-free docs-only context 只读访问 docs.flatkey.ai。

拒绝目标

生产 Flatkey origin、localhost、GCP metadata、link-local、RFC1918、literal IP、非 HTTP(S)、不可信 redirect、绕过 proxy 的路径均拒绝。

非交互运行时没有人工审批弹窗；因此全局审批策略保持 never，只对四个专用 MCP server 写入 default_tools_approval_mode = "approve"，并且每个 server 都必须有精确 enabled_tools。禁止 wildcard、yolo、danger-full-access 或任何会让模型获得任意工具/任意文件/任意网络访问的配置。

MCP server唯一允许的工具边界
playwrightbrowser_navigate、browser_navigate_back、browser_tabs、browser_click、browser_type、browser_fill_form、browser_select_option、browser_snapshot、browser_find、browser_wait_for、browser_console_messages、browser_network_requests、browser_network_request、qa_read_docs只能 attach 到 supervisor-owned Chromium，并受预算和 egress allowlist 控制。
evidenceqa_capture_screenshot截图工具不接受路径、selector 或关闭遮罩参数。
brokerget_current_verification_code只查询当前 run id、email tag 和 start time 对应的验证码状态。
controlqa_replay_checkpoint、qa_start_explorationcore 模式只允许到 checkpoint 后停止；不会进入发散探索。

页面内容被视为不可信输入，不能覆盖 QA policy、origin 限制、预算、清理和上传规则。broker MCP client 固定 run id、email tag、start time 和 broker URL；模型不能查询任意邮箱或传入任意 alias。

数据边界也分两层：私有 GCS 保存完整脱敏 evidence 和 root manifest，只有 QA 相关 service account / operator 能读取；传给 candidate-pr job 的 GitHub artifact 只包含 sanitized candidate bundle。模型 API token、Gmail OAuth、DingTalk webhook、验证码、cookie、Authorization header、完整 API key、完整邮箱地址和 secret value 都不得进入 artifact、PR、summary、截图或日志。

13. Plan Guard / Hash / INVALID 恢复

scripts/browser_qa/terraform_plan_guard.py 对 Terraform plan JSON 做精确白名单校验。它按完整 resource address 匹配，不使用子串判断；所有 meaningful change 必须是 create；未知 resource/output 即使是 no-op 也会失败；update、delete、replace、deposed object、重复 JSON key 和空 plan 都会失败。

python3 scripts/browser_qa/terraform_plan_guard.py --phase infra <plan.json>
python3 scripts/browser_qa/terraform_plan_guard.py --phase infra-recovery <plan.json>
python3 scripts/browser_qa/terraform_plan_guard.py --phase workloads <plan.json>

Hash 边界来自 runtime provenance：main manifest 中记录 skill_content_sha256、Codex 版本、model config、Playwright MCP 版本、Playwright package 版本和 Chromium 版本，用来证明本次 replay 使用的是固定 Skill 内容和固定运行工具链。

INVALID 恢复规则：任何 Phase A 或 Phase B saved-plan apply 非零退出后，原 saved plan 立即作废；不能重放旧 plan，不能切到 -target，不能手工删除或猜测 import。已实现的 incident recovery 是 infra-recovery：只接受 3 个 report bucket IAM member create，恢复后 state 应精确等于 26 个 Phase A 地址。Phase B 失败不回滚 Phase A，也不影响已有 staging 应用服务。

14. 可观测性、中文钉钉与仅告警策略

最终状态优先级由代码定义：cleanup_failed > infrastructure_failed > replay_failed > findings_detected > passed。GitHub Summary 展示状态、replay/exploration 摘要、finding 数量、cleanup 状态和私有 GCS URI。

当前每次 Browser QA 都会在终态向钉钉发送一份脱敏中文报告；通过、回放失败、发现问题、清理失败、基础设施失败和候选固化异常都会通知。GitHub Actions 只在通知步骤临时注入 webhook 与机器人加签密钥，并按钉钉要求为每次请求生成毫秒时间戳和 HMAC-SHA256 签名；这些密钥、签名、测试邮箱、验证码和 API Key 都不会进入报告或日志。通知仍然只是告警，不会自动 rollback staging，也不会改动 main/production。本轮 run 31475296929 的通知步骤日志包含 DINGTALK_NOTIFICATION_SENT，消息为中文模板，并直接链接到该 GitHub Actions run。

双层摘要：钉钉同时展示产品状态和候选状态。产品 passed 只表示 replay/fixed cases/cleanup/report 主状态通过；如果候选状态是 cleanup_failed、infrastructure_failed、promotion_failed 或 unknown，消息标题和 final gate 仍按候选异常处理，不能被产品通过掩盖。每个 workflow 终态只发一条钉钉消息，不为三次 attempt 分别刷屏。
Candidate status中文含义处理
skipped本次没有可验证候选，或不是 normal/promotion-only 候选路径。只看产品主状态。
passed候选验证完成；有候选达到待人工审核或 Draft PR 条件。人工 review Draft PR，不自动 merge。
cleanup_failed候选 attempt 无法证明资源已清理。最高优先级处理残留，停止后续 attempt。
infrastructure_failed候选执行、GCS 拉取、schema、Cloud Run 或 GitHub artifact 失败。先修基础设施；该 attempt 不计入 3/3。
promotion_failed候选业务结果不满足 3/3 或聚合规则。保留 evidence，按 flaky/blocked 排查。
unknown候选步骤失败但没有可信输出。fail closed，按异常处理。

本地只读/单元验证

本地适合运行单元测试、contract tests、HTML 文档验证、敏感模式扫描。本文未运行 Terraform 或 GCP 命令。

Staging runbook 摘要

  1. Phase A：operator 在独立 root 中生成 refreshing saved plan，导出 JSON/文本，运行 --phase infra，人工确认后 apply 同一个 saved plan。
  2. 写入四个 output-backed GitHub repository variables，再安全写入 GCP_BROWSER_QA_GMAIL_BASE。
  3. 写入三个 Secret Manager version，不读取或打印 payload。
  4. Phase B：确认 26 个 Phase A address、三个 Secret latest version 均 ENABLED、workload 不存在，再运行 --phase workloads 并 apply 同一个 saved plan。
  5. 先运行 core；core 和 cleanup 成功后再运行 normal。
  6. 如 cleanup 中断或需重跑，用原始 GitHub run id 执行 cleanup-only。
  7. 如候选三次 execution 已完成但 PR artifact 或 candidate-pr job 失败，用原始 GitHub run id 执行 promotion-only 恢复，不重新跑产品 replay。

16. 从 0 部署 Runbook：小白版

这部分给第一次搭建的人使用。原则是“先建空壳，再人工写 secret version，再创建会引用 secret 的 workload”。所有命令里的值都是占位名，执行前由 operator 用本项目审批流程替换。

步骤要做什么成功标准
1. 账号和范围确认云账号、GitHub 仓库权限、staging 分支、项目 ID、region、staging website/console/docs origin。没有 production 写路径进入 allowlist。
2. API开启 Artifact Registry、Cloud Run、Secret Manager、IAM Credentials、Cloud Storage、Cloud Logging、WIF 所需 API。API enable 命令成功，未创建 workload。
3. Terraform 独立 root/state进入 deploy/gcp/envs/browser-qa-staging/，使用独立 backend prefix；不要混入主 infra root。plan 只出现 Browser QA 专属地址和 browser_qa_* outputs。
4. Phase A生成 saved plan，导出 JSON，记录 hash，运行 terraform_plan_guard.py --phase infra；人工审批后才单独 apply 同一个 saved plan。Artifact Registry、GCS bucket、Secret containers、service accounts、WIF、IAM 元数据存在。
5. 人工写三个 secret version只写 secret 名和值，不打印值：BROWSER_QA_MODEL_API_KEY_SECRET、BROWSER_QA_IDENTITY_SEED_SECRET、BROWSER_QA_OAUTH_JSON_SECRET。三个 latest version 均 enabled；secret payload 不进 Terraform state。
6. Phase B workloads生成 create_workloads=true 的 saved plan，导出 JSON，记录 hash，交给 --phase workloads 守卫；人工审批后才单独 apply 同一个 saved plan。broker service、main job、cleanup job 和必要 Run IAM 创建完成。
7. GitHub 接线写入 WIF provider、deployer service account、AR repo、GCS bucket、region、project、staging base email 等 vars；写入 DingTalk webhook/signing secret 到 GitHub Secrets。浏览器 QA workflow 只拿到必要 vars/secrets。
8. 构建镜像自动 staging 链路或手动 dispatch 都会让 workflow 执行 unit/contract tests、docker build、container smoke、MCP attach smoke、push image。镜像非 root，Codex/Playwright MCP 可启动。
9. staging workflow 接线staging deploy 成功并通过 /api/status 后调用 gcp-browser-qa.yml，当前自动输入是 mode: normal 与 fail_on_findings: false。失败只影响 QA 告警，不自动 rollback staging。
10. 首跑验收验证自动 normal 跑完完整 core_body、探索、candidate 三次 execution、sanitized artifact、candidate-pr Draft PR、钉钉摘要；需要隔离 replay 时再人工 dispatch core。真实 staging 验收完成后，才能更新文档为“已跑通”。
11. 恢复和回滚cleanup-only 用原始 run id 清理；promotion-only 用原始 run id 重建候选 PR artifact；撤销时先停触发，再按 IaC 销毁 QA 专属资源。不会用手工删除制造 drift。
12. 撤销临时权限首跑结束后移除临时 owner/editor、临时本机凭证和一次性审批权限。只保留 workflow 所需最小权限。
Terraform guard 原则：必须使用 saved plan、导出 plan JSON、记录 plan hash 并用 phase guard 校验。不要直接 apply 一个夹杂主 infra 替换、生产资源 update/delete/replace 或未知 output 的 plan；任何 apply 非零退出后，原 saved plan 立即作废，重新生成并重新校验。

18. 故障处理

现象处理
plan guard 失败停止；读取 guard 的 exact finding；不要 apply、不要 -target。
Phase A / Phase B apply 非零退出标记 saved plan invalid；按实际残留状态写恢复设计和新 guard/plan；不要重放旧 plan。
gmail_invalid_grant这是基础设施失败；发布/重新授权/旋转 Gmail OAuth 后先跑 core。
Gmail plus alias 被禁修复 staging alias policy 或停止；不要临时改变身份策略。
core 失败但 cleanup 成功读取私有报告定位 replay；不要直接跑 normal。
cleanup_failed用原始 run id 运行 cleanup-only；若重复失败，人工检查 staging 残留。
manifest 缺失且 cleanup 失败/跳过先执行 cleanup-only，再继续排查基础设施或报告上传问题。

19. 已知限制
