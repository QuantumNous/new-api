# 单主密钥账户模式

状态：L1_VALIDATED（已完成生产人工验证；跨数据库、完整自动化门禁和真实 SMTP 供应商独立验证仍为待补证据）

## 目标

降低普通用户注册、保存密码和管理多条 API Key 的成本：普通用户只有一条主 API Key，可用它调用 API 和登录后台；密码登录作为兼容与恢复方式保留。

## 目标用户与角色

- 普通用户：仅有一条主 API Key，不能创建、删除或同时持有第二条 Key，只能查看掩码、复制当前 Key或重置。
- 管理员和服务账号：不受单 Key 产品界面约束，继续使用既有多 Key 能力；其 Key 是否允许登录必须由独立策略控制，不能默认全部允许。

## L1 产品决策（推荐边界）

本方案采用“邮箱身份 + 单主 Key + 密码兼容”的双轨认证，而不是把 API Key 变成唯一的账户恢复手段：

- 普通用户以邮箱作为找回和通知地址；主 Key 同时承担 API 调用和后台登录。
- 原密码登录保留，老用户不迁移、不强制轮换；新用户可不设置密码，但登录后可补设密码。
- 管理员/服务账号继续使用多 Key，不被普通用户的单 Key 规则影响。
- 简化注册只在“邀请确认、原子建户、主 Key 轮换、会话撤销、找回限流”同时可用时开放；不能用 `APIKeyLoginEnabled` 或 `EmailDefaultTokenEnabled` 任一开关代替完整模式。
- `SinglePrimaryAPIKeyEnabled` 开启后，普通用户默认必须持有管理员签发的 `invite_token`；公开邮箱验证码注册只能作为单独的兼容迁移策略，不能与严格邀请模式共用同一产品承诺。
- 初始邮件发送一次性邀请链接；管理员同时指定用户名和角色（默认普通用户，可选管理员，权限由服务端再次校验）。默认用户确认注册后仅在 HTTPS 页面一次性展示完整 Key；本次 L1 生产部署按产品方明确要求，同时发送包含完整 API Key 的邮件。该双重交付是风险接受例外，不能作为默认安全基线。

因此，产品承诺是“少填字段、少管理 Key”，不是“取消所有账户恢复和安全校验”。

## L1 假设与验证顺序

按风险优先验证以下假设，未验证前不得把模式标为生产可用：

| 假设 | 风险 | 最小证据 |
| --- | --- | --- |
| 用户能保存一次性展示的主 Key | 高 | 受控可用性测试：复制、关闭、重新登录成功率 |
| 邮箱找回比密码重置更低成本 | 中 | 新用户完成注册到首次 API 调用的时间和失败率 |
| 双用途 Key 的泄露风险可接受 | 高 | 威胁建模、限流/审计/会话撤销演练和人工安全批准 |
| 普通用户单 Key 不影响管理员多 Key | 高 | 角色矩阵和并发回归测试 |
| 邮件供应商失败不会产生半账户 | 高 | SMTP 失败、超时、重试和事务回滚测试 |

最小实验路径：邀请链接概念测试 → 一次性 Key 展示可用性测试 → 轮换/会话撤销回归 → 邮箱找回不可枚举测试 → 小范围灰度。未完成后四项时只允许保留密码登录。

## 功能开关边界

该模式必须作为一个完整产品模式启停，不能只开启其中一部分。开启时同时约束普通用户的邀请注册、单主 Key、Key 登录、重置和邮箱找回；关闭时沿用既有注册、密码登录和多 Key 管理行为。

现有 `APIKeyLoginEnabled` 与 `EmailDefaultTokenEnabled` 只能视为过渡配置，不能单独代表本规格已经满足。

### SMTP 配置与就绪判定

- SMTP 连接参数可通过部署环境变量提供：`SMTP_SERVER`、`SMTP_PORT`、`SMTP_ACCOUNT`、`SMTP_FROM`、`SMTP_TOKEN`，并用 `SMTP_STARTTLS_ENABLE` 或 `SMTP_SSL_ENABLED` 选择传输安全方式；不要把真实凭据提交到仓库。
- Gmail 等要求应用专用密码的服务应把应用专用密码放在部署环境的密钥管理中。`SMTP_TOKEN` 不是普通邮箱登录密码，也不会由公开状态或设置接口回显。
- `SinglePrimaryAPIKeyEnabled` 是数据库/后台选项，不是环境变量。开启前必须先完成 SMTP 静态配置，并关闭 `EmailDefaultTokenEnabled`；后台状态中的 `single_primary_api_key_ready=false` 或 warning 表示该模式不可作为生产配置使用。
- 就绪字段只表示静态配置满足最低要求，不代表已经连通供应商。进入更大范围生产前仍需验证失败回滚、重试和告警；本次 L1 已完成生产人工验证，但真实 SMTP 独立证据仍未补齐。

### 生产发布与前端缓存

- 生产容器必须固定 `SESSION_SECRET`；若每次重启随机生成，会使数据库中尚未消费的邀请和找回链接全部无法校验。
- 前端构建产物由 Go 二进制嵌入。发布必须先构建前端再交叉编译 Go；根页面与 `index.html` 禁止缓存，构建版本变化时前端清理本地 UI 缓存并自动重新加载。
- 静态资源可长期缓存，但入口页面必须重新拉取带新资源哈希的 HTML，避免管理员继续使用旧邀请表单。

### 当前 Gmail 参数盘点（L1，只读）

- 应用层所需的非秘密参数已经明确：Gmail SMTP 主机 `smtp.gmail.com`、提交端口 `587`、发件账号、发件地址（可回退到发件账号）以及 STARTTLS；隐式 TLS 465 与 STARTTLS 587 二选一。
- SMTP 只需要 Gmail 应用专用密码作为 `SMTP_TOKEN`，不需要也不应保存 Gmail 网页登录密码。网页登录密码不能填入 `SMTP_TOKEN`。
- 本轮对话中出现过真实 Gmail 登录密码和应用专用密码；它们视为已暴露，不能写入仓库、文档、工单、截图或命令历史。启用任何测试前必须在 Google 账户中修改登录密码、撤销旧应用专用密码并重新生成新的应用专用密码；新值仅注入部署环境的密钥管理器。
- 进入 158 服务器部署前仍缺少部署参数：SSH 主机/端口/用户/密钥位置、项目或容器路径、环境变量注入方式、公开 HTTPS 地址、Cloudflare DNS/隧道映射、重启与回滚窗口，以及隔离环境的测试收件地址。上述参数不应包含秘密本身。
- 仍缺运行证据：隔离 Gmail 投递、SMTP 超时/失败回滚、Go 认证测试、SQLite/MySQL/PostgreSQL 并发验证、浏览器/客户端 E2E 和生产前人工安全批准。静态 `single_primary_api_key_ready` 不能替代这些证据。

## 主流程

### 邮件邀请与首次使用

1. 管理员输入客户邮箱并发送一次性邀请链接。
2. 系统不得在发送邀请时提前创建可用账户或主 Key。
3. 邀请链接默认一次性使用并在 24 小时后过期；重复使用、过期或已撤销时返回统一失败。
4. 用户打开链接并确认邮箱后，系统原子创建普通账户和唯一主 Key；注册事务不自动创建持久后台会话。
5. 页面一次性完整展示主 Key，提供复制操作和“我已保存，去登录”确认；关闭后只显示掩码。
6. 用户保存后用同一 Key 登录后台，也可立即调用 API。

### API Key 登录

1. 登录页保留“API Key 登录”和原有“密码登录”。
2. 只有普通用户当前唯一的主 Key 可以建立其后台会话。
3. Key 被撤销、已重置、过期或账号被禁用时拒绝登录。
4. API 额度耗尽不影响登录后台，以便用户查看用量或充值；登录校验与 API 调用额度校验必须分离。
5. 已启用 2FA 的账户仍需完成 2FA，不能因使用 Key 登录而绕过。

### 用户主动重置

1. 已登录用户发起重置前，必须通过当前密码、邮箱验证码、Passkey 或 2FA 中至少一种现有安全验证；仅拥有当前 Session 不足以直接重置。
2. 系统在一个数据库事务中生成新 Key并使旧 Key 失效，任何时刻不得出现两条可用主 Key。
   轮换生成的新主 Key 恢复为启用且永不过期，保留原有额度与用量；额度耗尽仍只限制 API 调用，不阻止后台登录。
3. 重置成功后撤销该用户全部旧后台会话。
4. 当前响应一次性展示新 Key；窗口提供复制和“我已保存并重新登录”，不得把完整 Key写入 URL、日志或本地持久存储。
5. 用户确认后退出到登录页；若响应中断或未保存，使用邮箱找回流程。

### 忘记 Key

1. 登录页提供“忘记 API Key”，用户输入邮箱。
2. 无论邮箱是否存在，接口返回相同状态和文案，避免账户枚举。
3. 邮件发送一次性重置链接，不直接附带新 Key，也不能因输入邮箱就立刻废止旧 Key。
4. 链接默认 10 分钟过期、只能使用一次；确认成功后才原子轮换主 Key并撤销全部旧后台会话。
5. 页面一次性展示新 Key，并向账户邮箱发送“主 Key 已重置”安全通知。

### 密码兼容

- 既有用户继续使用密码登录和密码重置。
- 新邀请用户不强制设置密码；可在登录后主动设置密码作为恢复方式。
- 密码重置撤销全部后台会话，但不自动轮换主 Key；账户失窃处置需要单独提供“撤销所有会话并轮换主 Key”的管理员动作。

## 权限与安全边界

- 主 Key 是双用途高权限凭据；泄露影响同时覆盖 API 调用和后台账户访问，产品必须明确提示。
- 普通用户的主 Key 不能删除或禁用到零条；对应操作统一表现为“重置”。
- 管理员不能查看普通用户完整主 Key，只能触发重置邀请或撤销。
- API Key 登录不得继承 API 调用专属的额度判断；IP、模型和分组限制也不能被误当成后台权限规则。
- 所有邀请、登录、重置、找回请求保留现有限流和人机验证，并增加按邮箱、账号和来源 IP 的限制。
- 邮件供应商失败不得留下半创建账户、双 Key 或已失效旧 Key但未交付新 Key的状态。
- 缓存发布或旧会话撤销在轮换提交后失败时，必须有明确的交付契约：返回一次性新 Key并带非敏感告警，或进入可重试的待交付状态；禁止只返回错误而让用户拿不到新 Key。
- 任何数据库提交后的异常都必须遵守同一交付契约；不能只捕获已知的缓存/Session 错误，而让其他后置异常造成“新 Key 已提交但响应无 Key”。

## 失败状态

- 邀请邮件失败：不创建账户和 Key，允许管理员重试。
- 首次确认失败：不创建账户和 Key。
- 主动重置失败：旧 Key和旧会话保持有效，不展示新 Key。
- 邮箱找回邮件失败：旧 Key不变，公开响应仍避免暴露账户是否存在。
- 重置已提交但新 Key展示中断：旧 Key已失效，用户必须通过邮箱找回；该事件必须有审计记录。
- SMTP 不可用：禁止管理员开启或保持该模式为可用状态，健康检查和后台设置需要给出明确告警。

## 计费影响

- 单 Key不改变用户余额、用量归属、预扣或结算语义。
- Key轮换必须保留用户级余额、订阅和历史日志；历史记录通过 token ID 或已删除/已轮换标记继续可审计。
- 额度耗尽只阻止需要额度的 API 调用，不阻止后台登录。

## 验收条件

- 普通用户在并发请求下最多只能存在一条可用主 Key。
- 管理员/服务账号既有多 Key行为不受影响。
- 邀请确认后账户和主 Key要么全部成功，要么全部不存在；后台会话在用户保存 Key 后通过正常登录建立。
- 只有主 Key可登录；其他普通 API Key、旧 Key、禁用 Key和被撤销 Key均不能登录。
- 零额度主 Key可以登录后台，但不能绕过 API 调用的额度校验。
- 主动或邮箱重置后，旧 Key不能调用 API或再次登录，所有旧后台会话不能刷新。
- 找回请求不能通过响应差异判断邮箱是否注册。
- 完整 Key只在首次创建或成功重置后的单次响应中出现，日志、URL、列表接口和管理员接口只返回掩码。
- 密码登录、密码重置、2FA和 Passkey 既有行为保持兼容。

## L1 结论

方向可行，能显著减少普通用户的注册字段、密码保存和多 Key管理成本；但双用途主 Key提高了单点泄露风险，只有把“唯一性、额度与登录解耦、原子轮换、会话撤销、邮箱确认和限流”作为不可拆分边界后才适合进入实现阶段。

当前实现已在生产完成人工验证：邀请表单支持邮箱、用户名和角色；邀请注册写入用户名/角色；普通用户单主 Key、Key 登录、轮换、邮箱找回和入口缓存更新均已部署。生产用户 `1028408511@qq.com` 已删除并保留删除前备份；开发人员 Key 已导出到仓库外的受限文件，未写入 Git。Go/Bun 自动化门禁、三数据库并发验证、真实 SMTP 供应商独立验证和浏览器自动化 E2E 仍未取得完整通过证据，这些是后续增强验收项，不应伪称为已通过。

## UNKNOWN / 待决策

- 邀请链接和找回链接的最终有效期是否允许管理员配置。
- 新邀请用户的自动用户名展示规则。
- 是否需要另设公开 OTP 迁移模式；当前 L1 实现默认不开放公开 OTP 注册。
- 轮换后置失败目前采用“返回新 Key+非敏感告警”；若未来需要后台自动恢复，可增加待交付队列，但不属于本 L1 必需项。
- 找回流程的非交付后置异常已静态统一收口为一次性 Key + 告警；在取得未知错误回归证据前，不能宣称邮箱找回闭环达到上线验收。
- 管理员/服务账号哪些 Key允许后台登录。
- 邮件供应商健康检查和告警在生产环境的具体实现。
- 管理员邀请已有后端 `POST /api/user/invite` 及管理员用户页邀请弹窗；普通用户直建仍由后端拒绝。面向客户开放前仍需完成浏览器 E2E 与实际 SMTP 投递验证。

## L1 静态复核补充（2026-08-13）

- 跨库静态审查未发现单主功能新增的数据库专属迁移；GORM 行锁、AuthFlow 唯一约束和 `OnConflict` 写法可映射 SQLite、MySQL、PostgreSQL。
- 邮箱并发锁仍有运行时前提：MySQL 依赖邮箱索引及隔离级别下的 gap/next-key lock，PostgreSQL advisory lock 存在理论 hash 碰撞（只会额外串行），SQLite 依赖单写者与 busy timeout。三库并发验证前不得标记生产可用。
- 前端 7 个语言包已覆盖受影响的认证文案；格式检查通过，但依赖缺失导致 typecheck、lint、build 尚未运行。
