# 代理积分与套餐兑换码迁移设计

## 背景

源项目 `/Users/luodashuaige/Documents/claude_code2/new-api-main` 已实现较完整的代理分销体系，覆盖代理积分、套餐兑换码采购、库存、退款、客户绑定、返佣、推广码和运营看板。目标项目 `/Users/luodashuaige/Documents/new-api` 已演进出独立的订阅体系和新的 Default 前端，不能直接复制源项目的 `Package + Offer`、旧版 `Redemption` 和 React/Semi UI 实现。

本次只迁移代理业务的核心闭环，不迁移旧数据。目标是让管理员给代理配置积分和统一套餐代理价，代理用积分批量购买套餐兑换码，最终用户兑换后获得当前项目的订阅权益，并允许符合规则的未使用兑换码退款。

## 已确认的产品决策

- 只迁移功能，从空数据开始，不导入源项目的代理、余额、流水、订单或兑换码。
- `1 积分 = 1 元`，支持精确到 `0.01` 积分。
- 复用当前 `SubscriptionPlan` 和 `UserSubscription`，不重新引入源项目的 `Package` 模型。
- 每个订阅套餐使用一个统一代理价，首版不支持代理级价格覆盖。
- 仅未兑换且未过期的套餐码可以退款，退款按购买快照计算并扣除手续费。
- 套餐码有效期独立于订阅时长，由代理套餐配置决定，默认 365 天。
- 每次最多购买 100 个套餐码；每个代理每日默认最多生成 200 个，管理员可以单独调整。
- 代理积分首版只由管理员充值或扣减，不支持代理在线购买积分。
- 只实现 `web/default`，不修改 `web/classic`。
- 技术细节由实现者根据目标项目架构自主决策。

## 目标

- 管理员可以开通、禁用代理，并维护代理的每日购买限额。
- 管理员可以安全地充值或扣减代理积分，所有变更都有不可变流水。
- 管理员可以为现有订阅套餐配置代理价、兑换码有效期和退款手续费。
- 代理可以查看余额和可采购套餐，并使用积分批量购买套餐码。
- 代理可以查询订单、库存和积分流水，并导出自己的兑换码。
- 最终用户可以通过统一兑换入口兑换套餐码并获得订阅权益。
- 未使用且未过期的套餐码可以按购买时规则退款。
- 购买、兑换、退款在并发和重复请求下不会重复扣款、重复授予权益或重复退款。
- 新增代码兼容 SQLite、MySQL >= 5.7.8 和 PostgreSQL >= 9.6。
- 现有余额额度兑换码、订阅购买和支付回调行为保持不变。

## 非目标

- 用户绑定代理和客户关系管理。
- 用户直购套餐返佣。
- 多级代理、推荐关系或上下级分成。
- 推广优惠码、代理资料和运营看板。
- 代理在线购买积分或接入支付渠道。
- 将代理身份加入用户系统角色或改变现有管理员权限模型。
- 迁移源项目的历史数据。
- 修改 `web/classic`。

## 总体架构

`SubscriptionPlan` 继续作为套餐定义的唯一来源。代理模块只管理代理身份、积分、代理商业配置、采购订单和套餐兑换码：

```text
管理员开通代理/调整积分 ──> 代理积分账户 ──> 代理采购订单 ──> 套餐兑换码
                                  │                │             │
                                  │                │             ├─ 用户兑换 ─> UserSubscription
                                  │                │             └─ 未使用退款 ─> 积分返还
                                  │                └─ 价格、有效期、手续费、权益快照
                                  └─ 不可变积分流水

SubscriptionPlan ──> AgentPlanOffer ──> 代理采购时生成快照
```

后端遵循 Router → Controller → Service → Model：

- Router：注册代理端、代理管理端和统一兑换入口。
- Controller：身份校验、参数解析和稳定的 API 响应。
- Service：购买、退款、积分调整和兑换事务，是业务规则的唯一入口。
- Model：数据结构和单一数据访问操作，不在控制器中拼接财务事务。

## 积分单位与金额规则

数据库内部使用 `int64` 保存积分最小单位：

- 数据库 `1` = `0.01` 积分 = `0.01` 元。
- 数据库 `100` = `1.00` 积分 = `1.00` 元。
- API 展示金额使用两位小数的字符串，例如 `"100.00"`，避免 JavaScript 浮点数参与账务。
- 管理员提交积分调整时也提交十进制字符串，由后端严格解析成最小单位整数。
- 代理购买只提交套餐 ID、数量和幂等键，单价与总价全部由服务器计算。
- 单价乘数量、余额加减、退款费计算均做溢出检查，拒绝无法安全表示的金额。

退款手续费使用整数基点：

- `10000` 基点 = 100%。
- `500` 基点 = 5%。
- 范围限定为 `0..10000`。
- 手续费按每个兑换码的购买单价计算，精确到最小积分单位并使用统一的四舍五入规则。
- `退款积分 = 购买单价 - 手续费`，结果不得为负数。

## 数据模型

### AgentAccount

代理账户与用户一对一：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 主键 |
| `user_id` | int | 用户 ID，唯一索引 |
| `status` | string | `active` / `disabled` |
| `balance` | int64 | 积分最小单位余额 |
| `daily_code_limit` | int | 每日生成上限，默认 200 |
| `daily_count_date` | string | 当前计数所属日期 `YYYY-MM-DD` |
| `daily_code_count` | int | 当日已生成数量 |
| `version` | int64 | 乐观并发版本 |
| `created_at` | int64 | 创建时间 |
| `updated_at` | int64 | 更新时间 |

代理身份是业务身份，不修改 `User.Role`，也不在 `User` 上增加代理布尔字段。代理接口在 `UserAuth` 后查询有效的 `AgentAccount`。

每日计数按照应用统一时区计算，由后端向前端返回下次重置时间，不能使用浏览器本地日期参与校验。日期变化后，在下一次成功购买中把计数重置为本次购买数量。

### SubscriptionEntitlementSnapshot

权益快照使用带版本号的稳定 DTO，而不是直接序列化整个 GORM 模型。首版 `version = 1`，保存创建订阅所需字段：

- 原始套餐 ID 和名称。
- `duration_unit`、`duration_value`、`custom_seconds`。
- `max_purchase_per_user`。
- `upgrade_group`、`downgrade_group`。
- `total_amount`。
- `quota_reset_period`、`quota_reset_custom_seconds`。
- `allow_wallet_overflow` 的标准化布尔值。

快照不保存零售价、支付渠道商品 ID、排序等与履约无关的字段。序列化和反序列化必须使用 `common.Marshal`、`common.Unmarshal` 等项目 JSON 包装函数。

### Redemption 扩展

在现有 `Redemption` 增加：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | int | `0` 为现有额度码，`1` 为套餐码 |
| `agent_user_id` | int | 套餐码所属代理，索引 |
| `agent_order_id` | int | 代理采购订单，索引 |
| `subscription_plan_id` | int | 原套餐 ID，索引 |

类型使用零值代表现有额度码，现有行无需回填。新增“已退款”状态，但不改变现有启用、禁用和已使用状态的数值。

套餐码复用现有 `expired_time`、`redeemed_time` 和 `used_user_id`。价格、手续费和权益从不可删除的采购订单快照读取，避免在每个兑换码上重复保存大段快照。

现有兑换码管理接口只查询和修改 `type = 0` 的额度码。套餐码只能通过代理管理接口操作；通用的删除无效兑换码功能必须排除套餐码，防止财务审计记录被软删除。

## 权限模型

### 代理端

- 使用现有 `UserAuth`。
- 每个请求额外校验当前用户存在 `status = active` 的代理账户。
- 被禁用代理不能采购、导出或主动退款，但可以查询自己的历史订单和流水。
- 代理只能读取和操作自己的订单及兑换码，所有查询都以服务端用户 ID 强制过滤。

### 管理端

- 代理、订单、兑换码和流水的只读查询使用 `AdminAuth`。
- 开通/禁用代理、调整积分、修改限额和代理套餐配置首版使用 `RootAuth`。
- 后端权限是最终边界，前端隐藏按钮不能替代权限校验。
- 管理员积分调整同时写入积分账本和现有管理审计日志。

### 最终用户兑换

- 使用现有 `UserAuth`。
- 对外统一返回通用失败信息，不暴露兑换码是否存在、已使用、已退款或已过期。
- 后端日志保留具体失败原因和请求关联信息。

## 核心事务

### 管理员积分调整

1. 校验代理、方向、金额、原因和幂等键。
2. 查询是否已有相同业务键的积分流水；存在则返回原结果。
3. 读取代理账户及 `version`。
4. 使用 `WHERE id = ? AND version = ?` 更新余额和版本；扣减时额外验证余额充足。
5. 写入包含变更前后余额的积分流水。
6. 写入管理审计日志。
7. 提交事务。

乐观版本更新兼容三种数据库，不依赖 SQLite 不支持的行级 `FOR UPDATE`。只有版本冲突时才重试整个事务，固定少量重试，不使用随机等待。

### 代理购买套餐码

1. 校验功能开关、代理状态、套餐 ID、数量 `1..100` 和幂等键。
2. 相同代理和幂等键已有订单时直接返回原订单，不再扣款。
3. 在事务中读取套餐和启用的代理套餐配置。
4. 标准化并序列化版本化权益快照。
5. 安全计算总价并校验余额。
6. 根据应用统一日期检查或重置每日计数，确认购买后不超过代理上限。
7. 以账户版本为条件同时更新余额、每日计数和版本。
8. 创建采购订单。
9. 使用现有安全随机码生成机制创建指定数量的套餐码；数据库唯一索引处理极小概率碰撞。
10. 写入一条购买积分流水。
11. 提交事务并返回订单及兑换码。

余额、每日限额、订单、兑换码和流水属于同一事务。创建任意一个兑换码失败时全部回滚。

### 套餐码兑换

1. 统一兑换服务按 `key` 查询兑换码，不向调用方暴露具体状态。
2. 校验为套餐码、未使用、未退款且未过期。
3. 使用 `WHERE id = ? AND status = enabled` 条件更新为已使用，写入兑换用户和时间。
4. 读取采购订单中的权益快照，校验快照版本和内容。
5. 调用共享订阅权益创建函数，来源记录为 `agent_redemption`。
6. 创建订阅或更新兑换码任一步失败时回滚事务。
7. 事务提交后刷新受影响的用户组缓存并记录用户日志。

现有 `CreateUserSubscriptionFromPlanTx` 的核心逻辑会重构为可接收稳定权益参数的复用函数。正常订单继续从当前套餐生成权益参数，套餐码从快照生成，避免复制订阅时长、额度重置和用户组变更逻辑。

### 套餐码退款

1. 校验幂等键和最多 100 个不重复兑换码 ID。
2. 在事务中读取全部兑换码和对应订单。
3. 校验全部兑换码属于代理、状态为未使用且尚未过期。
4. 按每个订单的单价和手续费快照计算手续费及返还积分。
5. 使用条件更新把全部兑换码从启用改为已退款；影响行数必须等于请求数量。
6. 以代理账户版本为条件增加余额。
7. 按订单更新退款数量、退款金额和订单状态。
8. 每个兑换码写入独立退款流水，业务键使用兑换码 ID，防止重复退款。
9. 提交事务。

管理员特殊退款复用同一服务，仅权限和操作人不同，不能绕过已兑换或已退款限制。被禁用代理的自主退款被拒绝，管理员仍可处理未使用且未过期的码。

## 订阅履约规则

- 套餐码等价于一次已成功支付的订阅购买，遵守当前套餐最大购买次数规则。
- 订阅起始时间是实际兑换时间，不是代理采购时间。
- 订阅结束时间根据权益快照和兑换时间计算。
- 额度重置周期从实际兑换时间开始计算。
- 用户组升级、到期降级和钱包溢出策略沿用当前订阅实现。
- 代理套餐配置被关闭、当前套餐被禁用或后来改价，不影响已经出售的码。
- 权益快照无法解析或版本未知时拒绝兑换并回滚，不能创建部分权益。

## Default 前端设计

### 代理端

新增代理工作台入口，只对有效代理显示：

- 概览：积分余额、今日已生成/上限、未使用库存、已兑换和已退款数量。
- 套餐采购：展示套餐名称、权益摘要、代理价、有效期和退款规则；输入数量后由前端展示服务器返回的预估总价，最终金额以创建订单响应为准。
- 兑换码库存：按套餐、订单、状态和时间筛选；支持复制、批量导出和批量退款。
- 采购订单：展示数量、单价、总价、退款数量和订单状态。
- 积分流水：展示充值、扣减、采购和退款，突出余额变化。

### 管理端

- 代理管理：搜索用户、开通/禁用代理、查看余额和每日限额。
- 积分调整：独立确认弹窗，显示调整前后余额并强制填写原因。
- 套餐代理配置：基于现有订阅套餐配置代理价、是否开放、有效期和手续费。
- 代理订单与兑换码：支持按代理、套餐、状态和时间查询。

### 前端工程约束

- 使用 React Query 管理服务端状态，购买和退款成功后精确失效余额、订单、库存和流水查询。
- 表单使用 TypeScript、Zod 和现有表单组件校验。
- 金额在前端保持字符串，格式化时才展示，不用浮点数反算应扣或应退金额。
- 所有用户可见文本使用 `useTranslation()`；补齐 en、zh、fr、ru、ja、vi 平铺翻译文件。
- 组件遵循 `web/default` 的 Base UI、Tailwind、TanStack Table 和现有功能目录结构。
- 不向 `web/classic` 添加入口或兼容层。

## 功能开关与上线

新增代理体系总开关，默认关闭：

- 开关关闭时，代理入口隐藏，代理端接口返回功能未开启。
- 管理端仍可开通代理、充值积分和配置套餐，为上线做准备。
- 开关开启后，仅有效代理看到代理工作台。
- 回滚时关闭总开关即可，订单、兑换码和积分流水全部保留，不删除表或字段。

推荐上线顺序：

1. 部署新增表、字段和后端代码，保持功能关闭。
2. 管理员创建代理账户并配置套餐代理价。
3. 使用测试代理完成充值、采购、兑换和退款验收。
4. 开启功能总开关。
5. 观察购买失败率、兑换失败率、退款和账本对账结果。

## 数据库迁移策略

- 新表通过 GORM `AutoMigrate` 创建，并加入当前主数据库迁移清单。
- `Redemption.type` 使用零值代表额度码，现有数据不需要批量更新。
- 新增可空关联字段，不添加会阻断现有数据的强制外键。
- 索引使用 GORM 兼容定义，不使用数据库专属部分索引或表达式索引。
- `entitlement_snapshot` 使用 `TEXT`，不使用数据库专属 JSON 类型。
- 不使用布尔业务默认标签；默认状态、限额、有效期和开关在创建/更新标准化逻辑中设置。
- SQLite 的迁移和并发行为必须单独验证；不依赖 `ALTER COLUMN` 或行级锁。

## 审计与对账

以下不变量必须始终成立：

- 代理余额不得小于零。
- 从初始余额 0 开始，某代理全部积分流水的 `delta` 之和等于当前余额。
- 每条流水的 `balance_after = balance_before + delta`。
- 一个采购订单只有一条购买扣款流水。
- 一个套餐码最多有一条退款流水。
- 订单 `total_price = unit_price × quantity`。
- 订单累计退款数量不得超过购买数量。
- 已使用和已退款状态互斥。
- 套餐码成功兑换必然对应一个 `UserSubscription`，事务失败不能留下已使用但无订阅的兑换码。

管理员详情页提供单代理对账结果。发现不一致时只报警和禁止新的财务操作，不自动改余额。后端日志记录代理 ID、订单号、兑换码 ID、幂等键和请求关联信息，但不在普通错误响应中泄露兑换码状态。

## 验收场景

以管理员给代理充值 1000 积分、套餐代理价 60 积分、退款手续费 5% 为例：

1. 代理购买 10 个兑换码，扣除 600 积分，余额变为 400。
2. 系统生成一个采购订单、十个唯一套餐码和一条 `-600.00` 的购买流水。
3. 重复提交同一幂等键，返回原订单，余额和兑换码数量不变。
4. 用户兑换一个套餐码，准确创建一个订阅；再次兑换失败且不新增订阅。
5. 管理员修改套餐时长、额度和代理价，剩余九个码仍按购买快照履约并按 60 积分计算退款。
6. 代理退回一个未使用且未过期的码，手续费 3 积分，返还 57 积分，余额变为 457。
7. 已兑换、已退款或已过期的码不能退款。
8. 代理被禁用后不能新购或自主退款，已分发给用户的码仍可兑换。
9. 当前额度兑换码继续通过原接口增加用户额度，不受套餐码迁移影响。

## 风险与控制

- **账务并发风险**：使用账户版本、条件更新、唯一业务键和单事务，避免依赖单一数据库的锁语义。
- **历史承诺变化风险**：价格、手续费、有效期和订阅权益全部在采购订单中固化。
- **现有接口兼容风险**：保留 `/api/user/topup`，新增统一兑换接口；现有额度码接口和返回结构不变。
- **误删财务记录风险**：套餐码不进入现有无效兑换码清理，代理订单、流水和套餐码禁止物理删除。
- **跨数据库风险**：使用 GORM、整数、TEXT 和乐观并发，不使用数据库专属 JSON、函数或 DDL。
- **前端重复技术栈风险**：只在 Default 前端实现，不复制旧仓 Semi UI 页面。
- **上线风险**：总开关默认关闭，先配置和验收再开放，异常时可快速关闭且不损失数据。
