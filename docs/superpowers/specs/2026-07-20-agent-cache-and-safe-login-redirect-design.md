# 代理余额缓存与安全登录重定向修复设计

## 背景

代理积分与套餐兑换码 MVP 已完成管理员充值、代理采购、用户兑换、未使用码退款和账本对账闭环。浏览器端到端验收确认后端财务状态正确，但发现两个前端一致性问题：

1. 退款成功后，退款弹窗显示服务器返回的新余额，切回代理概览时却可能暂时显示旧余额，手动刷新后才正确。
2. Root、代理和普通消费者依次退出并登录时，登录页可能继续使用上一个账号留下的 `redirect`，让新账号进入无权页面并看到 403。

本次修复只调整 Default 前端的查询缓存同步和登录后导航决策，不修改代理积分、订单、兑换码、退款、账本或订阅履约等后端财务逻辑。

## 已确认的根因

### 余额短暂回退

退款和采购成功后只按基础查询键调用 `invalidateQueries`。概览实际使用包含当前用户 ID 的查询键，并配置了 `initialData` 与 30 秒 `staleTime`。当概览 Tab 不是活动查询时，基础键失效不会保证它立刻重新请求；重新进入概览时还可能先使用代理访问查询提供的旧 `initialData`。

因此需要同步两个当前用户作用域的缓存：

- 代理概览缓存：`agent / overview / userID`。
- 代理访问缓存：`agent / access / userID`，它是路由守卫和概览初始数据的来源。

### 登录后错误跳转

登录页直接信任 `redirect` 参数。登录成功取得新用户信息后，没有验证目标是否为站内路径，也没有检查新用户的角色和代理访问能力。已登录用户再次访问登录页时，路由守卫同样直接使用该参数。

## 目标

- 采购或退款成功后，代理看到的余额立即等于服务器交易响应中的 `balance_after`。
- 后台重新获取完整概览，最终仍以后端状态为准。
- 订单、兑换码和积分流水继续按交易结果刷新。
- 新账号登录后不会进入上一个账号才有权限访问的页面。
- 合法的站内深链接继续保留。
- 外部、畸形或无权的登录重定向统一回退 `/dashboard`。
- 修复同时覆盖密码、微信、Passkey 等复用 `handleLoginSuccess` 的登录方式，以及已登录用户访问登录页的情况。

## 非目标

- 不修改后端权限中间件或 403 页面。
- 不改变代理账户状态、全局代理开关和管理员角色定义。
- 不重构全部路由守卫。
- 不新增数据库字段、接口或依赖。
- 不修改 `web/classic`。

## 方案选择

### 余额同步

选择“服务器交易结果立即写入 + 后台完整校准”：

- 只扩大 `invalidateQueries` 的范围仍会让旧余额短暂可见。
- 只写缓存虽然立即生效，但采购会同时改变每日采购数量等其他概览字段。
- 先写入服务器已经确认的余额，再后台读取完整概览，可以同时满足即时反馈和最终一致性。

### 登录重定向

选择“统一的角色与业务访问能力解析器”：

- 所有登录统一进入 `/dashboard` 虽然安全，但会破坏 `/wallet` 等合法深链接。
- 只判断用户角色不能覆盖 `/agent` 所需的全局开关和有效代理账户。
- 集中解析站内路径、角色权限和代理业务权限，可以保留合法目标并阻止跨角色 403。

## 设计一：代理交易后的查询缓存同步

### 查询键

代理访问查询键纳入代理工作台统一查询键定义，所有调用方通过同一构造函数生成带用户 ID 的完整键，避免手写键漂移。

### 即时更新

新增稳定的代理交易缓存同步逻辑。采购或退款接口成功后：

1. 从当前认证状态读取用户 ID。
2. 使用响应中的 `balance_after` 同步更新当前用户的概览缓存和代理访问缓存。
3. 只替换 `balance` 字段，保留缓存中的每日限额、当日采购数量和重置时间。
4. 缓存不存在时不创建不完整的概览对象。
5. 交易成功弹窗和成功提示不依赖后续刷新是否成功。

该更新使用服务器已提交事务返回的余额，不进行前端加减计算，也不实施需要回滚的乐观扣款。

### 后台校准

即时更新后执行后台刷新：

- 重新获取完整代理概览，并将结果写回概览缓存和代理访问缓存。
- 使订单、兑换码和积分流水查询失效并刷新当前活动查询。
- 后台概览请求失败时保留交易响应确认的新余额，不使用旧缓存覆盖，也不把已经成功的采购或退款改成失败状态。
- 下一次手动刷新、重新进入页面或查询自然过期时仍可再次向服务端校准。

采购和退款共用同一套同步逻辑，避免两条交易路径以后再次出现行为差异。

## 设计二：安全登录重定向

### 路径规范化

新增登录后目标解析模块，只接受以单个 `/` 开始的站内相对路径，并保留合法的查询参数和片段：

- 拒绝 `http://`、`https://`、协议相对 URL、反斜杠变体和无法解析的值。
- 登录、注册、OTP、403 等不适合作为登录后落点的页面回退 `/dashboard`。
- 使用路径段边界匹配，避免 `/users-example` 被误判为 `/users`。

### 访问能力分类

当前受限目标按现有路由守卫分为：

- Root 专用：`/system-settings`、`/system-info`。
- 管理员及以上：`/agent-admin`、`/channels`、`/redemption-codes`、`/users`、`/subscriptions`、`/models`。
- 有效代理专用：`/agent`。
- 普通认证页面：例如 `/dashboard`、`/wallet`、`/profile`、`/usage-logs` 和 `/playground`。

Root 同时满足管理员权限。管理员不会因为角色而自动获得代理工作台权限；进入 `/agent` 仍需要全局代理功能开启且当前用户拥有有效代理账户。

### 代理能力探测

只有规范化后的目标属于 `/agent` 时才调用现有代理访问探测：

- 探测成功并返回概览：允许进入 `/agent`。
- 明确 403、代理功能关闭、账户不存在或账户停用：回退 `/dashboard`。
- 网络或服务异常：保守回退 `/dashboard`，不把登录流程导向错误页。

其他普通或角色受限目标不额外发送代理接口请求。

### 登录流程接入

统一解析器接入两处：

1. `handleLoginSuccess` 在 `getSelf` 成功并拿到新账号用户信息后解析目标，再执行替换式导航。
2. 已登录用户访问 `/sign-in` 时，登录路由 `beforeLoad` 使用同一解析器，不再直接信任查询参数。

如果登录后无法取得可信的新用户信息，目标回退 `/dashboard`，后续由现有认证布局继续验证会话，不能使用旧账号状态判断权限。

## 错误处理

- 财务交易成功与后台页面刷新解耦。刷新失败不能撤销或掩盖服务器已经确认的成功结果。
- 重定向解析失败、代理能力探测失败或目标权限不足均回退 `/dashboard`，不暴露额外权限细节。
- 后端路由守卫继续作为最终权限边界；安全重定向只改善登录体验，不能替代服务端授权。
- 不新增用户可见文案，因此无需增加 i18n 键。

## 测试设计

### 代理缓存测试

使用真实 TanStack `QueryClient` 验证：

- 交易余额同时更新当前用户的概览缓存和代理访问缓存。
- 其他概览字段保持不变。
- 不修改其他用户的缓存。
- 后台概览成功时用完整服务器结果校准两个缓存。
- 后台概览失败时保留交易响应确认的余额。
- 订单、兑换码和账本查询仍被刷新。

### 登录重定向矩阵

使用确定性的表格测试验证：

| 用户 | 原目标 | 期望 |
| --- | --- | --- |
| Root | `/agent-admin` | 保留 |
| 管理员 | `/agent-admin` | 保留 |
| 普通代理且访问有效 | `/agent` | 保留 |
| 普通代理 | `/agent-admin` | `/dashboard` |
| 普通消费者 | `/wallet?tab=topup` | 保留 |
| 普通消费者 | `/agent` | `/dashboard` |
| 普通消费者 | `/system-settings/site` | `/dashboard` |
| 管理员 | `/system-settings/site` | `/dashboard` |
| 任意用户 | 外部或协议相对 URL | `/dashboard` |
| 任意用户 | `/403` 或认证页面 | `/dashboard` |

额外验证代理访问探测只在 `/agent` 目标上调用，并且探测异常安全回退。

### 构建与端到端验收

- 运行新增测试及现有代理工作台测试。
- 对修改文件运行 lint、格式检查和 TypeScript 类型检查。
- 运行 Default 前端生产构建。
- 使用最新 `custom` 代码重建 Docker 容器。
- 浏览器复验采购和退款后无需手动刷新即可看到正确余额。
- 依次使用 Root、代理、普通消费者账号复验跨角色登录，确认不会再因旧 redirect 进入 403。
- 检查浏览器控制台和后端日志没有新增错误。

## 完成标准

- 两个问题均有先失败后通过的自动化回归测试。
- 采购和退款后概览即时余额与服务器响应一致，后台校准成功或失败都不会显示旧余额覆盖新余额。
- 所有登录方式和已登录登录页守卫共用同一安全目标解析逻辑。
- 权限矩阵和站内 URL 校验通过。
- Default 前端测试、类型检查、变更文件 lint、格式检查和生产构建通过。
- Docker 浏览器端到端验收通过。
- 用户原有未跟踪 CSV 文件保持不变。
