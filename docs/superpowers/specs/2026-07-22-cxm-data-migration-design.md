# cxm 代理及客户数据迁移设计

> 日期：2026-07-22
> 分支：`custom`
> 状态：待评审
> 源服务器：`154.17.4.137`（只读）
> 目标环境：本地 Docker PostgreSQL（可回滚）

## 1. 背景与目标

源服务器运行的是旧代理数据模型，代理用户 `cxm`（源用户 ID `315`）已经拥有真实客户、积分流水、套餐兑换码和大量调用日志。目标项目已经迁移了代理采购与兑换的 MVP，但数据模型已演进为新的代理账户、订阅套餐、订单和兑换码模型，不能直接复制旧表。

本次先在本地 Docker 环境做一次高保真迁移实验，验证以下完整闭环：

1. `cxm` 及其客户关系、账户余额、积分流水和认证信息可正确迁移；
2. `cxm` 可以看到所属客户及其调用日志；
3. `cxm` 可以购买并分发新的套餐兑换码；
4. 客户兑换 `cxm` 分发的兑换码后获得订阅权益，并自动绑定到 `cxm`；
5. 余额、账本、订单、兑换码、订阅和客户日志在重启后仍保持一致；
6. 迁移过程可审计、可重复检查、可回滚，不修改源服务器。

本阶段不向生产服务器写入任何数据。

## 3. 方案选择

### 3.1 候选方案

**方案 A：在线直转。** 直接从源库查询并写入本地。实现简单，但无法形成一致快照，也不利于重试和审计。

**方案 B：源库整库复制后转换。** 数据保真度高，但会携带无关用户、系统配置和基础设施状态，并可能污染已有本地实验数据。

**方案 C：选定数据闭包的一致性导出包，再事务导入本地（采用）。** 在源 PostgreSQL 的只读、可重复读事务中导出 `cxm` 所需的数据闭包，落成本地权限为 `0600` 的迁移包；本地先备份，再在单个事务内执行转换和导入。该方案兼顾一致性、最小权限、可审计性和回滚能力。

### 3.2 选用理由

- 源服务器只执行 `SELECT`，不执行更新、删除、迁移或重启；
- 导出包可计算 SHA-256 并保存清单，便于逐表核对；
- 目标本地数据库已有其他实验数据，不需要被整库覆盖；
- 导入失败时回滚本地事务，导入前备份可用于整库恢复；
- 迁移脚本可以按业务键幂等检查，避免重复创建订单和兑换码。

## 4. 数据映射

### 4.1 用户与客户归属

复制 `cxm` 和 13 个客户的用户字段：用户 ID、用户名、显示名、状态、角色、分组、额度、已用额度、请求次数、创建时间、最后登录时间、邀请关系、绑定代理字段、邮箱及现有认证字段。源用户的密码、Access Token、OAuth 标识和用户级配置属于本次“最大限度模拟生产”的范围，写入本地迁移包但不在日志或最终报告中打印。

目标使用 `users.bound_agent_id` / `bound_at` 作为客户归属事实来源：

- `cxm.bound_agent_id = 0` 保持不变；
- 13 个客户的 `bound_agent_id = 315` 原样迁移；
- 绑定时间优先使用源记录已有绑定时间；没有绑定时间时使用邀请/兑换发生时间；
- 后续新兑换继续使用 `TryBindUserToAgent` 的“只绑定一次”语义，已绑定客户兑换其他代理兑换码不会转移归属。

目标本地已存在少量用户和代理实验数据，导入前必须检查用户 ID、用户名、Access Token、邮箱、代理绑定字段等冲突。用户 ID 无冲突时保留源 ID；发生冲突时停止导入，不自动改写身份映射。

### 4.2 代理账户与积分账本

旧 `agent_credits` 转换为 `agent_accounts`：

- `UserId = 315`；
- 旧状态 `1` 映射为 `active`，旧状态 `2` 映射为 `disabled`；
- `Balance = 815000`；
- 每日购买上限使用目标默认值 `200`（旧值为 `0`，表示未设置上限）；
- 导入日将每日计数初始化为 `0`，避免历史日期阻塞本地验收；
- 保留创建和更新时间；版本号从 `1` 开始。

旧 `agent_credit_logs` 转换为新的 `agent_credit_logs`：

| 旧变更类型 | 新事件类型 | 说明 |
|------------|------------|------|
| `topup` | `admin_credit` | 管理员充值 |
| `deduct` | `admin_debit` | 管理员扣减 |
| `purchase` | `purchase` | 关联重建订单 |
| `refund` | `refund` | 关联重建订单和兑换码 |

每条流水保留旧的变更前余额、变更后余额、增减额、操作人、备注和发生时间。业务键使用 `legacy-cxm:<source_log_id>`，导入前按业务键做幂等检查。导入后必须满足：

```text
初始余额 + 所有流水 Delta = agent_accounts.balance
```

### 4.3 套餐与代理报价

目标使用 `subscription_plans` + `agent_plan_offers`，不引入旧 `packages` / `offers` 表。

源套餐映射：

| 源套餐 | 目标计划 | 代理价 | 退款手续费 |
|---------|----------|--------|------------|
| `8 / pro` | 保留计划 ID `8` | 7,000 | 约 714 bps |
| `9` | 保留计划 ID `9` | 300 | 约 1,667 bps |
| `10` | 保留计划 ID `10` | 23,000 | 约 435 bps |
| `11 / Ultra` | 保留计划 ID `11` | 80,000 | 250 bps |

源退款手续费是固定金额，目标模型使用百分比基点。本次按 `fixed_fee * 10000 / agent_price` 转换并四舍五入；这是结构性模型差异，迁移报告必须记录原值、换算值及误差。Ultra 的换算可以精确重现 78,000 的单码退款金额。

套餐额度按源项目的额度单位转换：`QuotaUSD * QuotaPerUnit`，并用源用户套餐的 `quota_allocated` 做抽样和汇总校验。套餐标题、时长、分组、升级/降级组、货币、零售价格和自定义说明写入目标计划快照。源 `vip` 和 `默认分组` 字符串先保留；如果本地没有同名分组配置，不能静默覆盖全局分组配置，验收时需单独确认分组行为。

代理报价的兑换码有效期使用目标默认 `365` 天；若源兑换码的创建/过期时间可以可靠推导，则优先使用源值。计划和报价 ID 只有在目标所有相关表无冲突时才保留，否则停止导入并要求人工处理。

### 4.4 历史订单与兑换码

旧模型没有订单表。本次按旧购买积分流水重建合成订单：

- 一个旧 `purchase` 流水对应一个目标 `agent_purchase_orders` 订单；
- 通过 `(package_id, created_time)` 将该批次的旧兑换码归入订单；
- `OrderNo = legacy-cxm-agent-credit-<source_log_id>`；
- `IdempotencyKey = legacy-cxm:<source_log_id>`；
- 数量为该批次兑换码数，单价为旧购买总额/数量，总价为旧扣款绝对值；
- 订单快照保存当时套餐权益、代理价、有效期和退款规则；
- 5 个已退款的 Ultra 兑换码对应订单标记为 `refunded`，退款数量和退款金额从源退款流水重建；
- 其余历史订单按兑换码使用状态标记为 `completed`。

兑换码映射：

- 旧 `type=2` 套餐码映射为目标订阅码类型；
- 保留兑换码原文、创建时间、过期时间、使用时间、使用用户、状态、套餐名称和代理用户 ID；
- 填入目标 `AgentOrderId`、`SubscriptionPlanId` 和不可变 `EntitlementSnapshot`；
- `Quota` 置为零，避免被误当作旧额度码；
- 状态按 enabled/disabled/used/refunded 一一映射；
- 迁移前检查兑换码主键、密文/明文唯一索引和订单外键冲突。

源库当前没有未使用的 `cxm` 兑换码，因此验收不会消耗历史码。验收会让 `cxm` 新购买一枚本地兑换码，再由一个新建的本地测试用户兑换。

### 4.5 用户套餐、订阅与额度

旧 `user_packages` 转换为 `user_subscriptions`，保留历史记录而不是只导入当前有效记录：

- 套餐 ID 按上表映射；
- `AmountTotal = quota_allocated`；
- `AmountUsed = AmountTotal - 对应 quota_grant 的剩余量`，结果限制为不小于零；
- 已清理、已过期或无有效结束时间的记录不得被误标为当前可用订阅；
- 当前有效套餐设置 `active`，历史结束记录设置 `expired`；
- `Source` 使用 `legacy_agent_migration`；
- 开始/结束时间、分组快照、钱包溢出策略等按源记录保存。

源数据核对显示：每个客户的 `users.quota` 等于所有活跃额度授予的剩余量，其中订阅额度约占 1,229,098,932，非订阅/钱包额度约占 8,477,178。为避免新系统重复计算，迁移规则为：

- 订阅剩余额度进入 `user_subscriptions.AmountTotal - AmountUsed`；
- 仅非订阅额度剩余量写入 `users.quota`；
- `users.used_quota` 原样保留作为历史消耗统计；
- 导入后对每个客户执行 `quota + active_subscription_remaining = source.quota` 校验。

现有客户管理 DTO 的“剩余额度”计算需要在实现阶段用真实数据验证。若它把目标 `users.quota` 再减去历史 `used_quota`，会与源系统“quota 表示当前剩余量”的语义不一致；验收若确认显示错误，应修正 DTO 的展示口径为“钱包剩余 + 订阅剩余”，不能改写账务字段。

### 4.6 调用日志和认证关联数据

迁移 13 个客户的全部 `logs`，按源日志 ID 保留主键（导入前检查冲突）；目标新增字段在源不存在时使用空值或目标默认值。日志查询必须继续按 `Log.UserId` 过滤，不能使用用户名匹配。

为最大限度模拟生产，复制这些用户在目标同构的用户级认证关联表（例如 tokens、二次认证和 Passkey 记录），但只复制 `cxm` 和 13 个客户的行；任何表结构不兼容或主键冲突都视为阻断条件，不做静默丢弃。源环境变量、Redis 数据、渠道、模型、系统选项和其他用户不在迁移范围内。

## 5. 导出与导入流程

### 5.1 源端导出

1. 通过指定 SSH 私钥连接源服务器；不使用密码登录，不执行远程写操作。
2. 在源 PostgreSQL 的 `REPEATABLE READ READ ONLY` 事务中读取选定数据闭包。
3. 导出为本地权限 `0600` 的压缩 JSONL/表数据包，并生成 manifest：表名、行数、源最大 ID、SHA-256、导出事务时间。
4. 导出完成后立即执行只读计数复核，确认包内数量与数据库快照一致。
5. 迁移包不得进入 Git，不在终端、提交记录或最终答复中打印密码、Access Token 或兑换码原文。

### 5.2 本地导入

1. 确认本地 Docker 服务健康并记录镜像、容器、Git commit 和数据库连接信息。
2. 使用 `pg_dump` 创建本地数据库完整备份，记录备份路径、大小和 SHA-256。
3. 预检查用户、套餐、计划、兑换码、日志和关联认证表的主键/唯一键冲突；出现冲突立即停止。
4. 在一个本地数据库事务中按依赖顺序导入：用户 → 代理账户 → 计划/报价 → 订单 → 兑换码 → 订阅/额度 → 账本 → 日志 → 用户级认证关联。
5. 显式维护源 ID 到目标 ID 的映射；使用源 ID 时同步修正 PostgreSQL sequence。
6. 提交后执行逐表数量核对、余额核对、外键核对、客户绑定核对和额度守恒核对。
7. 重启本地后端容器清除缓存，再重复关键查询；导入失败或核对失败时回滚事务，必要时恢复导入前备份。

## 6. 本地端到端验收

所有写操作仅发生在本地 Docker 环境。

### 6.1 认证准备

- 保存 `cxm.access_token` 原值（当前为空）；
- 写入一个随机的 32 字符本地临时 Access Token，仅供自动化验收；
- 通过 `Authorization: Bearer <token>` 和 `New-Api-User: 315` 访问代理接口；
- 验收结束后恢复原值，并检查数据库中已恢复。

### 6.2 客户与日志

- 访问代理概览、客户列表和客户日志接口；
- 断言客户数量为 13，客户绑定代理均为 `315`；
- 断言客户日志总数为 188,431（允许 API 分页，但总数必须一致）；
- 抽查客户额度、订阅名称、结束时间、状态与导入校验结果一致；
- 确认日志接口不会向代理返回密码、Access Token、IP 或管理员字段。

### 6.3 购买、分发和兑换

1. 用 `cxm` 购买源 `pro` 对应的目标套餐 1 枚兑换码。
2. 断言订单、兑换码、余额、账本和每日购买计数同时更新。
3. 创建一个本地专用测试客户，使用已知认证信息；不复用或消耗历史重要客户的兑换码。
4. 测试客户兑换新码。
5. 断言兑换码变为已使用、测试客户获得对应 `UserSubscription`、`bound_agent_id` 原子写入 `315`。
6. 重新访问 `cxm` 客户列表和日志，断言客户数增加 1，测试客户调用日志可按代理范围查询。
7. 用历史已退款 Ultra 兑换码验证其状态和历史订单仍为退款态，不允许再次兑换。

### 6.4 重启与财务对账

- 重启本地后端和前端容器；
- 重启后重复概览、客户、日志、订单、库存和积分流水查询；
- 校验代理余额等于账本余额；
- 校验每个客户的 `wallet_remaining + active_subscription_remaining` 等于源 `users.quota`；
- 校验所有兑换码订单外键、订阅外键和日志用户 ID 均存在；
- 验收通过后恢复临时 Token，并再次确认 `cxm` 原始 Access Token 为 `NULL`。

## 7. 回滚与停止条件

以下任一情况发生时停止导入或回滚，不尝试“尽量导入”：

- 源导出期间检测到写事务或快照计数不一致；
- 用户名、用户 ID、Access Token、兑换码、计划或日志主键冲突；
- 源套餐无法映射为目标订阅且会改变可用权益；
- 账本余额、额度守恒或订单/兑换码数量不一致；
- 认证关联表结构不兼容；
- 本地导入事务、sequence 修正或服务重启后查询失败。

回滚优先级：未提交事务直接回滚；已提交但验收失败时停止本地服务并恢复导入前 PostgreSQL 备份。源服务器不执行回滚，因为本方案不修改源数据。

## 8. 迁移产物与审计记录

本地保留以下不含明文凭据的审计材料：

- 导出 manifest 和 SHA-256；
- 本地数据库导入前备份及 SHA-256；
- 源/目标逐表计数和额度对账报告；
- ID 映射和合成订单映射（不包含 Access Token、密码或兑换码原文）；
- 端到端验收结果、容器重启记录和回滚点。

迁移包、临时 Token 和数据库备份存放在受限目录，不提交 Git，不推送 GitHub，不上传生产服务器。
