# cxm 回滚兼容投影设计

> 日期：2026-07-23
> 分支：`custom`
> 状态：已批准，进入实现与隔离演练

## 1. 目标

在新版数据库已经接收写入后，生成一份旧版可读取的兼容投影，使旧版能够继续读取代理客户、调用日志、套餐权益、兑换码库存、代理余额和购买流水。投影必须保留新版订单与订阅原始记录；切回新版时恢复新版表结构，不删除新版数据。

本次只验证生产切换所需的“新版写入 → 旧版接管 → 新版恢复”路径。旧版接管期间如果发生写入，恢复命令必须检测到并拒绝静默覆盖，要求先执行单独的旧版增量回灌。

## 2. 方案

### 2.1 兼容投影

新增一次性 CLI 子命令 `rollback-project`，目标仅支持 PostgreSQL。命令在单个事务中：

1. 创建受控的 `agent_rollback_runs`、`agent_rollback_projections` 和 `agent_rollback_user_snapshots` 元数据表；
2. 将切换时间之后的新版 `agent_credit_logs` 投影到保留的旧表 `agent_credit_logs_legacy`，字段映射为旧版 `user_id/before/after/change_type/...`；
3. 将切换时间之后的新版订阅投影为旧版 `user_packages` 与 `quota_grants`，并把订阅剩余额度加入 `users.quota`；
4. 将新版代理订单对应的订阅兑换码映射为旧版兑换码类型和字段；
5. 保存每一条投影的新版主键、旧版主键和运行标识，避免重复投影；
6. 将旧账本表和时间字段转换为旧版运行时所需的表结构，然后交换 `agent_credit_logs` 与 `agent_credit_logs_legacy` 的表名和 sequence。

新版 `agent_purchase_orders` 没有旧版等价表，因此旧版通过投影后的购买流水和兑换码库存看到订单；新版订单原表始终保留，旧版 UI 无法展示新版订单的完整快照属于已知兼容边界。

### 2.2 恢复新版

新增 `restore-current` 子命令：

1. 在事务中检查旧版接管期间的写入指纹：用户额度/登录字段、兑换码状态、旧套餐与额度授予、旧代理余额和旧账本行数/最大 ID；
2. 只允许发现与投影本身相符的变化；若检测到旧版业务写入，返回明确错误，不删除或覆盖数据；
3. 将 `agent_credit_logs` 表名交换回新版表，恢复新版用户时间字段；
4. 删除本次投影创建的旧版订阅/额度授予和新增旧账本行，并从 `users.quota` 中扣除未消耗的投影订阅剩余额度；
5. 保留元数据表和新版原始订单、订阅、账本、兑换码，重新运行新版迁移并校验序列。

严格模式拒绝旧版接管期间的真实业务写入，防止把未知旧版语义当作新版账务处理。旧版写入的增量回灌作为后续独立工作，不在本次静默处理。

## 3. 数据映射与不变量

- `agent_credit_logs.event_type`：`purchase`/`refund` 保持；`admin_credit` → `topup`；`admin_debit` → `deduct`。
- 购买流水备注使用旧版格式 `购买兑换码: <plan_title> x<quantity>`；金额、前后余额和代理用户 ID 来自新版不可变账本。
- 每个新版订阅生成一个旧 `user_packages` 和一个 `quota_grants(source_type='user_package')`；`remaining = amount_total - amount_used`，不得为负。
- 每个用户投影后满足：`users.quota = 投影前钱包额度 + 所有活动旧额度授予剩余量`。
- 兑换码保留新版原始行和 ID，只调整旧版接管所需的类型/关联字段；恢复新版时不得删除兑换码。
- 旧账本 sequence、用户时间字段和目标表存在性必须在命令开始时检查，缺失或类型不匹配直接阻断。
- 所有步骤在同一事务内完成；任意错误回滚。

## 4. 测试与演练

新增纯函数测试覆盖事件映射、订单备注、订阅剩余额度、投影去重和旧写入指纹。隔离 PostgreSQL 演练：

1. 从切换前 staging 备份创建目标副本；
2. 模拟新版购买、兑换、客户绑定、代理调账和调用日志写入；
3. 运行 `rollback-project`，启动旧版镜像，核对客户、日志、套餐、余额、兑换码和购买流水；
4. 在没有旧版业务写入的情况下运行 `restore-current`，启动新版镜像并核对原始订单、订阅、账本、兑换码和客户关系；
5. 额外向旧版副本写入一条受控数据，验证 `restore-current` 严格模式拒绝恢复并保留数据。

生产切换前必须通过以上全部检查；本设计不修改 Caddy、生产端口或生产数据库。
