## 1. 背景与目标

Flatkey 当前的订阅邀请模式把双方权益分成两种形态：被邀请人首次购买套餐时获得固定金额减免，邀请人在好友首笔套餐付款成功并经过观察期后获得可用于 API 消费的通用余额。

本次调整把邀请双方的权益统一为“套餐专用抵扣额度”：

1. 被邀请人通过邀请链接注册后获得配置金额的套餐抵扣。
2. 被邀请人完成首笔付费套餐后，邀请人立即获得配置金额的套餐抵扣。
3. 抵扣额度只能用于套餐购买和续费，不能用于 API 消费、提现或转入通用余额。
4. 抵扣额度可累计、可部分使用、永久有效，并适用于所有已支持的套餐支付方式。
5. 结账和续费必须真实减少应付金额，而不是先按原价收费后再赠送余额。

本设计只改变订阅邀请模式。旧的首次充值邀请模式继续保留原有行为。

## 2. 已确认的产品规则

| 事项 | 决策 |
| --- | --- |
| 权益形态 | 邀请双方都获得套餐专用抵扣额度，不进入通用余额 |
| 被邀请人发放时点 | 通过邀请关系注册成功时发放 |
| 邀请人发放时点 | 被邀请人完成首笔付费套餐后立即发放 |
| 观察期 | 不保留；首笔付费套餐成功即到账 |
| 有效期 | 永久有效 |
| 金额 | 读取发放时的管理员配置并保存快照 |
| 邀请次数上限 | 读取 `QuotaForInviterMaxCount`；`0` 表示不限 |
| 累计与部分使用 | 多笔额度累计；结账自动尽可能抵扣，未用完部分继续保留 |
| 使用范围 | 首次购买、后续手动购买和自动续费 |
| 支付方式 | Stripe/银行卡、支付宝、Pix、UPI 和余额支付 |
| 其他优惠 | 不叠加；按订单币种比较实际减免金额，自动采用更高的一项；金额相同则保留邀请额度 |
| 零元订单 | 允许抵到应付金额为零；仍必须走安全的套餐开通或续费状态机 |
| 退款 | 首版不处理退款回收或额度恢复 |
| 历史数据 | 未转入通用余额的邀请奖励迁移为套餐抵扣；已转入余额的不追溯拆回 |

## 3. 方案比较

### 3.1 套餐抵扣账户加不可变流水——采用

为每个用户维护套餐抵扣账户，并用不可变流水记录发放、预占、核销、释放和迁移。账户提供高效余额读取，流水提供审计、幂等和问题追踪。

该方案满足累计、部分使用、永久有效、多支付方式、自动续费和多节点并发要求，同时与 API 通用余额完全隔离。

### 3.2 复用通用余额——拒绝

复用 `users.quota` 或现有邀请可转额度的改动较小，但额度会被 API 请求消费，也仍然需要“转余额”语义，不满足“只能直接减套餐金额”的产品目标。

### 3.3 每次邀请发一张独立优惠券——拒绝

优惠券便于按邀请追踪，但多张券累计、部分使用、剩余金额保留、多币种和自动续费都会变成额外状态机。Stripe Checkout 对单个 Session 的优惠数量也有限，不能把 Stripe 优惠券作为内部权益账本。

## 4. 数据模型

### 4.1 套餐抵扣账户

新增用户级账户，建议命名为 `subscription_discount_accounts`：

| 字段 | 语义 |
| --- | --- |
| `user_id` | 用户唯一键 |
| `available_usd_minor` | 当前可用额度，单位为 USD 分 |
| `reserved_usd_minor` | 已被待支付订单或草稿发票预占的额度 |
| `created_at` / `updated_at` | 审计时间 |

账户余额必须满足：

- `available_usd_minor >= 0`
- `reserved_usd_minor >= 0`
- 只有数据库事务内的受控服务可以修改账户聚合值。
- 修改前锁定账户行；不存在时通过唯一键安全创建，再重新读取并锁定。

### 4.2 不可变流水

新增 `subscription_discount_entries`，每次状态变化插入一条记录，不更新历史流水：

| 字段 | 语义 |
| --- | --- |
| `id` | 流水主键 |
| `user_id` | 权益所属用户 |
| `entry_type` | `grant_invitee`、`grant_inviter`、`migration`、`reserve`、`commit`、`release` |
| `available_delta_usd_minor` | 对可用额度的增减 |
| `reserved_delta_usd_minor` | 对预占额度的增减 |
| `available_after_usd_minor` | 写入后的可用额度快照 |
| `reserved_after_usd_minor` | 写入后的预占额度快照 |
| `source_type` / `source_key` | 邀请关系、迁移批次、订单或 Stripe 发票来源 |
| `order_id` / `trade_no` | 套餐订单关联信息，可空 |
| `payment_currency` | 实际订单币种，可空 |
| `applied_amount_minor` | 在订单币种中实际抵扣的最小货币单位金额，可空 |
| `pricing_snapshot` | 配置值、套餐 USD 标价、本地报价与换算快照 |
| `idempotency_key` | 全局唯一业务幂等键 |
| `created_at` | 创建时间 |

推荐幂等键：

- 被邀请人发放：`invitee:{user_id}`
- 邀请人发放：`inviter:{invitee_id}:first-paid-subscription`
- 历史迁移：`migration:invite-discount-v1:{source_type}:{source_id}`
- 套餐订单预占：`subscription-order:{trade_no}:reserve`
- Stripe 续费预占：`stripe-invoice:{invoice_id}:reserve`
- 核销与释放在对应预占键后追加 `:commit` 或 `:release`

### 4.3 金额与币种

内部账户统一保存 USD 分，因为现有邀请金额配置以 USD 或可换算为 USD 的 quota 表示。实际支付币种可能为 USD、BRL、INR 或套餐配置的其他币种。

换算使用该套餐订单的权威后端报价比例：

`订单币种抵扣 = USD 抵扣额度 × 原始订单本地币种金额 / 原始订单 USD 标价`

结果按订单币种最小单位取整并封顶于原始应付金额。付费套餐的原始 USD 标价必须大于零，否则不允许使用 USD 抵扣换算。流水同时保存消耗的 USD 分、订单币种抵扣金额和报价快照，后续配置或价格变化不能改写历史订单。

## 5. 权益发放

### 5.1 被邀请人

用户通过有效邀请关系注册成功时，按当时的 `InviteFirstSubDiscountUSD` 创建一次 `grant_invitee` 流水。金额为零时不发放正向额度，但邀请关系仍正常保存。

发放与邀请关系落库处于同一可靠业务边界。若历史或异常路径存在邀请关系但缺少发放流水，套餐报价前的幂等校验可以补发，避免用户因瞬时数据库错误永久失去权益。

### 5.2 邀请人

被邀请人的首笔付费套餐订单进入成功状态时：

1. 确认用户存在有效邀请人。
2. 确认这是该被邀请人的首笔成功付费套餐。
3. 在事务内检查 `QuotaForInviterMaxCount`；`0` 表示不限次数。
4. 按当时 `QuotaForInviter / QuotaPerUnit` 的 USD 值创建 `grant_inviter` 流水。
5. 增加邀请人的可用套餐抵扣额度，并更新邀请统计。

同一个被邀请人最多触发一次邀请人奖励。支付 webhook、余额支付重试和多节点并发通过唯一幂等键收敛为一笔发放。

达到次数上限时不发放邀请人额度，但被邀请人的套餐抵扣不受影响；邀请明细记录“达到配置上限”。

### 5.3 配置快照

已发放权益不受后续配置调整影响。管理员修改金额或次数上限只影响修改后的新发放事件。

## 6. 报价、预占与核销

### 6.1 报价

所有套餐入口都由后端返回以下权威字段：

- 原始套餐金额
- 可用邀请抵扣额度
- 本次邀请抵扣金额
- 其他候选优惠及最终选中的优惠类型
- 最终应付金额
- 抵扣后的预计剩余额度
- 报价币种、报价 ID 和过期时间

报价只读取额度，不预占。用户打开多个页面或反复切换支付方式不会锁死额度。

邀请额度内部可以累计使用；邀请优惠与召回优惠、促销码等其他优惠不叠加。后端在同一订单币种中计算各候选优惠的实际减免金额，选择更高的一项。金额相同时使用非邀请优惠并保留邀请额度，确保用户未来仍可使用该永久权益。未被选中的邀请额度不消耗。

### 6.2 创建订单

用户确认购买后，在数据库事务内：

1. 重新验证套餐、支付方式、用户资格和报价有效期。
2. 锁定套餐抵扣账户。
3. 重新计算最终优惠，防止前端篡改或额度并发变化。
4. 将本次要使用的额度从 `available` 移到 `reserved`。
5. 写入 `reserve` 流水和订单价格快照。
6. 创建订单或续费意图。

签名报价必须绑定用户、套餐、月份、支付方式、原始金额、USD 抵扣、本地币种抵扣、最终应付、订单请求 ID 和过期时间。

### 6.3 核销与释放

- 余额支付：订单与余额扣款成功时立即把预占额度核销。
- Stripe/银行卡、支付宝、Pix、UPI：创建支付会话后保留预占，成功回调时核销。
- 支付失败、会话过期、订单取消或发票作废：释放预占回可用额度。
- `invoice.payment_failed` 不立即释放，因为同一张发票可能重试；只有发票终止或订单失效才释放。
- 定时任务扫描超过有效期的待支付预占并幂等释放，作为遗漏 webhook 的兜底。

抵扣覆盖整个一次性套餐订单时，系统直接完成零元订单，不调用要求正金额的支付网关。零元订单仍经过相同的订单、幂等、套餐开通和审计链路。

## 7. Stripe 订阅

### 7.1 首次订阅 Checkout

首次订阅需要在 Stripe Checkout 页面展示真实折后金额，因此使用一次性金额优惠：

1. 后端预占内部额度。
2. 按当前 Checkout 币种创建精确金额的 `duration=once` Coupon。
3. 创建 `mode=subscription` Checkout Session，并把 Coupon 作为本次唯一 discount。
4. Session、Subscription 和后续首张 Invoice metadata 写入内部订单号和预占标识。
5. 首张发票支付成功后核销；Session 过期或订单失败后释放。

当首期被抵为零时，Checkout 仍需建立真实订阅，并配置为收集后续续费所需的付款方式；不能把零元首期误处理成无需 Stripe 订阅的本地套餐开通。

Stripe Checkout Session 当前最多接受一个 discount，因此其他优惠和邀请抵扣必须在创建 Session 前由后端选出减免金额更高的一项。

### 7.2 自动续费

续费使用内部账本作为唯一权益来源，不把完整额度同步为 Stripe Customer Balance。Customer Balance 会自动用于同币种的下一张发票，无法可靠绑定特定套餐发票，容易误用于其他账单。

处理 `invoice.created` 时：

1. 用 Stripe event ID 和 invoice ID 去重。
2. 确认发票仍为 `draft`，且对应 Flatkey 套餐订阅。
3. 暂停该发票 `auto_advance`。
4. 在数据库中计算并预占可用邀请抵扣。
5. 使用 Stripe idempotency key 为该草稿发票创建精确的负数 Invoice Item。
6. 写入内部预占标识和抵扣 metadata。
7. 恢复 `auto_advance`，让 Stripe 正常定稿和收款。

`invoice.paid` 核销预占；`invoice.voided`、`invoice.marked_uncollectible` 或明确终止的订阅发票释放预占。重复和乱序事件只能得到已有结果。

若内部账本或 Stripe 调整失败，处理器返回失败并保持发票为草稿，不允许静默按原价推进。必须告警并依靠幂等重试恢复。

### 7.3 Stripe 官方依据

- Checkout Session `discounts` 当前最多一个：<https://docs.stripe.com/api/checkout/sessions/create>
- Coupon 可用于 Checkout 和订阅，支持 `once`：<https://docs.stripe.com/billing/subscriptions/coupons>
- 负数 Invoice Item 可降低 upcoming/draft invoice 金额：<https://docs.stripe.com/api/invoiceitems/create>
- 草稿发票可编辑并控制 `auto_advance`：<https://docs.stripe.com/api/invoices/update>
- `invoice.created` 失败会延迟自动定稿，事件可能重试：<https://docs.stripe.com/billing/subscriptions/webhooks>
- Stripe POST 请求应复用 idempotency key：<https://docs.stripe.com/api/idempotent_requests>

## 8. 配置与管理后台

不新增活动或活动创建入口。订阅邀请模式继续使用现有配置：

| 配置 | 新语义 |
| --- | --- |
| `InviteFirstSubDiscountUSD` | 被邀请人注册后获得的套餐抵扣 USD 金额 |
| `QuotaForInviter / QuotaPerUnit` | 邀请人每次成功邀请获得的套餐抵扣 USD 金额 |
| `QuotaForInviterMaxCount` | 邀请人最多获得奖励的成功邀请次数；`0` 不限 |
| `InviteRewardSubscriptionModeEnabled` | 启用新的订阅邀请权益模式 |

`InviteRewardUnlockDelaySeconds` 在新订阅邀请模式下不参与发放；旧模式需要时可继续保留兼容读取。

管理后台在订阅邀请模式下使用明确文案：

- 邀请人套餐抵扣
- 被邀请人套餐抵扣
- 奖励次数上限
- 付费套餐成功后立即到账
- 套餐抵扣永久有效，仅限套餐购买与续费

## 9. 用户界面

### 9.1 邀请页

邀请页不再提供“转入 API 余额”入口。订阅邀请模式展示：

- 当前可用套餐抵扣
- 累计获得套餐抵扣
- 成功邀请数
- 等待首笔套餐付款人数
- 配置的双方奖励金额与次数上限

三步说明改为：

1. 分享邀请链接。
2. 好友注册并立即获得套餐抵扣。
3. 好友首笔付费套餐成功后，你立即获得套餐抵扣。

邀请明细状态为：

- 等待首笔付费套餐
- 奖励已到账
- 达到奖励次数上限
- 奖励不可用

不再展示“锁定”“解锁日期”或“转余额”。

### 9.2 套餐与结账页

套餐卡片或购买弹窗展示可用套餐抵扣。后端报价完成后展示：

- 套餐原价
- 邀请抵扣
- 其他被选中的优惠（若金额更高）
- 最终应付
- 购买后预计剩余套餐抵扣

如果其他优惠更高，明确提示“本次使用更高优惠，邀请抵扣额度未消耗”。前端不自行计算换算、封顶或剩余额度。

### 9.3 国际化

所有新增或修改的用户可见文案通过 `t()`，真实翻译并同步到现有 8 个 locale：英语、中文、法语、俄语、日语、越南语、西班牙语和葡萄牙语。

## 10. 历史迁移

迁移遵循以下已确认口径：

1. 尚未转入通用余额的 `aff_quota` 迁移为用户套餐抵扣额度，并清零旧的可转余额，防止双花。
2. 已创建但尚未解锁的订阅邀请奖励迁移为套餐抵扣并立即可用，不再等待观察期。
3. 已转入并混入 `users.quota` 的历史奖励不追溯拆回。
4. 已使用过被邀请人首次套餐优惠的用户不再重复发放。
5. 尚未完成首笔付费套餐的历史邀请关系，在之后满足条件时按新规则给邀请人结算。
6. 历史奖励金额按原始事件实际金额迁移，不使用当前配置重算。

迁移用版本标记、唯一业务键和数据库事务实现。多个 console 实例重复执行时，每个历史来源最多生成一条迁移流水。

## 11. 一致性与错误处理

- 账户读取、价格换算或预占失败时阻止结账并提示重试，不静默按原价收费。
- 发放、预占、核销和释放全部以数据库事务、行锁和唯一约束保证多节点安全，不依赖进程内锁。
- 套餐开通与邀请人发放在同一可靠本地事务边界内完成；Stripe webhook 失败则返回非成功状态并等待重试。
- 支付 webhook 使用事件 ID 去重，但业务幂等以订单号、发票号和流水幂等键为最终边界。
- 支付成功后不能因通知、日志或前端刷新失败而重复发放或重复扣减。
- 预占清理任务使用条件更新抢占记录，多节点同时扫描不会重复释放。
- 所有价格和权益日志避免输出完整支付凭据、Stripe Secret 或用户敏感身份。

## 12. 退款边界

首版明确不实现退款、拒付或争议后的套餐抵扣回收和恢复：

- 被邀请人的订单退款后，不恢复该订单已经消耗的套餐抵扣。
- 邀请人已因该订单获得的套餐抵扣不撤销。
- 已发放或已消耗额度不因退款产生负余额。

这意味着首版存在“购买后退款仍保留邀请人奖励”的已知反作弊风险。该风险已被产品明确接受，后续退款方案必须单独设计和确认，不得在实施中擅自加入回收逻辑。

## 13. 测试策略

实现遵循测试驱动：先锁定行为，再修改生产代码。

### 13.1 账本与模型

- 被邀请人发放、邀请人发放和配置快照
- 金额为零、次数上限为零和达到上限
- 多次邀请累计、部分预占、部分核销和剩余保留
- 同一幂等键重复执行
- 多节点并发发放和并发预占
- 预占、核销、释放后的账户不变量
- SQLite、MySQL 和 PostgreSQL 兼容迁移

### 13.2 报价与支付

- USD、BRL、INR 和配置币种换算、取整与封顶
- 邀请抵扣和其他优惠选择更高者且不叠加
- 余额、支付宝、Pix、UPI 和 Stripe 首次购买
- 一个月和多月预付订单
- 抵扣部分金额和抵扣至零
- 报价篡改、过期、用户不匹配和并发额度变化
- 失败、取消、过期订单释放预占

### 13.3 Stripe 续费

- `invoice.created` 预占并写入负数 Invoice Item
- 暂停和恢复 `auto_advance`
- Stripe API 重试复用 idempotency key
- `invoice.paid` 核销
- 发票作废或终止释放
- `invoice.payment_failed` 保留预占以等待重试
- 重复、乱序 webhook 和服务重启后的恢复

### 13.4 历史迁移

- 未转邀请额度迁移且旧字段清零
- 待解锁奖励立即迁移
- 已转通用余额不修改
- 已使用被邀请人优惠不重复发放
- 多实例重复执行只产生一条迁移流水

### 13.5 前端与国际化

- 邀请页统计、步骤、明细状态和移除转余额入口
- 套餐卡片与结账价目明细
- 其他优惠更高时不消耗邀请额度
- 加载、空、错误和重试状态
- 8 个 locale 包含全部新文案且无英文占位
- 类型检查、lint 和构建通过

## 17. 完成标准

1. 邀请双方获得的权益均为套餐专用抵扣，金额和次数上限来自配置快照。
2. 被邀请人注册后可立即使用；邀请人在好友首笔付费套餐成功后立即获得。
3. 权益永久有效、可累计、可部分使用，剩余额度正确保留。
4. 所有套餐支付方式和 Stripe 后续续费都真实减少应付金额。
5. 其他优惠不与邀请抵扣叠加，系统自动采用实际减免更高的一项；金额相同保留邀请额度。
6. 专用额度不会进入或消耗 API 通用余额。
7. 重复请求、并发结账、重复或乱序 webhook 不会重复发放或双花。
8. 历史未转邀请奖励按确认口径迁移，已转通用余额保持不变。
9. 邀请页、套餐页和结账页准确展示权益和价格，8 种语言完整。
10. 目标后端测试、前端测试、类型检查、lint、国际化检查、构建、格式检查和 Git 范围检查全部通过；无法运行的验证明确记录。
