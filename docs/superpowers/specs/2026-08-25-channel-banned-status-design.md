# Channel “已封禁”状态设计

## 目标

为渠道（尤其 Flatkey 的 Codex/GPT 账号池）增加一个可人工确认的“已封禁”状态，
将已确认不可恢复的账号与现有“手动禁用”和“自动禁用”区分开，同时保持现有状态值
和历史数据兼容。

## 已确认的现状

- 渠道状态存储在 `channels.status`：`1=启用`、`2=手动禁用`、`3=自动禁用`。
- 自动恢复逻辑只恢复 `3`，Codex 凭据刷新任务只扫描 `1` 和 `3`。
- 控制台状态列目前展示并筛选“启用/禁用”，行操作可在启用与手动禁用之间切换。
- 渠道状态变更会同步更新 abilities，并刷新本地渠道缓存、向其他节点发布变更。

## 设计

### 状态语义

新增 `ChannelStatusBanned = 4`，前端对应文案为 `Banned`（中文翻译为“已封禁”）。

- `4` 表示运维已确认该账号被上游封禁或永久不可用。
- `4` 与 `2`、`3` 一样不参与路由；只有显式“解除封禁”才改回 `1`。
- 自动恢复仍只允许 `3 -> 1`；自动探测或自动禁用不得把 `4` 改写为 `3`。
- 现有 `1`、`2`、`3` 的含义和历史数据不变，不做一次性数据迁移。

### 后端

1. 在公共渠道状态常量中声明值 `4`。
2. 扩展渠道列表和搜索接口的状态解析：`banned`/`4` 精确匹配 `status=4`；
   既有 `disabled` 仍表示所有非启用状态（包含 `2`、`3`、`4`）。
3. 保护状态更新路径：自动禁用只处理非封禁账号，避免测试或后台任务把 `4` 覆盖为
   `3`；手动解除仍通过既有更新接口写回 `1`。
4. 保持既有 ability 更新、缓存刷新和跨节点发布机制，不新增进程内状态。

### 控制台前端

1. 扩展渠道状态常量、徽标配置和多语言文案，给 `4` 使用危险色徽标并显示“已封禁”。
2. 在渠道状态筛选中增加“已封禁”，请求后端使用 `status=banned`。
3. 行操作增加“标记为已封禁”和“解除封禁”；标记动作写入 `status=4`，解除动作写入
   `status=1`。已有启用/禁用切换保持原行为，不能误把 `4` 当作普通手动禁用恢复。
4. 状态原因/时间提示沿用现有 `other_info.status_reason/status_time` 展示方式。

### 数据流

```text
管理员点击“标记为已封禁”
  -> updateChannel(status=4)
  -> channels.status=4 + abilities.enabled=false
  -> 缓存刷新/跨节点通知
  -> 控制台徽标与“已封禁”筛选可见
```

“解除封禁”走同一更新接口写入 `status=1`，恢复 abilities 和正常路由；自动恢复任务
不会触碰 `4`。

## 错误处理与兼容性

- 后端仍使用现有渠道更新接口和统一错误响应，不新增数据库列或迁移。
- 未识别的状态值继续显示为 Unknown，不影响旧客户端。
- “已封禁”账号仍可被管理员查看、编辑和删除，但不会进入模型路由。
- 生产为多节点部署，正确性依赖数据库更新、缓存刷新和已有发布机制，不依赖本地
  内存锁或单节点顺序。

## 验证计划

- Go：补充状态解析/筛选和封禁状态不可被自动恢复覆盖的单元测试；运行相关
  `go test`，再运行 `go build ./...`。
- 前端：补充状态配置/筛选与行操作的测试（如已有测试框架覆盖该模块），运行
  `bun run typecheck`、`bun run lint` 和 `bun run build:check`。
- 手工 smoke：本地控制台将一个测试渠道标记为“已封禁”，确认状态徽标、筛选、
  路由不可用和解除封禁后的恢复行为。

## 非目标

- 不自动判定永久封禁；HTTP 401 或 token 失效仍由运维确认后标记。
- 不修改多密钥子状态（本次针对 Flatkey 的单账号渠道状态）。
- 不改动生产数据库中的现有账号状态，除非后续明确要求批量迁移。
