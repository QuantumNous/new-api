# 官方主线与定制能力合并设计

## 目标

以官方 `upstream/main`（`9bf328d97`，2026-09-08）作为下一阶段集成基线，同时保留当前 `custom` 分支中的 Agent、CXM 迁移与回滚、用量排行榜、`actual_base_url` 地址隔离、定制构建和相关审计能力。集成结果必须能够独立构建、完成三种数据库迁移和定制功能回归，并具备可验证的回滚路径。

本设计只规定集成方案，不执行代码合并、生产部署或数据库写入。

## 基线证据

当前分支 `HEAD=7c45cbe1`，共同基线为 `8739c05c`（2026-07-08）。共同基线之后有约 79 个当前分支提交和 244 个官方提交。当前分支相对共同基线约有 221 个文件、34,777 行新增；官方相对共同基线约有 2,657 个文件、203,216 行新增和 183,976 行删除。

直接对比当前分支和官方分支得到约 2,802 个文件差异、203,344 行新增和 218,525 行删除。三方合并模拟发现 59 个冲突：35 个内容冲突、14 个修改/删除冲突、10 个文件位置冲突。前端冲突约 40 个，非前端冲突约 19 个。

最大的结构差异是官方将默认前端从 `web/default` 迁移到 `web` 根目录，并引入顶层 `relaykit` 和 `plugins`。当前分支的 Agent/CXM 代码是官方主线没有的定制能力，不能通过覆盖官方文件处理。

## 范围

### 必须保留

1. Agent 账户、代理客户绑定、客户查询、代理积分、套餐码、代理订单、兑换和退款流程。
2. CXM 数据迁移、审计、兼容投影、可逆回滚和迁移状态保护。
3. 用量排行榜 API、模型/渠道分布、分页排序和当前定制展示语义。
4. `actual_base_url` 字段、运行时真实地址、展示地址分离、超管权限和非超管脱敏。
5. 当前自有镜像、开发配置、文档和测试边界。

### 必须吸收

1. 官方最新 Go 模块、`relaykit` 协议转换层和顶层 `plugins` 任务系统。
2. 官方认证和访问令牌审计、密码传输保护、统一会话和账户安全修复。
3. 官方计费表达式、缓存 Token、Responses、工具调用、重试换组和额度饱和保护。
4. 官方模型/厂商管理、定价同步、模型修饰符、渠道能力判断和使用日志改进。
5. 官方数据库兼容性、SQLite WAL、PostgreSQL pooler、迁移幂等、并发额度更新和上游超时修复。
6. 官方前端表格、定价、用量日志、插件市场、移动端和测试体系。

### 不在本轮范围

- 不重写 Agent/CXM 的产品语义，不引入新的代理佣金或客户转移业务。
- 不把生产数据库直接升级到集成分支，不在合并阶段修改生产配置。
- 不恢复官方已经删除的 Classic 前端作为长期维护目标；如需兼容，只保留明确的构建或迁移过渡。

## 方案选择

### 采用：官方主线骨架 + 定制能力分层回迁

从官方 `upstream/main` 创建集成分支，先完成官方目录和核心运行时迁移，再按数据模型、服务、接口、前端的依赖顺序回迁定制功能。每个阶段单独提交、测试和评审；最终通过兼容性矩阵后再进入发布流程。

该方案把官方的新架构作为唯一长期基线，避免继续在 `web/default` 和 `web` 两套前端之间维护分叉，同时将当前定制能力保留为明确的集成层。

### 不采用：直接三方合并

直接合并会把前端目录迁移、官方删除文件和定制修改同时放入一个冲突集。它适合保留历史但不适合作为本次集成的操作顺序，容易留下旧路由、旧 DTO 和新模块并存的中间状态。

### 不采用：只 cherry-pick 官方提交

官方提交之间存在目录迁移、RelayKit 抽离、插件系统切换和认证重构依赖。逐提交挑选会重复处理已解决的上下文，且难以判断某个定制补丁应落在旧路径还是新路径。

## 目标架构

```text
upstream/main
  ├── Go 核心、认证、模型、计费、RelayKit、plugins
  ├── web/（官方默认前端）
  └── 官方迁移与测试
        │
        ├── 定制数据层：Agent/CXM 字段、迁移、审计、回滚投影
        ├── 定制服务层：绑定、积分、套餐码、迁移状态、排行榜聚合
        ├── 定制接口层：Agent/CXM/排行榜/真实地址权限和脱敏
        └── 定制前端层：Agent、排行榜和渠道真实地址 UI
```

定制代码只能通过官方现有的 model/service/controller/router 和前端 feature 边界接入。不得复制官方旧文件形成第二套认证、计费、用户或渠道实现。

## 关键兼容决策

### 前端

- 以官方 `web/src` 为最终路径；将当前 `web/default/src` 的定制 feature 迁移到对应官方 feature 目录。
- `web/classic` 的排行榜和渠道地址定制只作为迁移输入；官方删除 Classic 时不把它重新作为默认构建目标。
- 所有定制文案继续使用官方 i18n 结构，并为 `en/zh/fr/ja/ru/vi` 补齐键值。
- 先迁移数据访问和类型，再迁移页面，避免页面直接依赖旧 API 响应结构。

### 后端

- 以官方 `relaykit` DTO 和转换接口为边界，不把旧 `relay` 转换实现复制回新目录。
- Agent/CXM 的数据库字段和现有三数据库约束继续使用 GORM；迁移必须覆盖 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+。
- `actual_base_url` 的真实值只在运行时和超管授权路径使用，普通管理员、错误响应、日志和渠道测试继续返回脱敏地址。
- 官方计费表达式和额度饱和保护优先级高于旧定制计费路径；Agent/CXM 充值、退款和排行榜只能消费已结算的官方日志语义。

### 数据迁移

每次迁移前生成 schema 快照和关键表计数，迁移后执行字段、索引、约束、数据计数和回滚投影检查。CXM 迁移必须继续支持 dry-run、审计记录和按批回滚，不得用覆盖式脚本替换历史数据。

## 冲突处理规则

1. 官方安全、计费、数据库兼容和协议修复默认保留官方实现。
2. 当前定制功能的业务语义默认保留，但必须改接官方新接口；不能以旧文件整体覆盖官方文件。
3. `controller`、`model`、`service` 冲突按“官方基础逻辑 + 定制分支调用”重写，并为每个业务不变量添加回归测试。
4. 前端目录迁移冲突按新路径解决；确认没有引用旧 `web/default` 和 `web/classic` 构建路径后，才删除旧路径。
5. 官方删除而当前修改的文件必须逐个判断：属于官方替代功能的迁移到新接口；属于定制功能的保留并改名或移位；不能使用批量 `ours`/`theirs` 解决。

## 阶段门禁

### Gate 0：基线冻结

记录当前 commit、镜像、Go/Bun 版本、数据库 schema、定制 API 清单和未跟踪文件清单。集成分支必须从官方主线创建，当前 `custom` 保持不变。

### Gate 1：官方骨架可构建

官方后端、`relaykit`、`plugins`、官方前端和数据库初始化通过；不接入定制业务时，Go 测试和前端构建通过。

### Gate 2：后端定制可用

Agent/CXM、排行榜和真实地址在三种数据库上通过模型、服务、接口和权限测试；官方认证、计费和渠道测试不回归。

### Gate 3：前端定制可用

官方 `web` 构建通过，Agent、排行榜、定价/用量日志和真实地址页面通过类型检查、单元测试和手工接口验收。

### Gate 4：迁移与发布

完成 staging 数据库迁移演练、CXM dry-run/回滚演练、生产镜像构建、健康检查和回滚命令审查。所有失败均回到上一个已通过门禁的提交。

## 验收标准

1. `git diff --check` 无空白错误，官方与定制代码均无未解决冲突标记。
2. `go test ./...`、官方要求的 Go vet/build 检查和定制回归测试通过。
3. `web` 目录的 `bun install --frozen-lockfile`、`bun run typecheck`、`bun run test`、`bun run build` 通过。
4. SQLite、MySQL、PostgreSQL 的 AutoMigrate/升级/回滚演练通过。
5. Agent/CXM/排行榜/真实地址的 API 权限、审计、脱敏、额度和并发不变量通过。
6. 官方分档计费、缓存、Responses、工具调用和重试换组回归通过。
7. 生产部署前保留当前镜像和数据库备份，并能在不改写历史数据的情况下恢复上一版本。
