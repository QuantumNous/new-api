# 双钱包(充值钱包 / 免费钱包)拆分 — 需求文档

> 文档编号:WALLET-SPLIT-REQ-01
> 状态:待评审
> 关联分支:main

## 1. 背景与问题

当前系统中,用户余额是 `User` 表的**单一整数字段 `Quota`**(`model/user.go:39`)。所有来源的额度——在线充值、签到奖励、充值赠送、兑换码、邀请返佣、管理员手动调额——全部累加进这一个字段,**没有来源区分、没有明细、没有过期机制**。

由此产生两个核心业务痛点:

1. **退款无法区分资金来源**:用户申请退款时,系统分不清余额里多少是用户真金白银充值的、多少是平台赠送的(签到/充值赠送/免费兑换码)。理论上只应退还用户实际充值部分,但现状无法拆分。
2. **免费额度长期沉淀**:签到、赠送等免费额度一旦发放永不过期。大量不活跃用户账户里积压免费额度,形成平台的"隐性负债",且无法通过过期机制促活。

## 2. 目标

将用户余额从"单一钱包"拆分为**两个逻辑钱包**:

| 钱包 | 资金来源 | 是否可退款 | 是否过期 |
|------|----------|-----------|----------|
| **充值钱包**(recharge wallet) | 用户在线充值本金、原有历史额度、佣金转入 | 可退款 | 不过期 |
| **免费钱包**(free wallet) | 签到奖励、充值赠送额度、被标记为"免费"的兑换码额度 | 不可退款 | 逐条独立过期 |

**核心不变式**:`总可用额度 = 充值钱包余额 + 免费钱包余额`。对上游计费、Token 额度校验等所有"看总额"的逻辑,行为保持不变。

## 3. 功能需求

### 3.1 钱包拆分(REQ-3.1)

- **REQ-3.1.1** `User` 表新增 `free_quota` 字段表示免费钱包余额;现有 `quota` 字段语义收窄为**充值钱包余额**。
- **REQ-3.1.2** 数据迁移:上线时,存量用户的 `quota` 原值保留在充值钱包(即 `quota` 不动),`free_quota` 初始化为 0。**存量额度一律视为充值额度**,不追溯拆分。
- **REQ-3.1.3** 免费钱包的**每一笔入账**都以单条明细记录保存(来源、金额、发放时间、过期时间、剩余可用)。
- **REQ-3.1.4** 充值钱包的入账**不要求**逐条明细(维持现有日志即可)。

### 3.2 扣费顺序(REQ-3.2)

- **REQ-3.2.1** 消费扣费采用**三级优先级**:
  1. **免费钱包中会过期的额度**(按过期时间升序,即将到期优先)——抢在过期前消耗,避免浪费。
  2. **充值钱包**——充值额度可退款,尽早消耗以降低平台的退款敞口。
  3. **免费钱包中不过期的额度**——反正不会流失,留到最后消耗。
  > 设计理由:从"减少可退款余额敞口 + 避免免费额度过期浪费"双重目标出发。会过期的免费额度不花就没了,必须最先花;不过期的免费额度和充值额度都不流失,但充值额度是用户可申请退款的,先花充值额度能降低平台需退款的余额,故充值额度排在不过期免费额度之前。
- **REQ-3.2.2** 免费钱包**会过期额度**内部按**过期时间升序**扣减(即将到期优先);**不过期额度**内部按入账时间升序(先进先出)。
- **REQ-3.2.3** 免费钱包扣减**不产生逐条减扣明细**(仅更新每条入账明细的"剩余可用");充值钱包扣减维持现有日志。
- **REQ-3.2.4** 退款(预扣多退、任务失败退款)按"原路退回"原则:从哪个钱包扣的退回哪个钱包(免费钱包退回时恢复对应明细的剩余额度,但**不改变原过期时间**)。

### 3.3 免费额度过期(REQ-3.3)

- **REQ-3.3.1** 免费钱包每条入账明细带独立 `expired_time`。
- **REQ-3.3.2** 额度过期后,**已过期但未使用的部分**从免费钱包余额中扣除、明细标记为已过期,不再可用。
- **REQ-3.3.3** 回收机制:后台定时任务扫描过期明细并回收(用户余额准实时更新);同时在用户扣费时惰性检查并清理该用户的过期明细(双保险)。
- **REQ-3.3.4** 过期回收要写一条系统日志,便于审计。

### 3.4 签到改造(REQ-3.4)

- **REQ-3.4.1** 签到发放的额度进入**免费钱包**(而非现在的 `quota`)。
- **REQ-3.4.2** 签到额度有效期 **7 天**(可配置,默认 7 天),生成一条带 7 天过期时间的免费钱包明细。
- **REQ-3.4.3** 签到成功文案在原有基础上追加提醒:"签到额度有效期 7 天,不使用会过期"。前后端文案 + i18n 均需更新。

### 3.5 充值赠送改造(REQ-3.5)

- **REQ-3.5.1** 充值功能新增**赠送额度**能力:管理员可配置充值赠送规则(赠送额度 + 赠送额度过期天数)。
- **REQ-3.5.2** 用户充值成功时:**充值本金进入充值钱包**,**赠送额度进入免费钱包**(带过期时间的明细)。
- **REQ-3.5.3** 赠送规则采用**按充值档位配置赠送额**:管理员配置若干档位(如充 100 送 8、充 500 送 50、充 1000 送 120),充值时命中**最高满足档位**的赠送额。不采用固定比例赠送。
- **REQ-3.5.4** 所有支付渠道(Stripe / Creem / Waffo / WaffoPancake / 易支付 / 管理员补单)统一支持赠送。

### 3.6 兑换码改造(REQ-3.6)

- **REQ-3.6.1** 兑换码支持设置**兑换后额度的有效期**(兑换成功后 N 天过期)。若设置了有效期,则兑换额度进入**免费钱包**(带过期明细);未设置有效期则进入充值钱包(维持现状)。
- **REQ-3.6.2** 支持**自定义兑换码**(管理员可指定 key,而非仅随机 UUID),需校验唯一性。
- **REQ-3.6.3** 支持**同一个兑换码可被兑换多次**(设置最大兑换次数 `max_uses`),核销从"一次性开关"改为"计数模型"。
- **REQ-3.6.4** **限制同一个兑换码,同一用户仅可兑换一次**(即使该码 `max_uses > 1`,同一用户也不能重复领)。
- **REQ-3.6.5** **限制同一批次兑换码(按标签 tag),同一用户仅可兑换一次**——同一用户在带相同标签的一批码里,只能领其中任意一个。
- **REQ-3.6.6** 限领判定按 `(tag, userId)` 与 `(redemptionKey, userId)` 进行;限领记录**保存到该标签被删除为止**(标签删除时清理对应记录)。

### 3.7 管理员调额改造(REQ-3.7)

- **REQ-3.7.1** 管理员在后台调整用户额度时,必须能**选择目标钱包**:充值钱包 或 免费钱包(现状只调单一 `quota`)。
- **REQ-3.7.2** 三种调额模式(增加 `add` / 减少 `subtract` / 覆盖 `override`)都要支持指定目标钱包:
  - 目标为**充值钱包**:直接调整 `quota`(行为与现状一致)。
  - 目标为**免费钱包**:
    - `add` → 新增一条免费钱包明细(须指定过期时间/有效天数),`free_quota` 增加。
    - `subtract` → 按过期时间升序扣减免费明细,`free_quota` 减少。
    - `override` → 将免费钱包重置为指定值(实现上:作废现有免费明细并新增一条指定值明细,须指定过期时间)。
- **REQ-3.7.3** 给免费钱包**增加/覆盖**额度时,管理员**必须指定过期时间**(默认可给一个合理默认天数,如 7 天),以维持"免费钱包逐条过期"不变式。
- **REQ-3.7.4** 调额操作写管理日志时,须记录**目标钱包**信息(如"管理员增加用户免费钱包额度 X,有效期 N 天")。
- **REQ-3.7.5** 前端调额弹窗新增"目标钱包"选择项;选中免费钱包时展示"有效期"输入项。

## 4. 非功能需求

- **NFR-1 数据库兼容**:所有改动必须同时兼容 SQLite / MySQL≥5.7.8 / PostgreSQL≥9.6(遵循 CLAUDE.md Rule 2)。
- **NFR-2 性能**:扣费为每次 API 调用的热路径,免费钱包"按过期排序扣减"不得引入不可接受的延迟。需用 Redis 缓存免费钱包明细(ZSet 按过期时间排序),避免热路径直打 DB 聚合。
- **NFR-3 一致性**:两钱包余额之和必须始终等于旧口径总额;缓存(Redis)与 DB 必须最终一致,并修复现有"充值/兑换码事务不刷缓存"的隐患。
- **NFR-4 兼容 BatchUpdate**:改造必须兼容 `BATCH_UPDATE_ENABLED` 攒批模式。
- **NFR-5 并发安全**:高并发扣费/过期回收/退款不得出现余额错乱或双花。
- **NFR-6 向后兼容**:对外 API(如 `/dashboard/billing`、用户额度展示)语义保持"总额"口径不变,新增字段以扩展形式暴露。

## 5. 范围边界(明确不做)

- 不拆分**佣金余额**(`CommissionBalance`),它本就是独立体系。
- 不改动**订阅额度**(subscription)的核算逻辑;订阅额度是独立于两钱包的第三账。
- 不追溯拆分存量额度(存量一律算充值钱包)。
- 邀请返佣额度(`QuotaForInvitee`)、新用户注册赠送、佣金转入余额,本期**统一归入充值钱包(不过期)**,行为与现状一致,不设过期。

## 6. 关键设计决策(已与需求方确认)

| 决策点 | 结论 |
|--------|------|
| 钱包在 User 表如何存 | 新增 `free_quota` 字段,`quota` 收窄为充值钱包 |
| 免费明细过期粒度 | 逐条明细独立过期 |
| 过期未用部分处理 | 后台定时任务扫描回收 + 扣费时惰性回收(双保险) |
| 限领记录表设计 | 独立 `redemption_claim` 记录表,保留到标签删除 |
| 充值赠送规则形态 | 按充值档位配置赠送额(命中最高满足档位),不采用固定比例 |
| 邀请/佣金/注册赠送归属 | 统一归充值钱包,不过期 |
| 用户前端额度展示 | 拆分展示充值/免费/总额三值 + 免费钱包明细列表(带过期倒计时) |
| 管理员调额目标钱包 | 调额可选目标钱包(充值/免费);调免费钱包须指定过期时间 |

## 7. 前端展示需求(REQ-7)

- **REQ-7.1** 用户中心额度区**拆分展示**:充值钱包余额、免费钱包余额、总可用额度三个数值。
- **REQ-7.2** 展示免费钱包**明细列表**:每条含来源(签到/充值赠送/兑换码)、剩余额度、过期时间(带倒计时提示"N 天后过期")。
- **REQ-7.3** 对外总额口径的展示位(如导航栏余额)继续显示总额度,保证既有体验不变。

## 8. 验收标准(概要)

- [ ] 充值 → 本金进充值钱包,赠送进免费钱包并带过期明细
- [ ] 签到 → 额度进免费钱包,7 天过期,文案含提醒
- [ ] 免费兑换码 → 额度进免费钱包并带过期明细
- [ ] 消费扣费顺序:免费(即将到期优先)→ 充值
- [ ] 免费额度过期后被回收,总额度正确减少
- [ ] `quota + free_quota` 始终等于旧口径总可用额度
- [ ] 兑换码支持自定义 key / 多次核销 / 每人限领 / 标签批次限领
- [ ] `quota + free_quota` 始终等于旧口径总可用额度
- [ ] 三种数据库全部通过;BatchUpdate 开/关均正确;缓存与 DB 一致
- [ ] 前端拆分展示充值/免费/总额 + 免费明细列表(带过期倒计时)
