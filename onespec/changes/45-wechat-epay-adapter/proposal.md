# 微信支付 Epay 适配器需求文档

建设一个独立部署的轻量支付适配器，在不修改 new-api 源码的前提下，把 new-api 的 Epay 下单协议转换为微信支付 API v3 Native 扫码支付，并在支付成功后可靠、幂等地通知 new-api 完成充值到账。

需求覆盖 Epay 表单下单与 MD5 签名校验、微信支付 API v3 Native 下单、扫码收银台、微信异步通知验签解密、订单状态和通知任务持久化、失败重试、人工补偿、健康检查及审计能力。首期面向单个 new-api 站点和单个微信支付普通商户号，余额充值为主验收场景。

范围外包括修改 new-api 源码、支付宝及其他支付渠道、微信 JSAPI/H5/小程序支付、多商户及服务商模式、自动退款、分账、提现和完整支付运营后台。浏览器同步返回不得作为到账依据。

## 2. 变更详情

### 2.1 独立支付适配器与 Epay 入口
**Epay 订单接入**
- **现状**：new-api 已能按 Epay 协议生成表单下单请求并接收签名回调，但仓库内不存在将 Epay 协议转换为企业微信支付 API v3 的网关服务。
- **目标**：当 new-api 提交合法 Epay 订单时，支付适配器应校验商户身份、支付类型、签名、金额和目标地址，并创建唯一的本地支付订单；若订单号冲突、金额非法或地址不可信，支付适配器应拒绝请求且不得创建订单。
- **原因**：企业微信商户通道与 new-api 现有 Epay 协议不能直接连接，需要独立协议适配层，同时保持 new-api 后续升级能力。
- **影响**：新增独立服务、部署域名、数据库和密钥配置；new-api 仅需使用现有支付配置接入，不变更其代码和既有 Epay 契约。

### 2.2 微信 Native 支付与收银台
**微信支付下单和用户支付体验**
- **现状**：new-api 可拉起通用 Epay 表单，但没有企业微信 Native 下单、二维码收银台和本地支付状态展示能力。
- **目标**：当 Epay 订单校验通过时，支付适配器应以精确的人民币分金额向微信支付创建 Native 订单；当微信返回有效支付链接时，支付适配器应向用户展示订单金额、二维码、有效期和本地状态；若订单过期或返回地址不可信，收银台应停止支付引导且不得跳转到不可信地址。
- **原因**：用户需要从 new-api 充值入口完成企业微信扫码支付，同时同步页面行为不能越过服务端支付确认。
- **影响**：新增微信支付外部依赖和公开收银台；需进行金额精度、浏览器兼容、开放跳转和访问凭据安全测试。

### 2.3 支付通知、状态一致性与到账
**微信通知与 new-api 回调闭环**
- **现状**：new-api 的 Epay 回调处理已通过数据库事务和订单状态校验保证充值幂等，但缺少负责验证微信 API v3 通知并可靠转发 Epay 成功回调的上游服务。
- **目标**：当微信支付发送成功通知时，支付适配器应先验签和解密，再核对商户号、AppID、订单号、币种和金额；仅在全部匹配时，支付适配器应原子保存支付结果和 new-api 通知任务。若同一通知重复或并发到达，支付适配器应最多产生一次有效状态迁移和一次有效到账。
- **原因**：支付属于核心交易流程，必须防止伪造回调、错单、错额、半完成事务和重复充值。
- **影响**：新增订单状态机、可靠事务边界、唯一性约束和异常人工审查状态；需与 new-api 现有回调验签及幂等行为联调。

### 2.4 可靠通知、运维与安全
**下游通知和可运营性**
- **现状**：独立适配器尚无持久化通知、故障恢复、管理查询、人工补偿、健康检查、指标和密钥隔离能力。
- **目标**：当 new-api 暂时不可用或返回非成功结果时，支付适配器应持久化失败原因并按计划重试；在服务重启后，支付适配器应恢复未完成通知。授权管理员应能查询异常订单并重试通知，未授权请求应被拒绝。支付适配器应通过精确白名单、HTTPS、最小权限和日志脱敏保护支付数据与密钥。
- **原因**：付款成功后的通知失败不能导致订单永久未到账，且支付异常需要可追踪、可补偿、可告警。
- **影响**：新增后台任务、管理接口、审计日志、指标告警和备份恢复要求；生产上线依赖域名、证书、微信商户能力和人工退款 SOP。

### 2.5 明确不做
- 不修改 new-api 源码或其现有 Epay 充值逻辑。
- 不实现支付宝、银联、微信 JSAPI、H5、小程序等其他支付方式。
- 不实现多商户、服务商子商户、自动退款、撤销、分账、提现或完整支付管理后台。
- 不将浏览器同步返回或客户端轮询结果作为到账依据。
- 首期不将订阅购买及其他 Epay 业务纳入产品验收范围。

### 2.6 风险与应对
- 风险点: 金额精度错误、回调伪造、SSRF 或开放跳转、并发重复到账、通知任务丢失、微信验签材料配置错误、new-api 契约升级不兼容。
- 应对措施: 使用十进制定点金额；微信通知先验签解密再核对完整业务字段；对 URL 做规范化和精确白名单校验；通过唯一约束、事务和条件状态迁移保证幂等；持久化通知和恢复调度；上线前完成证书轮换、故障注入及 Epay 契约回归。
- 回滚策略: 暂停 new-api 的微信支付方式和适配器入口，保留订单只读查询、已支付订单通知补偿及审计能力；不得删除支付订单或以回滚为由撤销已确认到账结果。

- [ ] 验证 `0.01`、`0.10`、`1.01` 元分别精确转换为 1、10、101 分并传给微信支付。
- [ ] 验证微信 Native 下单成功、失败、超时和重复请求时的订单结果一致。
- [ ] 验证收银台展示、过期处理、不可猜测访问凭据和不可信返回地址拦截。
- [ ] 验证微信通知的签名、解密、商户、AppID、订单、币种和金额校验。
- [ ] 验证同一成功通知重复或并发 10 次时只形成一次有效支付和到账。
- [ ] 验证支付事务提交前故障会回滚，提交后重启可恢复 new-api 通知。
- [ ] 验证 new-api 停机、超时或返回非 `success` 时持久化重试，恢复后最终只到账一次。
- [ ] 验证订单查询和人工重试仅对授权角色开放，并留下完整审计记录。
- [ ] 验证日志、镜像、数据库和代码仓库不包含商户私钥或明文完整密钥。
- [ ] 验证下单校验、状态查询和正常到账满足 PRD 性能及时效目标。
- [ ] 灰度完成至少 20 笔真实小额支付，核对适配器订单、微信流水、new-api 订单和到账额度一致。
