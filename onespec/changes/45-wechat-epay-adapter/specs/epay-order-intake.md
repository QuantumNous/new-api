# Delta Spec: Epay 订单接入与校验

> 本文件聚焦支付适配器的 Epay 订单入口，是对 `../proposal.md §2.1 独立支付适配器与 Epay 入口` 的精化。
> 与 proposal 的分工：proposal 描述跨模块的全局变更意图，本文件描述 Epay 请求校验、金额和地址边界以及订单幂等行为。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当 new-api 提交字段完整且签名有效的 Epay 订单时，支付适配器应校验商户身份、支付类型、金额和目标地址，并创建唯一的待处理订单。
- 当订单金额通过校验时，支付适配器应以十进制定点语义保存原始元金额和对应人民币分金额。
- 当相同商户订单号和相同关键业务字段再次提交时，支付适配器应返回原订单的可继续支付结果，不得创建重复订单。

**前置约束**:
- 若商户 ID 与配置不一致、支付类型不是 `wxpay` 或签名类型不是 `MD5`，支付适配器应拒绝请求且不得创建订单。
- 若任一必填字段缺失、签名不匹配或金额不是大于等于 0.01 元且最多两位小数的合法十进制数，支付适配器应拒绝请求。
- 若通知地址不是配置允许的 HTTPS 来源和路径，支付适配器应拒绝请求。
- 若跳转地址既不是可信站点地址也不是可信相对路径，支付适配器应拒绝请求或忽略该跳转地址，不得产生开放跳转。

**异常与边界**:
- 当金额为 `0.01`、`0.10`、`1.01` 元时，支付适配器应分别得到 1、10、101 分，不得出现浮点舍入差异。
- 若地址规范化后指向环回、链路本地、私网、非预期端口或越过允许路径，支付适配器应拒绝请求且不得发起网络访问。
- 若相同商户订单号以不同金额、通知地址或其他关键业务字段提交，支付适配器应拒绝冲突请求并记录脱敏安全审计事件。
- 在并发提交相同订单的情况下，支付适配器应最多保留一个有效本地订单。

## 2. 验收标准

- [ ] **正常场景**: 给定配置有效且字段、签名、金额和地址均合法的请求，当 new-api 提交订单时，支付适配器创建一条待处理订单并继续支付流程。
- [ ] **签名场景**: 给定一份合法请求，当任意已签名字段被修改而签名未同步更新时，支付适配器拒绝请求且不创建订单。
- [ ] **金额边界**: 给定 `0.01`、`0.10`、`1.01` 元，当订单被校验时，持久化金额分分别为 1、10、101。
- [ ] **金额异常**: 给定三位小数、非数字、零、负数或超过配置上限的金额，当提交订单时，支付适配器拒绝请求且不创建订单。
- [ ] **地址安全**: 给定非 HTTPS、非白名单、私网、环回、异常端口或规范化后越界的地址，当提交订单时，支付适配器拒绝请求且不访问目标地址。
- [ ] **幂等场景**: 给定已存在的订单，当相同业务字段再次提交时，支付适配器返回原订单结果且订单数量不变。
- [ ] **冲突场景**: 给定已存在的订单，当相同订单号携带不同金额或通知地址时，支付适配器拒绝请求、保留原订单并记录审计事件。
- [ ] **并发场景**: 给定相同合法订单被并发提交，当请求全部完成时，仅存在一条有效订单且无相互冲突的支付结果。

## 3. 范围说明

**范围内 (In Scope)**:
- Epay 请求字段、商户身份、支付类型和 MD5 签名规则。
- 十进制金额校验和人民币分转换。
- 通知及跳转地址的规范化、白名单和 SSRF 防护。
- 商户订单号唯一性、重复请求和冲突请求行为。

**范围外 (Out of Scope)**:
- 微信支付 Native 下单和二维码展示，由 `wechat-native-payment.md` 负责。
- 微信成功通知、支付状态迁移和 new-api 回调，由 `payment-settlement.md` 负责。
- 具体实现方案（由 `design.md` 承接）。
