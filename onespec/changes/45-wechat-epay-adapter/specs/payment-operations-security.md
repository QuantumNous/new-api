# Delta Spec: 支付运维、安全与可恢复性

> 本文件聚焦支付服务的运营补偿、安全控制和可观测性，是对 `../proposal.md §2.4 可靠通知、运维与安全` 的精化。
> 与 proposal 的分工：proposal 描述生产可运营目标，本文件描述管理权限、人工补偿、健康状态、审计、指标、密钥和恢复要求。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当服务进程正常运行时，支付适配器应提供可用于判断进程存活的状态。
- 当数据库和必要支付配置均可用时，支付适配器应报告可接收支付流量；若任一关键依赖不可用，支付适配器应报告未就绪。
- 当授权管理员按商户订单号查询时，支付适配器应提供支付状态、微信交易号、金额、支付时间、通知状态、重试次数和最近脱敏失败原因。
- 当授权管理员对已支付且通知未成功的订单发起人工重试时，支付适配器应复用原通知任务并记录操作者、时间和结果。
- 当订单创建、支付成功、微信回调失败、订单进入人工审查或通知积压时，支付适配器应更新对应可观测指标。

**前置约束**:
- 若请求者未通过管理认证或没有相应权限，支付适配器应拒绝订单详情查询和人工重试，不得泄露订单数据。
- 若必要密钥、私钥文件或商户配置缺失，支付适配器应保持未就绪且不得接收新支付流量。
- 支付适配器应通过 HTTPS 和受控网络传输支付数据，数据库及服务内部端口不得直接暴露公网。

**异常与边界**:
- 在服务重启的情况下，支付适配器应从持久化数据恢复未完成通知和待处理状态，不得依赖仅存于内存的数据。
- 当通知积压、连续回调失败或订单进入人工审查时，支付适配器应产生可定位订单和请求的告警，但不得在日志中输出完整密钥、私钥或可复用支付凭据。
- 在微信验签材料轮换窗口内，支付适配器应按材料标识验证有效的新旧材料；旧材料退役后应停止接受其签名。
- 在微信或 new-api 不可用的状态下，支付适配器应延迟相关业务步骤，不得猜测支付成功。
- 当执行备份恢复时，支付订单与通知任务之间的关系应保持一致。

## 2. 验收标准

- [ ] **存活状态**: 给定服务进程正常运行，当请求存活状态时，返回可用结果，且非关键下游短暂故障不被误判为进程死亡。
- [ ] **就绪状态**: 给定正常配置和数据库，当请求就绪状态时返回可接流量；当数据库不可用或必要配置缺失时返回未就绪。
- [ ] **管理查询**: 给定授权管理员和已存在订单，当按订单号查询时，返回完成支付核对所需的支付及通知信息。
- [ ] **权限拒绝**: 给定普通用户或匿名请求，当查询订单或触发人工重试时，请求被拒绝且业务数据不变化。
- [ ] **人工补偿**: 给定已支付且通知未成功的订单，当授权管理员重试时，原任务被复用并记录完整审计信息。
- [ ] **指标告警**: 给定可控制的订单及故障场景，当创建订单、支付成功、回调失败、进入人工审查和通知积压时，对应指标准确变化并按配置告警。
- [ ] **敏感信息**: 给定正常和异常支付链路，当扫描镜像、代码仓库、数据库和日志时，不存在商户私钥或明文完整密钥。
- [ ] **重启恢复**: 给定待支付、已支付待通知和重试中的订单，当服务重启后，持久化状态保持一致且未完成任务可继续处理。
- [ ] **材料轮换**: 给定新旧验签材料并存的轮换窗口，当接收分别由有效材料签名的通知时均可正确验证；旧材料退役后其通知被拒绝。
- [ ] **备份恢复**: 给定生产等价数据，当执行备份和恢复时，数据恢复点不超过 15 分钟且单实例恢复不超过 1 小时。
- [ ] **性能指标**: 给定代表性正常负载，当测量服务处理时，排除微信网络耗时的下单校验 P95 不超过 300 毫秒，收银台状态查询 P95 不超过 500 毫秒。
- [ ] **到账时效**: 给定微信和 new-api 链路正常的一批成功订单，当统计支付成功到到账时长时，至少 95% 在 10 秒内完成且无重复到账。

## 3. 范围说明

**范围内 (In Scope)**:
- 服务存活和就绪状态语义。
- 受保护的订单查询及人工通知补偿。
- 审计日志、业务指标、故障告警和敏感信息保护。
- 密钥隔离、验签材料轮换、重启恢复、备份恢复和性能目标。

**范围外 (Out of Scope)**:
- 完整可视化支付运营后台。
- 自动退款、撤销、分账、提现和财务对账。
- Epay 入口、微信下单和支付确认的核心业务规则，由相邻 Delta Spec 负责。
- 具体实现方案（由 `design.md` 承接）。
