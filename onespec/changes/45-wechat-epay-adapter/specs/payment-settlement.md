# Delta Spec: 支付确认与 new-api 到账

> 本文件聚焦支付结果确认、订单一致性和下游到账，是对 `../proposal.md §2.3 支付通知、状态一致性与到账` 的精化。
> 与 proposal 的分工：proposal 描述交易闭环，本文件描述可信支付事实、状态迁移、事务原子性、幂等和 Epay 成功通知行为。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当微信支付发送异步通知时，支付适配器应先验证通知签名，再解密通知资源。
- 当通知表明交易成功且商户号、AppID、商户订单号、币种和金额均与本地订单一致时，支付适配器应原子保存支付结果并创建待发送的 new-api 通知任务。
- 当已支付订单需要通知 new-api 时，支付适配器应使用本地已核对订单数据生成 Epay 成功回调和签名。
- 当 new-api 的 HTTP 响应成功且正文去除空白后严格等于 `success` 时，支付适配器应将通知任务置为成功并停止重试。

**前置约束**:
- 若微信通知签名无效、资源无法解密或交易状态不是成功，支付适配器应拒绝业务处理且不得改变订单状态。
- 若商户号、AppID、订单号、币种或金额任一不匹配，支付适配器应将可关联订单置为人工审查，不得通知 new-api。
- 若本地订单不存在，支付适配器应拒绝自动到账并记录可审计异常。
- 若订单已过期或关闭后收到成功通知，支付适配器应进入人工审查，不得静默丢弃或直接到账。

**异常与边界**:
- 当相同成功通知重复或并发到达时，支付适配器应最多完成一次有效支付状态迁移并保留一个有效下游通知任务。
- 若支付结果更新和通知任务创建的事务在提交前失败，支付适配器应回滚全部业务变化。
- 在支付事务已提交但通知尚未完成的状态下，支付适配器应在重启后继续发送通知。
- 若 new-api 超时、连接失败、返回非成功响应或正文不是 `success`，支付适配器应保存脱敏失败原因并按计划重试。
- 当同一通知任务重试时，支付适配器应保持订单号、交易号、金额和其他业务标识一致，不得创建新支付订单。

## 2. 验收标准

- [ ] **合法通知**: 给定匹配的待支付订单，当签名、密文和全部业务字段合法的微信成功通知到达时，订单变为已支付且仅创建一个 new-api 通知任务。
- [ ] **签名异常**: 给定待支付订单，当微信签名、时间戳或随机串无效时，订单和通知任务均不变化。
- [ ] **解密异常**: 给定通过 HTTP 签名校验的通知，当资源无法解密时，订单不变且不创建通知任务。
- [ ] **字段不匹配**: 给定待支付订单，当商户号、AppID、订单号、币种或金额任一不匹配时，订单进入人工审查且不通知 new-api。
- [ ] **重复并发**: 给定同一合法成功通知，当连续和并发各发送 10 次时，仅产生一次有效支付状态迁移、一个有效通知任务和一次 new-api 到账。
- [ ] **事务回滚**: 给定可注入提交前故障的环境，当订单更新后、任务创建或事务提交前发生故障时，支付结果和任务均不留下半完成状态。
- [ ] **提交后恢复**: 给定支付事务已提交且通知未完成，当适配器重启时，通知任务恢复执行并最终完成。
- [ ] **回调内容**: 给定已支付订单，当通知 new-api 时，Epay 字段齐全、金额来自本地订单且签名有效。
- [ ] **成功判定**: 给定 new-api 返回前后带空白的 `success`，当适配器处理响应时，通知任务置为成功并停止重试。
- [ ] **失败重试**: 给定 new-api 超时、连接失败、返回非成功响应或其他正文，当适配器处理响应时，通知保持未完成并按计划重试。
- [ ] **重试稳定性**: 给定同一任务多次重试，当比较各次业务字段时，订单号、交易号和金额保持一致且不创建新支付订单。

## 3. 范围说明

**范围内 (In Scope)**:
- 微信通知验签、解密和完整业务字段核对。
- 支付订单状态、人工审查和事务原子性。
- 重复及并发通知幂等。
- Epay 成功回调内容、成功判定、持久化失败和恢复重试。

**范围外 (Out of Scope)**:
- Epay 下单入口和微信 Native 订单创建，分别由其他 Delta Spec 负责。
- 管理查询、人工补偿权限和指标告警，由 `payment-operations-security.md` 负责。
- new-api 内部充值实现的代码变更；本变更只依赖其现有 Epay 契约。
- 具体实现方案（由 `design.md` 承接）。
