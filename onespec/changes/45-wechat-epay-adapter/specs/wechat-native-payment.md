# Delta Spec: 微信 Native 下单与收银台

> 本文件聚焦微信 Native 下单和用户支付体验，是对 `../proposal.md §2.2 微信 Native 支付与收银台` 的精化。
> 与 proposal 的分工：proposal 描述支付链路目标，本文件描述微信订单创建、收银台状态展示及客户端行为边界。

## 1. 需求描述 (中文 EARS)

**主流程**:
- 当 Epay 订单通过校验时，支付适配器应以配置的 AppID、商户号、商户订单号、商品描述、回调信息、订单有效期和人民币分金额向微信支付创建 Native 订单。
- 当微信支付返回有效支付链接时，支付适配器应将支付链接关联到本地订单，并将订单置为可支付状态。
- 当用户以有效订单访问收银台时，收银台应展示商品名称、应付金额、微信支付二维码、剩余有效时间和本地支付状态。
- 当本地订单变为已支付时，收银台应在下一次状态刷新后展示成功，并仅在返回地址已通过校验时允许跳转。

**前置约束**:
- 若微信支付必要商户配置或验签材料缺失，支付适配器应停止接收新的支付流量，不得构造不可用的支付结果。
- 若微信未返回有效支付链接，支付适配器应将订单保持在不可支付状态，不得展示伪造二维码。
- 若收银台访问凭据无效或与订单不匹配，支付适配器应拒绝展示订单详情。

**异常与边界**:
- 若微信下单失败或超时，支付适配器应保存可追踪且脱敏的失败原因，并将订单置为创建失败或可重试状态。
- 当相同订单被重复或并发触发微信下单时，支付适配器应避免产生相互冲突的本地支付结果。
- 当订单过期或关闭时，收银台应停止展示可支付状态和有效二维码，并提示用户重新发起支付。
- 当状态查询暂时失败时，收银台应保留已有订单信息并允许恢复查询，不得自行推断支付成功。
- 在浏览器同步返回被伪造或提前触发的情况下，支付适配器和 new-api 均不得据此完成到账。

## 2. 验收标准

- [ ] **正常下单**: 给定一条校验通过的订单，当支付适配器调用微信支付时，请求中的商户身份、订单号和人民币分金额与本地订单一致。
- [ ] **支付链接**: 给定微信返回有效支付链接，当下单完成时，本地订单关联该链接并可进入收银台。
- [ ] **下单失败**: 给定微信返回业务错误、连接超时或无效支付链接，当下单结束时，订单不可支付且用户界面不暴露内部堆栈或密钥。
- [ ] **重复下单**: 给定同一订单被重复或并发触发，当请求完成时，本地仅保留一个一致的有效支付结果。
- [ ] **收银台展示**: 给定待支付订单和有效访问凭据，当用户打开收银台时，页面展示正确商品、金额、二维码、剩余时间和状态。
- [ ] **状态刷新**: 给定已打开的收银台，当本地订单变为已支付时，下一次刷新展示支付成功，但客户端请求本身不修改订单状态。
- [ ] **过期场景**: 给定过期或关闭订单，当用户打开收银台时，页面停止支付引导并提示重新发起订单。
- [ ] **跳转安全**: 给定缺失或不可信的返回地址，当支付成功时，页面停留在结果页且不跳转。
- [ ] **访问控制**: 给定无效、猜测或其他订单的访问凭据，当访问收银台时，订单信息不被披露。

## 3. 范围说明

**范围内 (In Scope)**:
- 微信 Native 订单创建的业务输入和成功判定。
- 支付链接与本地订单关联。
- 收银台内容、状态刷新、过期和安全跳转行为。
- 收银台访问凭据及客户端不可作为支付事实来源的约束。

**范围外 (Out of Scope)**:
- Epay 请求验签和地址入口校验，由 `epay-order-intake.md` 负责。
- 微信异步通知验签、解密及支付到账，由 `payment-settlement.md` 负责。
- 页面视觉设计和具体实现方案（由 `design.md` 承接）。
