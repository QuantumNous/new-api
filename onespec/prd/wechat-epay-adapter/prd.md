# 微信支付 Epay 适配器需求文档

## 0. 评审摘要（必读，约 2 页）

> 本节供产品、研发、测试快速评审；详细条款见 `## 1` 及之后。

### 0.1 一句话需求

建设一个独立部署的轻量支付适配器，在不修改 new-api 源码的前提下，把 new-api 的 Epay 下单协议转换为微信支付 API v3 Native 扫码支付，并在支付成功后可靠、幂等地通知 new-api 完成充值到账。

### 0.2 做什么 / 不做什么

- **做什么**：兼容 Epay 下单与回调签名；调用微信 Native 下单；提供扫码收银台；验签、解密并核对微信支付通知；持久化订单与通知任务；失败重试；提供健康检查、订单查询和人工补偿能力。
- **不做什么**：不修改 new-api 源码；不接入支付宝、银联、JSAPI、H5 或小程序支付；不支持多商户、服务商子商户、自动退款、分账、提现和完整支付运营后台。
- **首期业务边界**：以 new-api 账户余额充值闭环为验收主场景。适配器按通用 Epay 协议处理订单，不硬编码充值通知路径；订阅购买、其他 Epay 业务的产品验收不在本期范围内。

### 0.3 关键流程或生效方式

1. 用户在 new-api 选择微信支付并发起充值。
2. new-api 按 Epay 协议向适配器提交订单。
3. 适配器验签、校验白名单并保存订单，随后向微信支付发起 Native 下单。
4. 用户在适配器收银台扫码支付。
5. 适配器验证并解密微信支付异步通知，核对商户、应用、订单、币种和金额后将订单置为已支付。
6. 适配器以持久化任务向原始 new-api 通知地址发送 Epay `TRADE_SUCCESS` 回调。
7. 仅当 new-api 返回的正文去除空白后严格等于 `success` 时，适配器才将通知标记为成功。
8. 浏览器同步跳转只改善用户体验，不作为支付成功或额度到账依据。

### 0.4 验收怎么测

- 分别用 `0.01`、`0.10`、`1.01` 元下单，核对请求金额、订单金额和微信支付金额完全一致。
- 篡改 `pid`、`money`、`sign` 或提交非白名单回调地址，确认订单不会创建。
- 正常支付后验证用户额度只增加一次，目标为支付成功后 10 秒内到账。
- 对同一微信通知并发或连续重放 10 次，确认本地订单和用户额度均只完成一次。
- 模拟 new-api 停机和适配器重启，确认通知任务不丢失并能恢复重试。
- 伪造微信签名、金额、商户号、AppID 或币种，确认订单不进入已支付状态且不会通知 new-api。

## 2. 项目概述

### 2.1 项目背景

平台已基于 new-api 提供服务，并具备域名、HTTPS 和用户体系。new-api 原生支持 Epay，但企业微信商户使用微信支付 API v3，两者协议不能直接连接。现有个人收款监听方案不适合企业商户，完整支付中台对当前单站点、单商户场景又过重，因此需要一个独立、可审计、可恢复的轻量适配器完成协议转换。

代码现状表明，new-api 已具备 Epay 商户配置、表单拉起、签名回调、充值订单幂等入账和支付方式配置能力。本项目应复用这些公开协议边界，不侵入 new-api 内部实现。

### 2.2 业务目标

- 用户可从 new-api 充值页面选择微信支付并完成扫码付款。
- 支付资金直接进入平台微信支付企业商户账户。
- 支付成功后自动增加用户额度，重复通知不得重复入账。
- 支付失败、超时、验签失败或金额异常时不得错误增加额度。
- 支付订单、回调和下游通知均可查询、追踪和审计。

**成功指标**：

- 正常支付成功后，95% 的订单在 10 秒内完成 new-api 到账。
- 同一订单在重复通知场景下，重复入账数量为 0。
- 已支付订单在通知链路临时故障和服务重启后，最终可恢复通知。
- 上线灰度期至少完成 20 笔真实小额订单，并实现订单、微信流水、支付金额和到账额度四方一致。

### 2.3 项目范围

**范围内**：

- 单个 new-api 站点、单个微信支付普通商户号。
- Epay `POST /submit.php` 兼容下单。
- 微信支付 API v3 Native 下单和异步通知。
- 独立扫码收银台、订单状态查询和安全跳转。
- Epay 成功回调、持久化重试和人工重试。
- 订单、通知状态、关键日志、指标、健康检查和就绪检查。
- Docker 独立部署、HTTPS 入口和数据库持久化。

**范围外**：

- 修改 new-api 源码或改变其已有 Epay 协议。
- 支付宝、银联、JSAPI、H5、小程序支付。
- 多商户、服务商子商户、代理商入驻。
- 自动退款、撤销、分账、提现和财务对账平台。
- 完整可视化支付管理后台。
- 将浏览器同步返回作为到账依据。

## 4. 功能需求

### 4.1 Epay 下单

#### PAY-001：接收并校验 Epay 下单请求

**优先级**：P0

**需求描述**：适配器接收 new-api 提交的 Epay 表单请求，完成协议、身份、金额和目标地址校验后创建本地订单。

**业务规则**：

1. 下单入口为 `POST /submit.php`，请求类型为表单。
2. 必填字段包括 `pid`、`type`、`out_trade_no`、`notify_url`、`name`、`money`、`sign`、`sign_type`；`return_url` 和 `device` 可选。
3. `pid` 应等于配置的 Epay 商户 ID，`type` 首期仅接受 `wxpay`，`sign_type` 仅接受 `MD5`。
4. 签名计算时移除 `sign`、`sign_type` 和空值字段，按参数名 ASCII 升序拼接，末尾直接追加共享密钥并计算小写 MD5。
5. `money` 应为大于等于 0.01 元、最多两位小数的十进制金额；系统应使用十进制定点方式换算人民币分，不使用二进制浮点计算。
6. `out_trade_no` 在适配器内唯一；重复请求若关键业务字段一致，应返回原订单的可继续支付结果；字段冲突时应拒绝。
7. `notify_url` 仅允许配置的 HTTPS 站点来源和允许路径；`return_url` 仅允许可信站点或可信相对路径。
8. 地址校验应基于规范化后的协议、主机、端口和路径，不得仅使用字符串前缀匹配。

**验收标准**：

1. 当合法 Epay 请求到达时，适配器应创建唯一待支付订单并继续微信下单流程。
2. 当 `pid`、`type`、`sign_type` 或签名不合法时，适配器应拒绝请求且不创建订单。
3. 当金额包含三位以上小数、非数字、非正数或超过配置上限时，适配器应拒绝请求。
4. 当金额分别为 `0.01`、`0.10`、`1.01` 元时，适配器换算的金额应分别为 1、10、101 分。
5. 当通知或跳转地址指向非白名单域名、非 HTTPS 地址、内网地址或规范化后越过允许路径时，适配器应拒绝请求。
6. 当相同订单号以不同金额或不同通知地址再次提交时，适配器应拒绝冲突请求并记录安全审计事件。

### 4.2 微信 Native 下单

#### PAY-002：创建微信支付订单

**优先级**：P0

**需求描述**：适配器使用微信支付 API v3 创建 Native 订单，并把微信返回的支付链接与本地订单关联。

**业务规则**：

1. 微信请求应包含已配置的 AppID、商户号、商户订单号、商品描述、人民币分金额、回调地址和订单失效时间。
2. 适配器与微信之间应使用 API v3 要求的请求签名机制。
3. 微信返回有效 `code_url` 后，本地订单方可进入待支付状态。
4. 微信下单失败时应保存失败原因；不得向用户展示密钥、完整签名报文或内部堆栈。

**验收标准**：

1. 当本地订单校验通过时，适配器应以相同商户订单号和人民币分金额向微信支付下单。
2. 当微信返回有效支付链接时，适配器应保存支付链接并引导用户进入收银台。
3. 当微信下单失败或超时时，适配器应将订单标记为创建失败或保持可重试状态，且不得伪造支付链接。
4. 当相同订单重复发起微信下单时，适配器应避免创建相互冲突的本地支付结果。

### 4.3 扫码收银台

#### PAY-003：展示支付二维码和订单状态

**优先级**：P0

**需求描述**：适配器提供独立收银台，展示订单信息、微信支付二维码、剩余有效时间和支付状态。

**业务规则**：

1. 页面至少展示商品名称、应付金额、二维码、订单有效期和当前状态。
2. 页面轮询适配器本地状态，不直接以客户端结果修改订单。
3. 订单支付成功后可跳转至已校验的 `return_url`；无有效地址时显示明确成功状态。
4. 订单超时后停止支付轮询并提示重新发起订单。
5. 收银台访问标识应不可猜测，页面不得暴露 Epay 密钥、微信密钥和内部管理信息。

**验收标准**：

1. 当订单处于待支付状态时，用户应能看到与订单金额匹配的微信支付二维码和剩余时间。
2. 当本地订单变为已支付时，收银台应在下一次状态刷新后展示支付成功。
3. 当订单过期或关闭时，收银台应停止展示可支付状态并提示重新发起充值。
4. 当 `return_url` 不存在或未通过白名单校验时，收银台应停留在结果页，不得跳转到该地址。
5. 在浏览器同步跳转被伪造或提前触发的情况下，适配器和 new-api 应均不得据此完成到账。

### 4.4 微信支付通知

#### PAY-004：安全处理微信异步通知

**优先级**：P0

**需求描述**：适配器验证微信通知真实性，解密支付资源并完成全量业务核对。

**业务规则**：

1. 通知入口为 `POST /notify/wechat`。
2. 适配器应先验证微信 HTTP 签名，再使用 API v3 密钥解密资源。
3. 仅处理交易成功通知，并核对商户号、AppID、商户订单号、币种和实付金额。
4. 金额、商户、应用或订单不一致时，订单应进入人工审查状态，不通知 new-api。
5. 支付状态更新和下游通知任务创建应在同一可靠事务边界内完成。
6. 同一订单的重复或并发通知最多完成一次状态迁移和一次有效下游到账。

**验收标准**：

1. 当微信签名和加密资源均合法且交易信息完全匹配时，适配器应将订单置为已支付并创建 new-api 通知任务。
2. 当微信签名无效、报文无法解密或交易状态不是成功时，适配器应拒绝业务处理。
3. 当商户号、AppID、订单号、币种或金额任一不匹配时，适配器应停止自动到账并将订单标记为人工审查。
4. 当同一成功通知重复发送 10 次时，适配器应仅产生一个有效支付结果和一个待完成通知任务。
5. 当适配器在支付状态更新前发生故障时，数据库事务应回滚；当状态更新已提交时，重启后应能继续下游通知。

### 4.5 通知 new-api

#### PAY-005：发送可靠的 Epay 成功回调

**优先级**：P0

**需求描述**：适配器按 Epay 回调协议把支付成功结果通知至订单创建时保存的可信 `notify_url`。

**业务规则**：

1. 回调包含 `pid`、`type`、`trade_no`、`out_trade_no`、`name`、`money`、`trade_status=TRADE_SUCCESS`、`sign_type=MD5` 和 `sign`。
2. `money` 应取自本地已核对订单的原始金额，不信任微信通知之外的临时输入。
3. 回调应使用配置的 Epay 密钥重新签名。
4. 仅当 HTTP 请求成功且响应正文去除空白后严格等于 `success` 时，通知才算完成。
5. 通知任务应持久化；建议重试节奏为立即、1 分钟、5 分钟、15 分钟、1 小时，达到自动重试上限后保留人工重试入口并告警。
6. 重试同一订单时，应保持业务标识和签名字段一致，不创建新的支付订单。

**验收标准**：

1. 当订单支付成功时，适配器应向已保存的可信通知地址发送签名正确的 Epay 成功回调。
2. 当 new-api 返回正文 `success` 时，适配器应将通知标记为成功并停止重试。
3. 当 new-api 超时、连接失败、返回非成功响应或正文不是 `success` 时，适配器应保留失败原因并按计划重试。
4. 在 new-api 暂停服务后恢复的情况下，适配器应最终完成未成功通知。
5. 在适配器重启的情况下，未完成通知任务应继续执行且不得丢失。
6. 当管理员对已支付且未通知成功的订单执行人工重试时，系统应复用原通知任务并记录操作者和结果。

### 4.6 运维与审计

#### PAY-006：订单查询、健康检查和告警

**优先级**：P1

**需求描述**：为运维和异常处理提供最小可用的健康检查、受保护查询、人工补偿、日志与指标能力。

**业务规则**：

1. 提供存活检查和就绪检查；就绪检查应反映数据库及关键配置是否可用。
2. 管理查询应支持按商户订单号查看支付状态、微信交易号、金额、支付时间、通知状态、重试次数和最近失败原因。
3. 人工重试接口应受认证和授权保护，并记录审计日志。
4. 指标至少覆盖订单创建数、支付成功数、微信回调失败数、人工审查数、通知积压数和通知失败数。
5. 日志应包含可关联的订单号和请求标识，但不得输出完整密钥、私钥或敏感支付报文。

**验收标准**：

1. 当服务进程正常运行时，存活检查应返回可用状态。
2. 当数据库不可用或必要支付配置缺失时，就绪检查应返回不可接流量状态。
3. 当授权管理员查询订单时，系统应返回足够完成支付核对的信息。
4. 当未授权请求访问管理查询或人工重试能力时，系统应拒绝访问。
5. 当通知积压、连续回调失败或订单进入人工审查时，系统应产生可观测指标并触发配置的告警。

## 5. 非功能需求

### 5.1 安全需求

| 安全项 | 要求 |
|--------|------|
| 密钥管理 | 商户私钥以只读文件或密钥服务注入；Epay 密钥和 API v3 密钥以环境密钥注入；不得写入镜像、数据库或代码仓库 |
| 传输安全 | 公网入口和下游通知仅使用 HTTPS；适配器与数据库使用受控网络 |
| 回调安全 | 微信回调先验签后解密；Epay 回调按共享密钥签名 |
| SSRF 防护 | 通知和跳转地址使用精确白名单及规范化校验；禁止访问环回、链路本地、私网和非预期端口 |
| 幂等与一致性 | 唯一约束、事务和条件更新共同保证支付和通知不会重复生效 |
| 敏感日志 | 不记录完整密钥、私钥、签名原文、解密密文或可复用支付凭据 |
| 管理权限 | 订单详情、人工重试和配置操作仅向授权管理员或运维开放并保留审计 |
| 密钥轮换 | 微信公钥或平台证书应支持按标识选择并允许新旧材料安全过渡 |

### 5.2 性能需求

| 场景 | 目标 |
|------|------|
| Epay 下单校验 | 不含微信网络耗时的服务端处理 P95 不超过 300 毫秒 |
| 收银台状态查询 | 正常负载下 P95 不超过 500 毫秒 |
| 微信通知处理 | 正常数据库状态下尽快确认，避免因同步等待 new-api 而阻塞微信回调 |
| 到账时效 | 正常链路下 95% 的成功订单在微信支付成功后 10 秒内完成 new-api 到账 |
| 重复通知 | 同一订单 10 个并发通知仍只产生一次有效状态变更 |

### 5.3 可用性与恢复

| 项目 | 要求 |
|------|------|
| 持久化 | 支付订单和通知任务不得仅保存在内存中 |
| 服务重启 | 重启后应恢复未完成通知任务和待处理状态 |
| 数据恢复 | 生产环境应建立数据库备份和恢复演练机制，目标 RPO 不超过 15 分钟 |
| 故障恢复 | 单实例故障恢复目标 RTO 不超过 1 小时 |
| 降级原则 | 微信或 new-api 不可用时停止新增或延迟完成相关步骤，不得猜测支付成功 |

### 5.4 兼容性

- 适配器应兼容 new-api 当前 Epay 表单下单及 MD5 通知约定。
- new-api 升级前应回归 Epay 字段、签名算法、回调成功正文和支付方式 `wxpay`。
- 收银台应支持当前主流桌面和移动浏览器扫码或展示支付状态。
- 部署应支持 Docker Compose；数据库版本和运行时版本在技术设计中冻结。

## 6. 业务对象定义

### 6.1 支付订单

| 属性 | 必填 | 业务约束 |
|------|------|----------|
| 内部标识 | 是 | 系统生成，不对外作为安全凭据 |
| Epay 商户 ID | 是 | 等于服务配置值 |
| 商户订单号 | 是 | 全局唯一，来源于 new-api |
| 微信交易号 | 支付后必填 | 同一成功交易唯一 |
| 商品名称 | 是 | 长度受控，输出时转义 |
| 原始金额 | 是 | 十进制元，最多两位小数 |
| 金额分 | 是 | 正整数，与原始金额精确对应 |
| 支付状态 | 是 | 按状态机流转 |
| 微信支付链接 | 待支付时必填 | 只用于生成二维码，不写入普通日志 |
| 通知地址 | 是 | 保存规范化且通过白名单的地址 |
| 跳转地址 | 否 | 保存规范化且通过白名单的地址 |
| 通知状态 | 是 | 未创建、待通知、重试中、成功、失败 |
| 通知尝试次数 | 是 | 非负整数 |
| 最近通知错误 | 否 | 脱敏保存 |
| 创建、支付、通知时间 | 按状态必填 | 使用统一时区记录 |

### 6.2 状态流转

```text
CREATED -> PAYING -> PAID -> NOTIFY_PENDING -> NOTIFY_SUCCESS
   |          |        |            |
   |          |        |            +-> NOTIFY_FAILED -> 人工重试
   |          |        +-> REVIEW
   |          +-> CLOSED
   +-> CREATE_FAILED
```

**状态规则**：

- `PAID` 只能由通过验签、解密和业务核对的微信成功通知触发。
- `REVIEW` 不得自动转为 `PAID` 或触发 new-api 通知，需经授权人工处理。
- `NOTIFY_SUCCESS` 为通知终态，重复任务不得再次改变其业务结果。
- 过期或关闭订单收到成功通知时，应进入人工审查，不得静默丢弃或直接到账。

## 7. 业务流程

### 7.1 正常支付流程

1. 充值用户在 new-api 选择 `wxpay` 并提交充值金额。
2. new-api 生成订单号和 Epay 签名，向适配器提交表单。
3. 适配器校验请求、保存订单并调用微信 Native 下单。
4. 用户进入收银台并扫码支付。
5. 微信支付向适配器发送异步通知。
6. 适配器完成验签、解密、金额与身份核对，事务性保存支付结果和通知任务。
7. 通知任务向 new-api 发送 Epay 成功回调。
8. new-api 验签并幂等完成充值，返回 `success`。
9. 适配器标记通知成功，收银台展示成功或跳回可信地址。

### 7.2 异常流程

| 场景 | 处理 |
|------|------|
| Epay 请求验签失败 | 拒绝下单，不创建订单，记录脱敏安全日志 |
| 微信下单失败 | 订单进入创建失败或可重试状态，用户重新发起或稍后重试 |
| 微信回调验签失败 | 不改变订单，返回失败并记录告警 |
| 微信金额或身份不一致 | 订单进入人工审查，不通知 new-api |
| new-api 暂时不可用 | 保留持久化任务并按计划重试 |
| 适配器在通知前重启 | 启动后扫描或调度未完成任务继续通知 |
| 同一订单重复通知 | 返回幂等结果，不重复创建任务或到账 |
| 订单超时后用户付款 | 进入人工审查，禁止自动到账 |

## 8. 界面需求

### 8.1 支付收银台

**页面目标**：让用户明确知道订单、金额、剩余时间和支付结果，并完成微信扫码。

**界面要素**：

- 商品或充值名称。
- 应付人民币金额。
- 微信支付二维码。
- 订单剩余有效时间。
- 待支付、支付成功、已超时或处理异常状态。
- 支付成功后的可信返回入口。

**交互要求**：

- 状态轮询失败时页面应保留订单信息，并提供可恢复的重试提示。
- 二维码过期后页面应停止引导付款。
- 页面文案不得声称同步跳转等同于到账完成。
- 移动端打开时应保证金额、状态和操作区域清晰可用。

## 9. 系统集成

### 9.1 集成关系

| 系统 | 集成方式 | 数据流向 | 成功判定 |
|------|----------|----------|----------|
| new-api -> 适配器 | Epay 表单下单 | 订单、金额、回调地址和签名 | 适配器返回可提交的支付结果 |
| 适配器 -> 微信支付 | API v3 Native 下单 | 商户、订单和金额 | 返回有效支付链接 |
| 微信支付 -> 适配器 | API v3 异步通知 | 加密交易结果 | 验签、解密及业务字段全部匹配 |
| 适配器 -> new-api | Epay 成功回调 | 支付结果和 MD5 签名 | HTTP 成功且正文严格为 `success` |

### 9.2 new-api 配置边界

生产部署至少需要配置：

```text
Epay 端点：https://pay.allaimo.com
回调站点：https://token-api.allaimo.com
Epay 商户 ID：10001
Epay 密钥：与适配器共享配置一致
支付方式：wxpay
```

实际充值单价、最低充值量、单笔上限和每日上限由平台运营配置决定。适配器不得自行修改 new-api 的金额和额度换算逻辑。

### 9.3 容错机制

- 微信通知处理与 new-api 通知解耦，不能因等待 new-api 响应而长期阻塞微信回调。
- 下游通知采用持久化任务和有界重试，超过自动重试上限后告警并允许人工重试。
- 每次外部调用应设置连接、读取和总超时，并记录可关联但脱敏的错误信息。
- 服务启动时应检测关键配置、密钥文件和数据库连接；未就绪时不得接收支付流量。

## 10. 部署与配置

### 10.1 推荐拓扑

```text
Internet
  |
  +-- token-api.allaimo.com:443 -> Nginx -> new-api:3000
  |
  +-- pay.allaimo.com:443 ------> Nginx -> epay-adapter:8080
                                             |
                                             +-> PostgreSQL
                                             +-> api.mch.weixin.qq.com:443
```

### 10.2 配置要求

- 支付适配器和数据库端口不得直接暴露公网。
- Nginx 应传递真实客户端 IP 和原始协议，并配置合理的请求体、连接和响应超时。
- 生产与测试环境使用不同密钥和商户配置。
- 私钥文件采用只读挂载，运行账号仅拥有必要读取权限。
- 公开支付域名应配置有效 HTTPS 证书和证书到期监控。

## 11. 上线与灰度

### 11.1 上线前置条件

- Native 支付已开通，AppID 与商户号关联关系已核验。
- 微信公钥或平台证书模式、商户证书序列号、私钥及 API v3 密钥已配置并验证。
- 支付域名、HTTPS、Nginx、数据库备份和监控已就绪。
- 最低充值、单笔上限、每日上限、数据保留和人工退款 SOP 已确认。
- 正常支付、重复通知、金额篡改、故障重启和通知失败用例全部通过。

### 11.2 灰度策略

1. 初期设置较低的单笔和每日充值上限。
2. 先由内部账号完成小额真实支付闭环。
3. 连续观察至少 20 笔订单，逐笔核对适配器订单、微信流水、new-api 订单和到账额度。
4. 在无重复到账、错账和未处理积压后逐步提高限额。
5. 发现系统性错账、验签异常或通知积压时，应立即暂停新支付入口并保留查询和补偿能力。

## 12. 风险与依赖

| 风险或依赖 | 影响 | 缓解措施 |
|------------|------|----------|
| Native 支付未开通或 AppID 未关联 | 无法创建微信订单 | 联调前在商户平台完成能力核验 |
| 微信公钥或平台证书配置错误 | 微信通知无法验签 | 按实际模式配置并测试证书轮换 |
| Epay 共享密钥泄露 | 可伪造适配器与 new-api 间消息 | 密钥托管、最小权限、定期轮换和日志脱敏 |
| 金额精度处理错误 | 错收、少收或错账 | 全链路使用十进制定点金额并覆盖边界测试 |
| 重复回调或并发处理错误 | 重复增加额度 | 唯一约束、事务、条件更新和并发回归测试 |
| new-api 临时不可用 | 用户付款后延迟到账 | 持久化通知、重试、积压告警和人工补偿 |
| new-api 升级改变 Epay 契约 | 支付链路中断 | 升级前执行 Epay 契约回归测试 |
| 首期无自动退款 | 售后依赖人工 | 上线前建立退款与额度回收 SOP |
| 收银台或回调地址校验不严 | SSRF 或开放跳转 | 精确白名单、URL 规范化和私网地址阻断 |

## 13. 验收结论门槛

本需求只有同时满足以下条件才可判定验收通过：

1. 当用户完成合法微信 Native 支付时，系统应在目标时效内完成一次且仅一次到账。
2. 当任一签名、身份、订单、币种或金额校验失败时，系统应阻止自动到账。
3. 当微信或 new-api 重复通知、超时、停机或适配器重启时，系统应保持订单一致性并可恢复处理。
4. 当管理员查询或补偿异常订单时，系统应提供完整、受控、可审计的操作链路。
5. 在镜像、代码仓库、数据库和应用日志中，测试应无法发现商户私钥或明文完整密钥。
6. 灰度期至少 20 笔真实小额订单应实现订单、支付流水、金额和到账额度一致，且无重复到账和未解释差异。
